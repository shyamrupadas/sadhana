# Автоматическое обновление приложения и восстановление после ошибки

Status: ready-for-agent

## Изначальная цель задачи

При выпуске изменений, нарушающих совместимость API, пользователь Sadhana не должен оставаться с непонятной жёсткой ошибкой и без способа продолжить работу. Приложение должно по возможности само перейти на новый frontend, а при неудаче показать понятную страницу с ручным повтором.

Решение должно быть соразмерным небольшому проекту с 10–20 пользователями. Пользователь сознательно отказался от обратной совместимости API, черновиков и согласования каждого обычного обновления кнопкой. Потеря несохранённого ввода при перезапуске допустима; уже сохранённые серверные данные не должны выдаваться за потерянные или повторно отправляться как новые команды.

## Принцип решения

Сборка встраивает собственный идентификатор во frontend и создаёт из того же значения статический `release.json`. Приложение сравнивает выполняющуюся версию с опубликованной: при запуске, каждые 10 минут, после возвращения из фона при пропущенном интервале и при неожиданной ошибке.

Если доступна другая сборка, приложение подготавливает обновление PWA и автоматически перезагружается только после его готовности. Фактическую смену выполняющейся сборки подтверждает перед показом toast «Приложение обновлено».

Обычные проверки выполняются в фоне. Только после неожиданной ошибки показывается «Проверяем обновление…» с пределом ожидания 15 секунд. Одна неудачная попытка заканчивается понятной страницей ошибки; автоматического цикла перезагрузок нет. Выкладка минимально дорабатывается: сначала зависимости, затем входные файлы, затем объявление выпуска; старые хешированные зависимости временно сохраняются по прежним URL.

## Проблема

Пользователь может долго держать приложение открытым, в том числе как установленную PWA. После публикации нового API такой клиент продолжает выполнять старый JavaScript и отправлять прежние запросы. Существующая активация service worker сама по себе не заменяет выполняющийся интерфейс. Обычная перезагрузка до подготовки обновления может снова открыть старую сборку из кэша PWA.

Общий механизм восстановления после неожиданных ошибок интерфейса и запросов отсутствует. Часть ошибок сохранения лишь откатывает оптимистическое состояние. Отдельная перезагрузка при ошибке загрузки чанка не согласована с общим ограничением попыток. Пользователю непонятно, как продолжить работу.

Нынешнее копирование статики в рабочий каталог с удалением прежних файлов создаёт два риска: доступность неполного комплекта во время выкладки и отсутствие старого чанка, который запрашивает уже открытое приложение после выкладки. Эти риски нужно уменьшить без перехода к полноценной инфраструктуре атомарных публикаций.

## Решение

### Обычная работа

- При запуске выполняется фоновая проверка версии, затем она повторяется каждые 10 минут.
- При возвращении из фона проверка выполняется сразу, если интервал с последней проверки уже прошёл. Точное расписание выполнения таймеров в приостановленном приложении не обещается.
- Пока приложение работает нормально, проверка и подготовка обновления не показывают блокирующее сообщение и не требуют действий пользователя.
- Если версия отличается, приложение загружает и подготавливает обновление PWA, затем автоматически перезапускается с сохранением текущего адреса. При отсутствии обновления продолжает работу.
- Ошибка фоновой проверки или подготовки обновления сама по себе не заменяет работающий интерфейс страницей ошибки. Следующая проверка выполняется позже.
- После подтверждённого перехода на другую сборку показывается toast «Приложение обновлено». Уже отправленные команды не повторяются; актуальное состояние заново читается с сервера.

### Неожиданная ошибка

| Ситуация | Результат |
| --- | --- |
| Неожиданная ошибка интерфейса, загрузки чанка или API | Одна общая попытка восстановления; показывается «Проверяем обновление…» |
| Другая сборка подготовлена в пределах ожидания | Одна автоматическая перезагрузка на подготовленный frontend |
| Новой сборки нет | Страница ошибки без автоматической перезагрузки той же сборки |
| Проверка или подготовка завершилась ошибкой | Страница ошибки |
| Подготовка не завершилась за 15 секунд | Страница ошибки; установка worker может продолжаться независимо |
| После автоматического перезапуска приложение снова падает до успешного восстановления | Сразу страница ошибки без второй автоматической перезагрузки |
| Обновление стало готово после перехода на страницу ошибки | Готовность используется при ручном повторе; автоматического перезапуска с этого экрана нет |

Страница ошибки сообщает: «Что-то идёт не так, обновите страницу или попробуйте позже» и содержит кнопку «Обновить страницу».

Кнопка запускает новую проверку и подготовку с ожиданием до 15 секунд. Готова новая версия — переходим на неё. Новой версии нет — по явному нажатию пользователя перезагружаем текущую страницу. Ошибка проверки/подготовки или истечение ожидания — остаёмся на странице ошибки, сохраняя возможность повторить позже. Каждое нажатие разрешает одну попытку без последующего автоматического цикла.

Отсутствие связи обрабатывается как сейчас. Ожидаемые ошибки ввода и штатное поведение авторизации сохраняют свои сценарии; они не становятся неожиданными сбоями только по факту неуспешного HTTP-статуса. При этом неожиданные ошибки сохранения сна и отметок привычек должны участвовать в общем восстановлении, а не оставаться только незаметным откатом значения.

## Решения по реализации

### Ответственности и интеграция

- Композиция запуска, маршрутизации, общего экрана ошибки и обработки сбоев принадлежит слою `app`. Общая инфраструктура HTTP, проверки версии, взаимодействия с PWA и состояния восстановления имеет небольшой публичный интерфейс в рамках существующих слоёв. `shared` не импортирует `app` или `features`.
- Используются существующие границы приложения, React Router, React Query, HTTP-клиента и Vite PWA. Не создаётся отдельный механизм обновления внутри каждой фичи и независимый перезапуск для каждого запроса.
- Обработка охватывает ошибки отображения/загрузки маршрутов и неожиданные ошибки чтения и изменения данных. Одного React Error Boundary недостаточно для асинхронных операций. Обработка ошибок мутаций подключается явно, сохраняя необходимые действия по согласованности локального состояния.
- Существующая перезагрузка при ошибке чанка включается в общую защиту. Периодический таймер, события worker и параллельные ошибки не обходят ограничение попыток.
- Экран ошибки и ручной повтор не зависят от повторной загрузки упавшей фичи или её успешных запросов. Сбои, возникшие до выполнения самого механизма восстановления, не объявляются гарантированно перехватываемыми.

### Версия и кэширование

- Идентификатор относится к конкретному артефакту сборки, одинаков для встроенной версии frontend и строкового поля `version` в `release.json`. Он определяется до сборки; повторная публикация того же артефакта сохраняет его идентификатор.
- CI передаёт идентификатор сборке web. Он учитывается в ключе кэша сборки: недопустимо восстановить старый frontend из кэша и независимо объявить ему новый идентификатор в JSON.
- Публичный ресурс `GET /release.json` расположен на origin frontend и отдаётся nginx как статический JSON. При отсутствии файла возвращается ошибка, а не HTML через SPA fallback. Неуспешный или некорректный ответ не считается сменой версии.
- Файл версии запрашивается без HTTP-кэширования и не обслуживается сохранённым ответом PWA. Для HTML и скрипта worker проверяется актуальность HTTP-ответов; неизменяемые файлы с хешами могут кэшироваться надолго.
- Сравнивается опубликованная версия с идентификатором уже выполняющегося JavaScript, а не с первым полученным сетевым ответом. Отличие означает другой выпуск; версия не обязана быть возрастающим числом.

### Готовность PWA и перезапуск

- Проверка наличия версии, установка worker, готовность его ресурсов и выполнение нового frontend — разные состояния. Разрешение Promise проверки само по себе не разрешает перезапуск.
- Учитываются уже устанавливаемый, ожидающий и активный worker, а также обновление, пришедшее из другой вкладки. Отсутствие нового события установки не доказывает актуальность выполняющегося frontend.
- Перезапуск выполняется после готовности доставки новой сборки. Использование обновлённого кэша PWA допустимо: требование относится к новому коду, а не к обязательному повторному скачиванию каждого файла из сети.
- Перед перезапуском сохраняется информация, достаточная для ограничения повторов и подтверждения смены выполняющейся сборки. Toast показывается после такой смены, а не после любой перезагрузки или смены контроллера.
- Глобальная очистка всех кэшей, переустановка PWA и самописный service worker не являются исходным способом решения; используются возможности существующего PWA-инструментария.

### Одна попытка восстановления

- После неожиданной ошибки существует одна общая попытка с пределом блокирующего ожидания 15 секунд. Бюджет не перезапускается из-за следующей параллельной ошибки или перехода между стадиями проверки и подготовки.
- Защита переживает reload и сбрасывается после успешного восстановления целевого интерфейса и необходимых ему данных. Начало выполнения документа, первая отрисовка или один успешный запрос не доказывают успешного восстановления.
- Если после перезапуска снова исполняется прежняя сборка или повторяется неожиданный сбой до восстановления, обновление не объявляется успешным и второй автоматический перезапуск не запускается.
- Если сохранение защиты недоступно, механизм не должен запускать неограниченную последовательность перезагрузок; используется страница ошибки.
- После показа страницы ошибки автоматические события готовности и периодические проверки не перезапускают приложение. Ручная кнопка разрешает новую ограниченную попытку.
- 15 секунд — согласованный предел ожидания интерфейса. Он не гарантирует отмену фоновой установки worker и не является стандартным временем её выполнения.

### Запросы и данные

- Обновление не сохраняет и не восстанавливает черновики. Несохранённый ввод может потеряться при автоматическом перезапуске.
- Уже отправленные команды после перезапуска не воспроизводятся, в том числе через очередь отложенных мутаций. Заново выполняются чтения актуального состояния.
- Прерванное клиентское ожидание не доказывает отмену серверной операции. Toast не сообщает, что прерванная команда успешно сохранена или обязательно не сохранилась.
- Обратная совместимость API, версия протокола на сервере и миграции данных не вводятся этой задачей. Экран помогает при обнаруженной ошибке, но не обнаруживает любую молчаливую смену семантики успешного ответа.

### Минимальная доработка выкладки

- Сохраняется существующий сервер статики и действующий способ публикации через CI. Полная схема каталогов выпусков с атомарным переключением и общим хранилищем не вводится.
- Сначала полностью публикуются зависимости новой сборки. Затем публикуются входные файлы приложения. `release.json` объявляет выпуск после готовности комплекта; сбой предыдущих стадий не должен объявлять новый выпуск готовым.
- Прежние хешированные файлы сохраняются по прежним публичным адресам. Учитываются зависимости вне каталога assets, включая хешированный вспомогательный код Workbox. Общий `--delete` не удаляет сохраняемые зависимости.
- Зависимости текущей и предыдущей опубликованных сборок сохраняются всегда. Остальные удаляются через 30 дней после последнего выпуска, в составе которого они использовались. Для повторно используемых файлов учитывается состав выпусков, а не только файловый mtime.
- Сбой очистки не должен приводить к удалению зависимостей защищённых выпусков. Сведения о составе выпусков сохраняются в объёме, необходимом для этой политики, без введения отдельного сервиса управления релизами.
- Последовательная публикация входных файлов оставляет остаточный риск смешанного набора ответов. Этот компромисс принят для масштаба проекта; гарантии атомарности всего сайта не заявляются.
- Перед реализацией читается фактический server block nginx и проверяются заголовки, SPA fallback и правила кэширования. Конфигурация production не была проверена при обсуждении; одного изменения CI недостаточно считать HTTP-поведение настроенным.

## Решения по проверке

### Границы проверок

Основная автоматическая граница — существующие интеграционные проверки приложения. Проверки сборки и публикации защищают внешний артефакт, а не внутреннее устройство модулей. После обратной связи пользователя специализированный автоматический браузерный контур для этой функции исключён из требований: для масштаба задачи его стоимость избыточна. Фактическое переключение service worker проверяется адресным ручным проходом собранного приложения.

1. **Web integration, Vitest/RTL:** запуск оболочки приложения, действие пользователя или управляемый ответ API → видимое сообщение, страница ошибки, доступность ручного повтора и отсутствие повторной команды. Используются существующие провайдеры, точные HTTP-подмены, управляемые часы и локальные подмены браузерных событий. Проверяются внешние последствия, а не приватное состояние координатора.
2. **Один адресный ручной проход PWA:** локально обслужить сборку A со включённым service worker, открыть приложение, затем опубликовать сборку B на том же origin и проверить автоматический перезапуск, смену выполняющегося frontend и toast. Это проверка реального переключения worker, которое Vitest с подменёнными браузерными событиями не доказывает. Новая E2E-инфраструктура, отдельная автоматизация двух сборок и новый полный сценарий с API/БД для этой задачи не требуются. Используется обычная локальная подача собранной статики и при необходимости уже доступный dev API. Production не используется.
3. **Артефакт и публикация в изолированном каталоге/статическом сервере:** одинаковый идентификатор JSON и JS; последовательность объявления выпуска; доступность прежних зависимостей; соблюдение политики очистки; JSON-ответы и заголовки без обращения к production. Не нужны проверки текста YAML или приватных команд, если поведение можно проверить результатом публикации.

Отдельный тестовый endpoint продукта, дублирующий механизм обновления, новая общая тестовая инфраструктура и специализированный автоматический PWA/E2E-набор не требуются. Ручной проход закрывает конкретный пробел проверки browser lifecycle; он не дублирует всю интеграционную матрицу.

### Критичные сценарии

| Область | Проверяемое поведение |
| --- | --- |
| Фоновый режим | Проверка при запуске, 10-минутный интервал и возврат после пропуска; отсутствие блокирующего сообщения; неудача проверки сохраняет рабочий интерфейс |
| Версия и готовность | Та же версия не вызывает автоматического reload; другая сборка запускается после готовности; некорректный JSON не выглядит обновлением; уже активировавшийся worker не маскирует старый выполняющийся код |
| Восстановление | Ошибка UI, маршрута или API достигает общего сценария; несколько ошибок используют одну попытку; предел 15 секунд; отсутствие обновления и ошибки установки приводят к странице ошибки |
| Защита от цикла | Повторный сбой после перезапуска не вызывает ещё один reload; поздняя готовность и периодический таймер не обходят страницу ошибки; текущий chunk-retry не даёт дополнительной попытки |
| Ручной повтор | Кнопка разрешает одну новую попытку; при отсутствии другой сборки перезагружает текущую страницу; при неудаче сохраняет страницу ошибки и возможность повтора |
| Данные и сообщения | После фактической смены сборки появляется toast; после перезапуска читается актуальное состояние; уже отправленная команда не отправляется повторно; отсутствие сети и ожидаемые ошибки сохраняют свои сценарии |
| Сборка и публикация | Совпадение версий в артефакте, отсутствие преждевременного объявления выпуска и устаревшего JSON; старые assets и зависимости Workbox доступны по прежним URL |
| Очистка | Текущая и предыдущая сборки защищены; возраст считается от последнего выпуска с зависимостью; прочие файлы удаляются по 30-дневной границе; ошибка публикации не запускает опасную очистку |

Это набор требований к защите регрессий, а не требование написать отдельный тест для каждой строки или продублировать матрицу на всех уровнях. Предпочтительны несколько сценариев, каждый из которых защищает связанное внешнее поведение. Для таймеров используются управляемые часы; произвольные sleeps и реальное ожидание 10 минут или 30 дней не нужны.

### Существующие образцы и порядок выполнения

- В проекте есть интеграционная проверка главной страницы с отказом сохранения отметки и откатом оптимистического значения, а также проверки авторизации с существующим test harness. Они дают образец точных подмен HTTP и проверки видимого результата. Новое общее восстановление требует дополнительной проверки на уровне оболочки, а не механического копирования тестов каждой фичи.
- Существующие Playwright-сценарии сохранения привычки и сна показывают работу с настоящими API/БД и синтетическими аккаунтами. Они остаются существующими регрессиями; новый сквозной сценарий обновления с API/БД не добавляется.
- Готовой автоматизации публикации двух PWA-сборок на момент подготовки спецификации нет. Её создание не требуется; отсутствие такой проверки не позволяет объявлять фактический lifecycle worker доказанным одними интеграционными тестами.
- По ходу реализации запускаются адресные обычные тесты. Перед финальным этапом завершаются реализация, необходимые lint/typecheck/build и проверки артефакта/публикации. Действующий порядок завершения задачи и требуемый им небольшой существующий E2E-набор сохраняются; дополнительный PWA-E2E не вводится. После подготовки артефактов выполняется описанный выше адресный ручной проход.
- Автоматическая проверка не публикует файлы на production и не удаляет рабочую статику. Цель ручного прохода — реальная смена сборки через worker и видимость toast; таймауты, варианты ошибок и повторы, уже проверенные интеграционно, вручную не перебираются заново.
- HTTP-контракт предметного API и БД этой задачей не меняются. Регенерация TypeSpec и проверки миграций требуются только при отдельном изменении их области, которого эта спецификация не предусматривает.

## Вне рамок

- Обратная совместимость API, адаптеры прежних запросов, серверная проверка минимальной версии клиента и версионирование протокола.
- Миграция статистики, изменение хранения записей дня, формул статистики, архивирования или окончательного удаления привычек.
- Сохранение черновиков, восстановление несохранённого ввода, ожидание подтверждения пользователя для обычного обновления.
- Автоматическое повторение уже отправленных команд, очередь офлайн-записей и гарантия ровно однократного выполнения серверной операции.
- Гарантированное немедленное обновление закрытого, приостановленного или офлайн-приложения; гарантированная доставка нового экрана в клиент, который его ещё не получил.
- Гарантированное обнаружение любой несовместимости API, которая не проявилась как ошибка.
- Полная атомарная публикация, схема `releases/current/shared`, смена хостинга, CDN или отдельный сервис управления выпусками.
- Специализированный автоматический E2E-набор обновления PWA и новая инфраструктура для автоматического обслуживания двух сборок. Адресная ручная проверка переключения PWA остаётся в рамках задачи.
- Глобальная очистка пользовательского хранилища, принудительная переустановка PWA, новая система мониторинга и несвязанные рефакторинги.
- Реализация, production-выпуск, изменение nginx на сервере и коммит в рамках создания этой спецификации.
