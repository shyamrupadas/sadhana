# Автоматическое обновление приложения и восстановление после ошибки

Статус: сценарий согласован. Реализация не начата.

Сценарий опубликован в [спецификации](spec.md) со статусом `ready-for-agent`; этот документ сохраняет историю согласованных решений.

2026-10-24 — пользователь принял спецификацию и уточнённый план проверок без отдельного автоматического PWA/E2E-контура. Реализация не начата.

Обсуждение ведётся отдельно от MVP статистики и перехода серверных данных. Оно не меняет ограничения `.scratch/statistics-mvp/` и не вводит обратную совместимость API.

## Согласовано

2026-10-24 — ответы пользователя:

- При неожиданном сбое интерфейса или API приложение сначала автоматически проверяет наличие обновления.
- Дополнительно приложение регулярно проверяет обновления с интервалом 10 минут.
- Обычная фоновая проверка не показывает блокирующий экран. Сообщение «Проверяем обновление…» показывается только после неожиданной ошибки.
- Если обновление доступно, приложение должно перейти на новый frontend: загрузить и подготовить обновление PWA, затем перезагрузить страницу. Перезагрузка с повторным запуском прежнего frontend не считается успешным обновлением.
- Если одна попытка восстановления не помогла, показывается страница: «Что-то идёт не так, обновите страницу или попробуйте позже». Бесконечные автоматические перезагрузки недопустимы.
- При отсутствии связи сохраняется текущее поведение приложения.
- Допустима потеря несохранённого ввода; сохранение и восстановление черновиков не требуется.
- Поддержка обратной совместимости API не требуется.
- Для старых клиентов, ещё не получивших этот механизм, допустимы нынешняя обработка ошибки и необходимость ручной перезагрузки. Предварительный выпуск механизма не гарантирует его доставку всем.
- Уже отправленные команды после перезапуска приложения ради обновления автоматически не повторяются. Загрузка актуального состояния с сервера не является повторной отправкой команды.
- После перезапуска ради обновления показывается toast «Приложение обновлено».
- **Q4 согласован:** после неожиданной ошибки показываем «Проверяем обновление…» до 15 секунд. При отсутствии новой версии, ошибке проверки/подготовки или превышении ожидания показываем страницу ошибки. Если автоматическая перезагрузка уже состоялась и приложение снова падает, сразу показываем страницу ошибки. После перехода на страницу ошибки поздняя готовность worker не вызывает автоматический перезапуск; новую попытку запускает пользователь кнопкой. Таймаут интерфейса не отменяет установку worker.
- **Q7 согласован:** добавляем `release.json`. Сборка создаёт его из того же идентификатора, который встраивается во frontend. Файл отдаёт сервер статики без HTTP-кэширования и без кэшированного ответа PWA. Сравниваем опубликованную версию с выполняющейся сборкой; перед перезапуском ждём готовности обновления PWA. Toast показывается после подтверждённой смены выполняющейся сборки.
- **Выкладка согласована в минимальном объёме:** сначала загружаем зависимости новой сборки, сохраняем старые хешированные файлы по прежним URL (включая зависимости Workbox), затем публикуем входные файлы; `release.json` объявляет выпуск после готовности комплекта. Общий `--delete` не применяется к сохраняемым зависимостям; очистка выполняется отдельно. Полную схему `releases/current/shared` пока не вводим. Остаточный риск последовательной публикации входных файлов принят как компромисс для проекта с 10–20 пользователями.
- **Q8 согласован:** проверяем обновление сразу при запуске, затем каждые 10 минут. При возвращении из фона выполняем проверку сразу, если интервал уже прошёл. Неудачная фоновая проверка не мешает работе приложения; повторяем её позже.
- **Q9 согласован:** кнопка «Обновить страницу» на странице ошибки запускает новую проверку и подготовку обновления с ожиданием до 15 секунд. Если новая версия готова, переключаемся на неё; если новой версии нет, по явному нажатию пользователя перезагружаем текущую страницу. При ошибке проверки/подготовки или истечении ожидания остаёмся на странице ошибки. Каждое нажатие разрешает одну попытку без дальнейших автоматических перезапусков.
- **Q10 согласован:** зависимости текущей и предыдущей сборки сохраняем всегда. Остальные хешированные файлы удаляем через 30 дней после последнего выпуска, в котором они использовались. Очистка не определяется только временем изменения файла: повторно используемые зависимости учитываются по составу выпусков.

## Итоговый сценарий

| Событие | Поведение |
| --- | --- |
| Запуск, очередные 10 минут или возврат после пропущенного интервала | Проверяем `release.json` в фоне без блокирующего сообщения |
| В фоне обнаружена другая сборка | Подготавливаем PWA, автоматически перезагружаемся после готовности, показываем toast после подтверждённого обновления |
| Фоновая проверка или подготовка не удалась | Сохраняем работающий интерфейс, повторяем позже |
| Неожиданная ошибка UI/API | Одна общая попытка восстановления, «Проверяем обновление…» до 15 секунд |
| После ошибки нет новой сборки, проверка/подготовка не удалась или истекло ожидание | Страница ошибки с кнопкой «Обновить страницу»; поздняя готовность не перезапускает приложение автоматически |
| Приложение снова падает после автоматического перезапуска | Сразу страница ошибки без второго автоматического перезапуска |
| Нажатие «Обновить страницу» на странице ошибки | Новая ограниченная попытка; ручная перезагрузка допустима и без новой сборки |
| После перезапуска | Заново загружаем состояние; уже отправленные команды не повторяем |
| Отсутствие связи | Текущее поведение приложения сохраняется |

Защита от повторных автоматических перезапусков должна переживать reload, объединять ошибки чанков и API и не сбрасываться раньше успешного восстановления интерфейса и необходимых данных. Одновременные ошибки используют одну попытку. Страница ошибки и ручной повтор доступны независимо от работоспособности основного экрана.

Открытых продуктовых вопросов по этому обсуждению не осталось. При реализации проверяются фактический nginx-конфиг, состав артефактов, настройки кэширования и точные точки подключения обработки ошибок. Это техническая проверка исполнения согласованного сценария, а не основание считать текущий документ реализацией.

Таймаут 15 секунд принят как предел ожидания пользователя после ошибки, а не как отраслевой стандарт длительности установки. Исследование — в [практиках PWA](research/pwa-update-practices.md); порядок минимальной выкладки — в [исследовании публикации статики](research/static-release-deploy.md).

## Обоснования и ограничения исследования

При подготовке спецификации пользователь указал на избыточность полноценного E2E обновления. План проверок уточнён: автоматическая логика проверяется через существующие интеграционные границы и артефакты публикации, реальное переключение PWA — одним адресным ручным проходом между двумя локально обслуживаемыми сборками. Новый специализированный автоматический PWA/E2E-контур не является требованием; общий порядок завершения задач репозитория сохраняется.

- Официальные примеры Workbox и Angular подтверждают порядок «новая версия готова → переключение → полная перезагрузка». Проверка наличия worker и готовность frontend — разные события.
- Универсального стандарта «15 секунд на обновление» или правила сброса одной попытки после загрузки данных в исследованных источниках не найдено. Это параметры нашего сценария.
- Таймаут интерфейса не отменяет установку worker. После показа страницы ошибки поздняя готовность сама по себе не перезапускает приложение.
- Отсутствие нового worker при проверке не доказывает актуальность выполняющегося frontend: новый worker мог активироваться раньше. Поэтому проверка актуальности выбранного решения использует `release.json`, а не только событие `updatefound`.
- Сам номер версии не доказывает готовность файлов; подготовка PWA всё равно необходима. Более простой вариант с перезагрузкой без подтверждённой новой сборки рассматривался и не выбран.
- Toast должен подтверждать фактическую смену выполняющейся сборки, а не только факт перезагрузки страницы.
- Интервал 10 минут применим к работающему приложению; в фоне браузер может задерживать таймеры. Согласованная проверка при возвращении после пропущенного интервала компенсирует задержку.

## Проверенные ограничения на момент исследования

- В `apps/web/vite.config.ts` включён `autoUpdate`, но в исходниках нет клиентского управления обновлением service worker. Активация нового worker сама по себе не заменяет выполняющийся JavaScript.
- Общей обработки неожиданных ошибок интерфейса и API сейчас нет. Некоторые ошибки сохранения лишь откатывают оптимистическое состояние.
- В `apps/web/src/shared/lib/lazy-with-retry.ts` уже есть отдельная автоматическая перезагрузка при ошибке загрузки чанка. При реализации её необходимо согласовать с общим ограничением попыток.
- Экран ошибки работает только для обнаруженного сбоя. Несовместимый запрос, который сервер принял с другой семантикой, может не вызвать ошибку; этот механизм не заменяет явного отклонения устаревших команд сервером.
