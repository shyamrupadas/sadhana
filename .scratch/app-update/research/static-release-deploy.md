# Файл версии и публикация статического frontend

Дата: 2026-10-24. Дополнение к [исследованию PWA](pwa-update-practices.md). Проверены локальные исходники и документация; production nginx не читался, конфиги и приложение не менялись. Пользователь выбрал `release.json` и минимальную доработку выкладки из раздела «Соразмерность для 10–20 пользователей». Полная схема `releases/current/shared` ниже остаётся рассмотренной альтернативой; актуальные решения — в [документе обсуждения](../decisions.md).

## Кто создаёт и отдаёт release.json

Предлагаемый `release.json` — обычный файл сборки рядом с `index.html` и `sw.js`, например `{ "version": "<build-id>" }`. Название и схема не являются стандартом HTTP/PWA. Для нашей схемы полезны три свойства: идентификатор относится к конкретному артефакту, тот же идентификатор встроен в исполняемый frontend, файл объявляет только уже опубликованный комплект.

Разделение ответственности:

| Участник | Изменение |
| --- | --- |
| CI | Определить идентификатор до сборки, например commit SHA и номер/попытку запуска; передать его сборке; опубликовать готовый артефакт |
| Сборка web | Встроить идентификатор в JavaScript и создать `dist/release.json` из того же значения |
| nginx | Отдать файл по `/release.json`, как остальные статические файлы, с правильными заголовками |
| frontend | Запросить JSON без HTTP-кэша, сравнить с собственной встроенной версией, при отличии подготовить обновление PWA |
| PWA | Не перехватывать файл кэшированным ответом; установить новую версию до управляемой перезагрузки |

Новый endpoint API для этого не нужен. nginx сопоставляет URL с файлом через `root`/`alias`; вычислять номер версии на запросе или перезапускать nginx при каждом выпуске не требуется. [nginx root](https://nginx.org/en/docs/http/ngx_http_core_module.html#root).

Для Vite можно передавать `VITE_BUILD_ID` и читать `import.meta.env.VITE_BUILD_ID`: значения подставляются при сборке. Файл JSON лучше создавать в том же build-процессе; его не нужно вручную редактировать в `public/` перед каждым выпуском. В нашем [package.json](../../../package.json) web собирается через Turbo: значение должно участвовать в кэше задачи. Turbo автоматически учитывает `VITE_*` при framework inference Vite; для иного имени следует явно добавить `env`. Нельзя сначала получить старый `dist` из кэша, а затем объявить его новым независимо сгенерированным номером. [Vite env](https://vite.dev/guide/env-and-mode.html), [Turbo env](https://turborepo.dev/docs/crafting-your-repository/using-environment-variables#framework-inference).

Предлагаемый фрагмент nginx, который при реализации нужно встроить в существующий server block:

```nginx
root /var/www/sadhana-app/current;

location = /release.json {
    add_header Cache-Control "no-store" always;
    try_files $uri =404;
}
```

Точное сопоставление не позволит отсутствующему JSON превратиться в SPA `index.html`. `no-store` управляет HTTP-кэшами; код запрашивает файл с `cache: 'no-store'`. Отдельно исключаем его из precache и правил runtime caching SW: заголовок nginx не заставит произвольный worker перестать отдавать сохранённый ответ. В нынешнем конфиге собственных runtime caching правил нет; Vite PWA по умолчанию включает JS/CSS/HTML и manifest icons, поэтому исключение нужно проверить при добавлении файла, а не предполагать, что все JSON кэшируются. [nginx headers](https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header), [Vite PWA static assets](https://vite-pwa-org.netlify.app/guide/static-assets).

Для `index.html` и `sw.js` нужна перепроверка свежести, обычно `Cache-Control: no-cache`; хешированные неизменяемые assets можно кэшировать надолго. `no-cache` означает необходимость проверки перед повторным использованием, а не запрет хранить файл. Правила `add_header` следует объединить с существующими заголовками server block, поскольку у nginx есть правила наследования. Сам `release.json` подтверждает доступность выпуска на сервере, но не завершение установки его PWA на устройстве.

## Почему текущая выкладка создаёт риск

[deploy.yml](../../../.github/workflows/deploy.yml) выполняет `rsync -avz --delete` в `/var/www/sadhana-app/html/`, одновременно используемый для раздачи файлов. `--delete` удаляет из назначения то, чего нет в новой сборке. Порядок обработки отдельных файлов не образует транзакцию публикации всего сайта. [Документация rsync](https://download.samba.org/pub/rsync/rsync.1).

Первый сценарий — публикация B ещё идёт, но новый `index.html` уже доступен. Он ссылается на `/assets/main-B.js`, который пока не скопирован. Пользователь получает ошибку загрузки. Аналогично новый `sw.js` может начать установку до доступности всех его файлов. Сбой передачи может оставить такой смешанный каталог до следующей выкладки. Это возможные порядки событий, а не утверждение, что rsync всегда обрабатывает HTML первым.

Второй сценарий существует и после успешного завершения копирования. У пользователя выполняется выпуск A; переход на статистику запрашивает `/assets/statistics-A.js`. После `--delete` на сервере остался только файл B. Старый URL возвращает 404. Vite прямо описывает такую причину ошибок динамического импорта. PWA помогает, если ресурс сохранился в кэше, но серверная публикация не должна полагаться на наличие каждого старого файла у каждого устройства. [Vite load errors](https://vite.dev/guide/build#load-error-handling).

## Предлагаемая замена

```text
/var/www/sadhana-app/
  releases/
    A/  index.html, sw.js, release.json, ...
    B/  index.html, sw.js, release.json, ...
  shared/
    assets/  main-A.js, main-B.js, statistics-A.js, statistics-B.js, ...
    workbox-<hash-A>.js
    workbox-<hash-B>.js
  current -> releases/B
```

CI загружает новый выпуск в собственный каталог, не изменяя `current`. После полной загрузки проверяет файлы и добавляет хешированные зависимости в общий каталог. Их публикация заканчивается до переключения: частично загруженный asset не должен становиться доступным под финальным именем. При совпадении имени содержимое должно совпадать; хешированные файлы не перезаписываются изменёнными байтами.

nginx отдаёт `/assets/` из `shared/assets/` через `alias`, а HTML, `sw.js`, manifest и `release.json` — из `current`. Корневые хешированные зависимости SW также направляются в `shared`. В локальном `apps/web/dist` реально есть `workbox-9c191d2f.js`, поэтому ограничиться только каталогом `assets` нельзя. При реализации нужен список всех таких зависимостей из фактического артефакта. [nginx alias](https://nginx.org/en/docs/http/ngx_http_core_module.html#alias).

После проверок создаётся временная ссылка на готовый B и переименовывается поверх `current` одной операцией на той же файловой системе. На Linux `rename` атомарно заменяет имя, в том числе символическую ссылку. Нельзя сначала удалить `current`, а затем создать новую ссылку: это вернёт окно отсутствующего сайта. Обычная смена ссылки не требует reload nginx, если действующий конфиг допускает её использование; настройки кэша открытых файлов и ограничений symlink нужно проверить на сервере. [Linux rename](https://man7.org/linux/man-pages/man2/rename.2.html).

Старые хешированные файлы сохраняются на переходный период и удаляются отдельной очисткой по выбранной политике. Хранение старого `releases/A` само по себе недостаточно: `/assets/statistics-A.js` не начнёт автоматически искать файл в A после смены `current`. Для этого и нужен общий маршрут; альтернативы — URL с идентификатором выпуска либо перенос старых хешированных файлов в каждый следующий каталог.

Атомарная ссылка устраняет чтение незавершённого каталога и позволяет не объявлять новый `release.json` до загрузки файлов. Она не делает серию HTTP-запросов браузера одной транзакцией: HTML мог прийти до переключения, а JS — после. Сохранение адресуемых неизменяемых зависимостей закрывает именно этот переход. Для полного закрепления всех ресурсов за выпуском потребуются версионированные URL; для небольшого приложения предложенная схема практичнее. Совместимость API и уже выполняющийся код она не гарантирует.

Изменения ограничены build web, шагами CI и одноразовой настройкой nginx. Для реализации сначала нужно прочитать настоящий nginx server block: в репозитории его нет.

## Соразмерность для 10–20 пользователей

Пользователь уточнил масштаб проекта. Полная схема выше — вариант повышения надёжности, а не обязательное условие выпуска автообновления. Длительность текущей выкладки, частота ошибок и число активных во время неё пользователей не измерены; количественную вероятность сбоя по одному числу аккаунтов оценить нельзя. Малый масштаб снижает ожидаемое число затронутых людей, но не устраняет запросы старых чанков после завершения выкладки.

Атомарная публикация соответствует распространённой практике: например, Netlify публикует выпуск после загрузки всех файлов. Это подтверждает полезность принципа, но не обязывает небольшой проект самостоятельно воспроизводить всю инфраструктуру хостинга. [Netlify atomic deploys](https://docs.netlify.com/deploy/deploy-overview/#how-atomic-deploys-work).

С учётом принятой допустимости потери ввода и ручного восстановления моя соразмерная рекомендация — сначала минимально доработать порядок публикации: загрузить новые хешированные зависимости, сохранить прежние по прежним URL, затем публиковать входные файлы и объявлять `release.json` после готовности комплекта. Не применять общий `--delete` к сохраняемым зависимостям; предусмотреть отдельную очистку. Этот компромисс уменьшает риски, но не делает обновление нескольких входных файлов атомарным. Переход к `releases/current/shared` можно отложить до повторяющихся ошибок выкладки, частых релизов, необходимости удобного отката статики или более строгих требований к доступности.

Пользователь согласовал эту минимальную рекомендацию; полная атомарная публикация отложена. Зависимости текущей и предыдущей сборки сохраняются всегда; прочие хешированные файлы удаляются через 30 дней после последнего выпуска, в котором они использовались. Конфиги и CI не изменены.
