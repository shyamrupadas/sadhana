# 02: Фоновое автоматическое обновление PWA

**What to build:** Пользователь открывает приложение или продолжает работать в нём, а оно незаметно проверяет опубликованную версию, подготавливает доступное обновление PWA и автоматически переходит на новый frontend. После фактического обновления появляется toast «Приложение обновлено», текущий адрес сохраняется, уже отправленные команды не повторяются.

**Blocked by:** 01 — Публикация версии и сохранение файлов прежних сборок

**Status:** ready-for-agent

- [ ] Клиент сравнивает версию из `release.json` с идентификатором выполняющегося JavaScript. Первое сетевое значение не принимается за собственную версию; некорректный JSON или неуспешный ответ не считаются новым выпуском.
- [ ] Проверка выполняется сразу при запуске, затем каждые 10 минут. При возвращении из фона она выполняется сразу, если интервал с последней проверки уже прошёл. Приостановленному приложению не обещается точное фоновое расписание.
- [ ] Обычная проверка и подготовка не показывают блокирующее сообщение и не требуют нажатия кнопки. Ошибка фоновой проверки/подготовки оставляет работающий интерфейс, следующая проверка выполняется позже.
- [ ] При той же версии автоматической перезагрузки нет. Для другой сборки обновление загружается и подготавливается через существующие средства PWA; клиент перезапускается после готовности доставки нового frontend.
- [ ] Различаются проверка, установка, готовность worker и выполнение нового frontend. Учитываются уже активировавшийся, устанавливаемый и ожидающий worker, а также обновления из другой вкладки. Одно разрешение Promise проверки или отсутствие нового события установки не определяет актуальность кода.
- [ ] Обновление управляется общей координацией на уровне приложения. Параллельные проверки и события worker не вызывают независимые перезапуски в обход неё; сохраняются направления зависимостей существующих слоёв frontend.
- [ ] Перед перезапуском сохраняется достаточно информации для подтверждения смены сборки и ограничения повторов. Защита переживает reload и не сбрасывается раньше успешного восстановления интерфейса и необходимых данных. Если сохранить защиту нельзя, бесконечные автоматические перезапуски не допускаются.
- [ ] После подтверждённого перехода на другую выполняющуюся сборку показывается toast «Приложение обновлено». Обычный reload той же сборки или смена контроллера сами по себе не вызывают этот toast.
- [ ] Перезапуск сохраняет текущий адрес. Затем приложение заново читает актуальное состояние; ранее отправленные команды не воспроизводятся, в том числе через очередь мутаций. Toast не обещает успешного сохранения прерванной команды.
- [ ] Несохранённый ввод не сохраняется в черновики; переустановка PWA и глобальная очистка пользовательских кэшей/хранилища не используются как обычный способ обновления.
- [ ] Интеграционные проверки защищают расписание, незаметность фоновой проверки, реакцию на ту же/другую версию, ожидание готовности, обработку фоновой неудачи, подтверждение toast и отсутствие повторной команды. Проверяются внешние последствия; часы и браузерные события управляются локально в тестах.
- [ ] После подготовки артефактов выполнен один адресный ручной проход: сборка A открыта в локальном браузере с настоящим service worker, затем на том же origin опубликована B; подтверждены новый frontend, сохранение адреса и toast. Новая автоматическая инфраструктура PWA/E2E и полный сквозной сценарий с API/БД не добавляются.

## Границы и проверка

Источник: [принятая спецификация](../spec.md), сценарий обычной работы и решения о готовности PWA. Тикет опирается на достоверный ресурс версии и публикацию из 01.

Общий экран восстановления, предел 15 секунд после ошибки, ручной повтор и подключение ошибок интерфейса/API принадлежат тикету 03. В этом тикете создаётся общий путь подготовки/перезапуска, пригодный для их подключения; нельзя заранее вводить независимые перезагрузки, которые затем дадут несколько попыток.

Применяются существующие интеграционные границы и действующий порядок завершения задач. Специализированный автоматический PWA/E2E не требуется; обычные обязательные проверки репозитория сохраняются. Ручной проход выполняется локально и не требует production-публикации.
