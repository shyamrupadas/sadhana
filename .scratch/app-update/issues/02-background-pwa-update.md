# 02: Фоновое автоматическое обновление PWA

**What to build:** Пользователь открывает приложение или продолжает работать в нём, а оно незаметно проверяет опубликованную версию, подготавливает доступное обновление PWA и автоматически переходит на новый frontend. После фактического обновления появляется toast «Приложение обновлено», текущий адрес сохраняется, уже отправленные команды не повторяются.

**Blocked by:** 01 — Публикация версии приложения

**Status:** awaiting-human-review

- [x] Клиент сравнивает версию из `release.json` с идентификатором выполняющегося JavaScript. Первое сетевое значение не принимается за собственную версию; некорректный JSON или неуспешный ответ не считаются новым выпуском.
- [x] Проверка выполняется сразу при запуске, затем каждые 10 минут. При возвращении из фона она выполняется сразу, если интервал с последней проверки уже прошёл. Приостановленному приложению не обещается точное фоновое расписание.
- [x] Обычная проверка и подготовка не показывают блокирующее сообщение и не требуют нажатия кнопки. Ошибка фоновой проверки/подготовки оставляет работающий интерфейс, следующая проверка выполняется позже.
- [x] При той же версии автоматической перезагрузки нет. Для другой сборки обновление загружается и подготавливается через существующие средства PWA; клиент перезапускается после готовности доставки нового frontend.
- [x] Различаются проверка, установка, готовность worker и выполнение нового frontend. Учитываются уже активировавшийся, устанавливаемый и ожидающий worker, а также обновления из другой вкладки. Одно разрешение Promise проверки или отсутствие нового события установки не определяет актуальность кода. При обычном `rsync --delete` новая версия в JSON может появиться до завершения передачи остальных файлов: она не доказывает готовность обновления. Если подготовка из-за этого не удалась, сохраняется работающий интерфейс и следующая проверка выполняется позже.
- [x] Обновление управляется общей координацией на уровне приложения. Параллельные проверки и события worker не вызывают независимые перезапуски в обход неё; сохраняются направления зависимостей существующих слоёв frontend.
- [x] Перед перезапуском сохраняется достаточно информации для подтверждения смены сборки и ограничения повторов. Защита переживает reload и не сбрасывается раньше успешного восстановления интерфейса и необходимых данных. Если сохранить защиту нельзя, бесконечные автоматические перезапуски не допускаются.
- [x] После подтверждённого перехода на другую выполняющуюся сборку показывается toast «Приложение обновлено». Обычный reload той же сборки или смена контроллера сами по себе не вызывают этот toast.
- [x] Перезапуск сохраняет текущий адрес. Затем приложение заново читает актуальное состояние; ранее отправленные команды не воспроизводятся, в том числе через очередь мутаций. Toast не обещает успешного сохранения прерванной команды.
- [x] Несохранённый ввод не сохраняется в черновики; переустановка PWA и глобальная очистка пользовательских кэшей/хранилища не используются как обычный способ обновления.
- [x] Интеграционные проверки защищают расписание, незаметность фоновой проверки, реакцию на ту же/другую версию, ожидание готовности, обработку фоновой неудачи, подтверждение toast и отсутствие повторной команды. Проверяются внешние последствия; часы и браузерные события управляются локально в тестах.
- [x] После подготовки артефактов выполнен один адресный ручной проход: сборка A открыта в локальном браузере с настоящим service worker, затем на том же origin опубликована B обычным `rsync --delete` с удалением старых файлов; подтверждены новый frontend, сохранение адреса и toast. Новая автоматическая инфраструктура PWA/E2E и полный сквозной сценарий с API/БД не добавляются.

## Границы и проверка

Источник: [принятая спецификация](../spec.md), сценарий обычной работы и решения о готовности PWA. Тикет опирается на достоверный ресурс версии и публикацию из 01.

Общий экран восстановления, предел 15 секунд после ошибки, ручной повтор и подключение ошибок интерфейса/API принадлежат тикету 03. В этом тикете создаётся общий путь подготовки/перезапуска, пригодный для их подключения; нельзя заранее вводить независимые перезагрузки, которые затем дадут несколько попыток.

Применяются существующие интеграционные границы и действующий порядок завершения задач. Специализированный автоматический PWA/E2E не требуется; обычные обязательные проверки репозитория сохраняются. Ручной проход выполняется локально и не требует production-публикации.


## Comments

### Реализация и проверки — 2026-10-31

Реализована единая фоновая координация в `shared/lib/app-update.ts`: сравнение с выполняемым `VITE_BUILD_ID`, проверка при запуске, интервал 10 минут и возврат после пропуска. Регистрацией стандартного Workbox worker управляет приложение; независимая инъекция регистрации отключена. Готовность подтверждается версией precached HTML активного контроллера, а не завершением `registration.update()`. Версия HTML создаётся из того же значения, что JavaScript и `release.json`.

Перед reload сохраняется защита в `sessionStorage`. При недоступности хранилища автоматического reload нет. Toast и снятие защиты разрешены после реальной смены выполняемой сборки и успешной загрузки активных запросов страницы. Кэш мутаций не сохраняется, команды не воспроизводятся. Фоновое ожидание ограничено одной минутой, включая регистрацию; браузерная установка может продолжаться независимо. Общий экран ошибки и подключение ошибок остаются в тикете 03.
