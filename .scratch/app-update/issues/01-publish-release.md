# 01: Публикация версии приложения

**What to build:** Каждая сборка имеет публичную версию, которая совпадает с версией выполняющегося frontend. CI публикует готовый dist прежним rsync с удалением файлов старых сборок. Это даёт клиенту основу для автоматического обновления без отдельного механизма хранения выпусков.

**Blocked by:** None (can start immediately)

**Status:** awaiting-human-review

- [x] Сборка автоматически получает идентификатор конкретного артефакта, встраивает его во frontend и создаёт `release.json` только со строковым полем `version` из того же значения. Ручное увеличение номера не требуется; повторная публикация того же артефакта сохраняет идентификатор.
- [x] CI передаёт идентификатор в формате `YYYY-MM-DD-<8 символов SHA>` без номера запуска или попытки до сборки, и он учитывается в её кэше. Старый frontend, восстановленный из кэша, не объявляется новой сборкой через независимо созданный JSON.
- [x] Публичный `GET /release.json` на origin frontend возвращает актуальный JSON без HTTP-кэширования. Отсутствующий файл возвращает ошибку, а не HTML через SPA fallback. PWA не подменяет запрос сохранённым ответом.
- [x] Перед подготовкой настроек nginx проверен фактический server block. Для HTML и скрипта worker предусмотрена проверка свежести HTTP-ответов; правила учитывают существующие заголовки и маршрутизацию.
- [x] CI использует один существующий `rsync -avz --delete` из готового `dist` прямо в web root. `release.json` передаётся вместе с остальными файлами; отдельного порядка публикации не требуется.
- [x] Файлы, отсутствующие в новой сборке, удаляются при синхронизации, включая старые assets и корневые зависимости Workbox. Доступность прежних чанков не гарантируется.
- [x] Собственный скрипт публикации, Python, журнал, маркеры, manifest контрольных сумм, каталоги incoming и отдельная очистка не вводятся. Временные ошибки при передаче статики и ошибки загрузки удалённых старых чанков — принятый компромисс.
- [x] Проверка артефакта подтверждает совпадение версии JSON и выполняемой сборки. Синхронизация с удалением прежних assets и Workbox проверена в изолированном каталоге; production не используется.
- [x] Выдача JSON, отсутствие SPA fallback для него и заголовки проверены на локальном/тестовом статическом сервере. Проверки не публикуют файлы в production и не удаляют рабочую статику.

## Границы и проверка

Источник: [принятая спецификация](../spec.md), разделы о версии, кэшировании и простой выкладке. Клиентские обновление и toast реализуются в тикете 02, ошибки удалённых старых чанков участвуют в общем восстановлении из тикета 03. Хранение прежних выпусков и отдельная очистка исключены.

Результат проверяется через внешний артефакт и HTTP-ответы. Простой rsync не обещает атомарность комплекта или объявление версии только после завершения всех передач. После прерывания можно повторить выкладку.

При завершении реализации применяется действующий порядок проверок репозитория. Создание этого тикета не разрешает самостоятельный production-выпуск.

## Comments

### Текущее состояние после окончательного упрощения

Сохранены единая версия артефакта, `release.json` только с полем `version`, учёт идентификатора в Turbo cache и исключение JSON из precache/navigation fallback PWA. Выкладка остаётся исходным одним `rsync --delete`: без shell-скрипта, хранения старых зависимостей, журналов, маркеров и отдельной очистки. Тикет 04 отменён по решению пользователя.

2026-10-31 фактические права VDS и nginx проверены. Через admin/sudo применены правила `no-store` для JSON, `no-cache` для HTML и worker и 404 для отсутствующего JSON. Кандидат и полная конфигурация прошли `nginx -t`, reload и прямые origin-проверки успешны. Изолированный nginx подтвердил выдачу существующего JSON и 404 без SPA fallback. Резервная копия и команды восстановления описаны в [операционном документе](../../../docs/operations/app-update-nginx.md). Production-статика и API не публиковались; изменения относятся только к nginx.

Проверка во временном каталоге настоящим `rsync -avz --delete` подтвердила публикацию новых файлов и удаление прежних assets и Workbox. Граф зависимостей 01 → 02 → 03 корректен. `pnpm typecheck` и `pnpm test` успешны с результатами из Turbo cache. Ревью Standards и Spec — без замечаний к упрощению. Финальный E2E выполнен после завершения HTTP-проверок; результат фиксируется ниже.

### Итоговые проверки

- Исследовательская проверка: настоящий dist в Chromium подтвердил совпадение выполняемой версии с `release.json`; изолированный nginx на VDS подтвердил JSON/404 и cache policy.
- Внешние HTTPS-проверки после применения: HTML, `/login` и worker — 200 с `no-cache`; отсутствующий в текущей production-сборке `/release.json` — 404 с `no-store`. Конфигурации остальных сайтов не менялись, три соседних сайта отвечают 200.
- `pnpm typecheck`, `pnpm test`, lint web и сборка web выполнены успешно; повторные обычные проверки использовали Turbo cache.
- Автоматические E2E: `pnpm test:e2e` вне песочницы — 5 passed. Первая попытка в песочнице не смогла запустить dev API и не считается успешной.
