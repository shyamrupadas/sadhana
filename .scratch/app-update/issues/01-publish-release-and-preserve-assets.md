# 01: Публикация версии и сохранение файлов прежних сборок

**What to build:** Каждый готовый выпуск имеет достоверный публичный номер версии, который совпадает с номером выполняющегося frontend. Новый выпуск объявляется после загрузки его файлов, а открытые приложения сохраняют доступ к хешированным зависимостям прежних сборок. Это даёт клиенту основу для автоматического обновления и уменьшает ошибки загрузки при выкладке.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [ ] Сборка автоматически получает идентификатор конкретного артефакта, встраивает его во frontend и создаёт `release.json` со строковым полем `version` из того же значения. Ручное увеличение номера не требуется; повторная публикация того же артефакта сохраняет идентификатор.
- [ ] CI передаёт идентификатор до сборки, и он учитывается в её кэше. Старый frontend, восстановленный из кэша, не объявляется новой сборкой через независимо созданный JSON.
- [ ] Публичный `GET /release.json` на origin frontend возвращает актуальный JSON без HTTP-кэширования. Отсутствующий файл возвращает ошибку, а не HTML через SPA fallback. PWA не подменяет запрос сохранённым ответом.
- [ ] Перед подготовкой настроек nginx проверен фактический server block. Для HTML и скрипта worker предусмотрена проверка свежести HTTP-ответов; правила учитывают существующие заголовки и маршрутизацию.
- [ ] CI сначала полностью публикует зависимости новой сборки, затем входные файлы приложения и только после готовности комплекта объявляет выпуск через `release.json`. Сбой предыдущих стадий не объявляет новый выпуск готовым.
- [ ] Прежние хешированные файлы остаются доступны по прежним URL. Сохраняются также зависимости вне каталога assets, включая вспомогательный код Workbox. Общий `--delete` не удаляет сохраняемые файлы.
- [ ] Для успешных публикаций учитываются идентификатор, время публикации и состав зависимостей в объёме, необходимом для определения текущего/предыдущего выпуска и последнего использования файла. Неудачная публикация не становится успешным выпуском в этих сведениях.
- [ ] До реализации очистки из тикета 04 сохранённые старые зависимости автоматически не удаляются. Задача не вводит полную схему атомарных публикаций или отдельный сервис управления выпусками.
- [ ] Проверки артефакта подтверждают совпадение версии JSON и выполняемой сборки. Изолированная проверка публикации подтверждает порядок объявления, сохранение старых зависимостей и поведение при незавершённой загрузке.
- [ ] Выдача JSON, отсутствие SPA fallback для него и заголовки проверены на локальном/тестовом статическом сервере. Проверки не публикуют файлы в production и не удаляют рабочую статику.

## Границы и проверка

Источник: [принятая спецификация](../spec.md), разделы о версии, кэшировании и минимальной выкладке. Клиентские таймеры, автоматический перезапуск и toast реализуются в тикете 02; возрастная очистка — в тикете 04.

Результат проверяется через внешний артефакт и HTTP-ответы, а не сравнение текста CI-конфига или приватных команд. Сведения о составе выпусков доступны последующей очистке без зависимости от клиентского обновления. Остаточный риск последовательной публикации входных файлов сохраняется согласно спецификации.

При завершении реализации применяется действующий порядок проверок репозитория. Создание этого тикета не разрешает самостоятельный production-выпуск.
