# Локальные сквозные проверки

## Уровни и команды

E2E проверяют критичные пользовательские пути через настоящий браузер, frontend, API и PostgreSQL. Собственный API и хранилище не подменяются; синтетические тестовые данные допустимы.

Сквозной набор включает четыре сценария:

- Регистрация, открытие приложения и последующий вход с этими данными в новом контексте браузера.
- Вход и выход существующего пользователя.
- Создание привычки и сохранение полного цикла отметки после перезагрузки.
- Сохранение сна через полночь с проверкой после перезагрузки.

Ошибки ввода и перенаправление гостя проверяются через Vitest/RTL как frontend integration. Успешные пути повторяются на нескольких уровнях только при наличии дополнительной полезной гарантии.

Корневой `pnpm test` выполняет обычные тесты всех пакетов без браузера; web-команда `test` запускает Vitest. Корневой `pnpm test:e2e` запускает сквозной набор без кэширования результата Turbo. CI выполняет обычные тесты; E2E в CI не запускаются.

## Порядок проверок

Во время разработки выполняются адресные проверки нижних уровней. E2E запускаются после завершения всей задачи, исправления обнаруженных дефектов и успешного прохождения остальных необходимых проверок, в том числе когда тестовые файлы не менялись. Более ранний запуск выполняется по явному запросу пользователя.

После падения финального E2E исправляется причина, адресно повторяется затронутая проверка, затем весь небольшой сквозной набор. E2E не включены в watch и hooks. Изменения только документации, комментариев и опечаток по умолчанию не требуют тестов, lint и сборок.

## Сервисы и данные

Локальные E2E используют постоянную Neon dev-базу. Playwright переиспользует уже работающие dev-web и API. Недостающие сервисы запускаются командами `pnpm dev:api` и `pnpm dev:web` из корня проекта. После прогона Playwright отправляет SIGINT с таймаутом 5 секунд только сервисам, которые запустил сам.

Сценарии создают собственные аккаунты и записи. Очистка адресная, выполняется и после упавших сценариев. Создание аккаунта фиксируется в локальном manifest до записи в БД или отправки регистрации. При следующем запуске повторяется очистка прерванных прогонов; активные прогоны и обычные dev-профили сохраняются.

Перед сценариями проверяются конфигурация dev-цели и готовность схемы. Миграции автоматически не применяются. Подключение переиспользуемого API подтверждается входом с уникальным аккаунтом, предварительно созданным в проверенной dev-базе. Проверка подтверждает подключение к базе, но не конкретный worktree.

Подготовка и очистка данных выполняются утилитой API-пакета с существующими `pg`, bcrypt и проверкой dev-конфигурации. Постоянная dev-база не сбрасывается.

## Проверки

- `pnpm test`: API — 50 passed, 22 skipped (отдельные PostgreSQL-сценарии), contract — 10 passed, web Vitest — 6 passed.
- `pnpm lint`, `pnpm typecheck`: успешно. Сборки API/web и контракта выполняются как зависимости обычных тестов.
- Итоговый `pnpm test:e2e`: 4 passed за 36,6 секунды. После завершения сервисы и watcher-процессы остановлены, порты 8080/5173 свободны, manifests временных аккаунтов отсутствуют.
