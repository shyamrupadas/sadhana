# Реальный API и PostgreSQL в тестировании: первоисточники

Дата проверки: 2026-10-18. Исследовательская заметка для обсуждения; предложения ниже не являются принятыми решениями. Изменения тестов и CI не выполнялись.

## Подтверждённые факты

1. **Fastify поддерживает тестирование приложения без отдельного HTTP-процесса.** Официальный guide разделяет создание приложения и запуск сервера. `app.inject()` формирует запрос к приложению и дожидается загрузки плагинов; отдельно показано тестирование через настоящий listening socket. После теста рекомендуется `app.close()` для закрытия соединений с внешними сервисами. Таким образом, слово «fake» в описании HTTP injection относится к транспорту запроса, а не требует подмены БД. Последнее — вывод из устройства примеров. [Fastify: Testing](https://fastify.dev/docs/latest/Guides/Testing/).

2. **Браузерная изоляция не устраняет общее серверное состояние.** Playwright рекомендует независимые тесты и контролируемые данные БД. Для конкурирующих изменений данных документация предлагает уникальные записи на тест либо изоляцию данных между workers; browser contexts изолируют cookies, storage и память браузера. [Playwright: Best Practices](https://playwright.dev/docs/best-practices), [Playwright: Parallelism](https://playwright.dev/docs/test-parallel).

3. **В CI не нужна постоянно доступная dev-БД.** GitHub Actions создаёт новый service container на каждый job и удаляет его после завершения. Официальный пример PostgreSQL задаёт `POSTGRES_PASSWORD`, healthcheck `pg_isready` и проброс порта; job на runner подключается к `localhost`, job в контейнере — по имени сервиса. Нужен Linux runner; GitHub-hosted вариант — Ubuntu. [GitHub: Service containers](https://docs.github.com/en/actions/tutorials/use-containerized-services/use-docker-service-containers), [GitHub: PostgreSQL service](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers).

4. **Playwright сам может запускать frontend и backend.** `webServer` принимает массив конфигураций процессов с командой, адресом готовности и таймаутом. Пример использует `reuseExistingServer: !process.env.CI`; это позволяет локальное переиспользование, а в CI ожидает запуск управляемого процесса. [Playwright: Web server](https://playwright.dev/docs/test-webserver).

5. **Есть штатные способы сократить подготовку E2E.** `APIRequestContext` подходит для создания предусловий и проверки результата серверного изменения. Cookie storage можно переносить между API request context и browser context; `page.request` разделяет cookies с браузером. [Playwright: API testing](https://playwright.dev/docs/api-testing).

6. **Авторизация через реальный API не требует проходить форму в каждом сценарии.** Playwright допускает API login и повторное использование `storageState`. Общий аккаунт подходит, когда тесты не конфликтуют через серверное состояние; для параллельных изменений рекомендуются разные аккаунты. Сохранённое состояние может содержать cookies, позволяющие выдать себя за пользователя, поэтому его не следует коммитить. [Playwright: Authentication](https://playwright.dev/docs/auth).

7. **CI для браузерных тестов — обычный поддерживаемый сценарий.** Официальное руководство показывает GitHub Actions, установку браузеров, запуск тестов и сохранение отчёта. Для стабильности рекомендует начать с одного worker. Best Practices советует запускать тесты часто, в идеале на commit/PR, и скачивать только используемые браузеры. [Playwright: CI](https://playwright.dev/docs/ci), [Playwright: Best Practices](https://playwright.dev/docs/best-practices).

8. **Не нужно переносить всю проверку на полную цепочку.** Авторский материал Google объясняет, почему большой E2E-набор хуже локализует ошибки и дороже поддерживается; рекомендует проверять взаимодействие компонентов более узкими integration tests, когда они обнаруживают тот же дефект. Это инженерная рекомендация, не универсальная численная квота. [Mike Wacker, Google Testing Blog](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html).

9. **Транзакционный rollback не является универсальной очисткой E2E.** `node-postgres` требует один и тот же client для всех SQL внутри транзакции; `pool.query()` нельзя использовать как замену этому требованию. Следовательно, `BEGIN` из test setup не охватывает автоматически запросы API, выполненные через другие соединения. [node-postgres: Transactions](https://node-postgres.com/features/transactions).

10. **Удалённые изолированные БД тоже возможны.** Neon документирует независимые branches, schema-only вариант и branch на отдельный test run. Это альтернатива контейнеру, а не основание выполнять все прогоны на одной постоянной dev-ветке. [Neon: Branching workflows](https://neon.com/docs/get-started-with-neon/workflow-primer).

## Контекст репозитория

По `apps/api/package.json` используется Fastify 5 и `pg` 8; по `apps/web/package.json` — Playwright 1.63, Vitest и зависимость MSW. Наличие зависимости само по себе не означает её использование в тестах; текущие API-моки используют `fetch`/`page.route`. [CI workflow](../../../.github/workflows/contract.yml) уже запускается на PR и push в `master`, но перечисленные тестовые шаги используют `db.invalid` и не поднимают PostgreSQL или Playwright. [Deploy workflow](../../../.github/workflows/deploy.yml) проверяет только результат job `workspace-and-image` перед web-deploy: отдельный новый job сам по себе не станет условием выпуска, для этого потребуется расширить проверку. Это факты текущих файлов, а не оценка всех существующих тестов; их детализация находится в отдельном аудите.

## Предложения для обсуждения

- **Развести среды по назначению.** Постоянная Neon dev-ветка удобна для ручной разработки; автоматический прогон получает отдельную disposable БД с миграциями из текущего checkout и минимальными синтетическими fixtures. Настоящая БД совместима с искусственными, воспроизводимыми данными. Случайный накопленный dev-набор даёт скрытую зависимость от истории среды.
- **Основную новую уверенность получать через API + реальный PostgreSQL.** Для SQL, ограничений, авторизации и сохранения данных подходит `app.inject()` с настоящими плагинами приложения и БД. Отдельный listening process нужен там, где проверяется сеть/запуск или цепочка браузер → API.
- **Добавить небольшой набор полных пользовательских маршрутов.** Например, login через UI → изменение состояния → reload → сохранённый результат; refresh/logout; отклонение неавторизованного доступа. Оставить точные API-моки для UI-состояний: loading, ошибки, редкие ответы. Полный набор UI-ветвлений не обязан дублироваться с БД.
- **Одинаковая воспроизводимая цепочка локально и в CI:** чистый PostgreSQL нужной major-версии → миграции → fixtures → API → web → несколько E2E → очистка. Предварительно измерить длительность; для соло-разработчика начать с одного worker и Chromium, без sharding и облачных preview-сред. Периодичность и блокировку deploy решить по цене прогона и риску дефектов.
- **Сохранять реальные auth-механизмы.** В проекте собственный email/password + bcrypt + JWT/cookies/refresh; внешний OAuth для предложенной схемы не требуется. Setup может логиниться через API обычным тестовым пользователем. Для целевого smoke login остаётся через UI; выпуск JWT прямо из fixtures не проверяет login/cookie-цепочку.

Контейнерный PostgreSQL не доказывает исправность Neon pooling, TLS, удалённого сетевого доступа или production cookie/domain-конфигурации. Нужен ли отдельный редкий smoke для этих границ — открытый вопрос; это не причина переносить весь автоматический suite на общую dev-БД.

## Дополнение 2026-10-19: ресурсы CI и допустимые варианты среды

В обсуждении поддержана смешанная схема тестирования. Обязательность запуска в CI, его периодичность и влияние на выпуск остаются открытыми; реализация не выполнялась.

- **Ресурсы runner.** Стандартный `ubuntu-latest` для private-репозитория предоставляет 2 CPU и 8 GB RAM; для public — 4 CPU и 16 GB RAM. API, PostgreSQL, web и браузер делят ресурсы одного runner. Эти характеристики не доказывают достаточную скорость конкретного suite: фактические длительность и потребление ресурсов пока не измерены. [GitHub: Hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).
- **Размещение PostgreSQL.** Service container работает рядом с job на том же runner; внешний хостинг БД для этого варианта не нужен. Официальный пример использует `pg_isready` как healthcheck перед работой с сервисом. [GitHub: PostgreSQL service](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers).
- **Стоимость — иллюстрация, не прогноз.** Стандартные runners для public-репозиториев бесплатны. GitHub Free включает для private-репозиториев 2 000 минут в месяц; Linux 2-core сверх квоты стоит $0.006/мин. Условные 100 прогонов по 5 минут — 500 минут: при доступной квоте без доплаты за минуты, а если все эти минуты сверх квоты — $3, без учёта storage. Доступная квота зависит также от остальных workflow; пять минут не являются замером этого проекта. [GitHub: Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions).
- **Постоянная dev-БД технически допустима.** E2E могут работать на ней при выделенных данных, отсутствии конфликтов и очистке только принадлежащих прогону записей. Disposable БД — рекомендация для воспроизводимости, а не требование Playwright. Даже один разработчик может запускать локальную проверку одновременно с CI; браузерная изоляция не разделяет серверные записи. Основание рекомендации — требования контролировать данные и изолировать состояние. [Playwright: Best Practices](https://playwright.dev/docs/best-practices), [Playwright: Parallelism](https://playwright.dev/docs/test-parallel).
- **Два разных объёма запуска.** Для API + PostgreSQL через `app.inject()` отдельный listening backend не нужен. Полный браузерный E2E требует доступного HTTP API; при изолированном прогоне в CI это отдельный процесс в job вместе с web. Это различие позволяет оценивать сложность двух наборов отдельно. [Fastify: Testing](https://fastify.dev/docs/latest/Guides/Testing/), [Playwright: Web server](https://playwright.dev/docs/test-webserver).

## Дополнение 2026-10-19: быстрый цикл проверок и финальный E2E

### Факты из первоисточников

- **Узкий запуск поддерживается инструментами.** Vitest 3 позволяет выбирать файл, имя теста (`-t`) и тест по строке. Watch mode повторно запускает связанные с изменением тесты через граф модулей. Это механизмы короткой обратной связи, а не обязанность запускать весь набор после правки. [Vitest 3: Filtering](https://v3.vitest.dev/guide/filtering), [Vitest: Features](https://vitest.dev/guide/features.html).
- **Монорепозиторий не требует полного pipeline.** Turbo поддерживает фильтры по пакету, зависимым пакетам и изменениям Git; можно выполнять только часть графа задач. Фильтрация пакета сама по себе не разделяет unit и E2E внутри одного package script. [Turborepo: Running tasks](https://turborepo.dev/docs/crafting-your-repository/running-tasks).
- **Браузерные проверки тоже можно сужать.** Playwright запускает отдельный файл, тест по имени (`-g`) или строке и предыдущие упавшие тесты (`--last-failed`). UI mode и Inspector помогают диагностировать конкретную проверку. Следовательно, работа над самим E2E не требует ожидать завершения всего тикета для каждого диагностического запуска. Последнее — применение возможностей инструмента, не его универсальная рекомендация о порядке разработки. [Playwright: Running and debugging](https://playwright.dev/docs/running-tests).
- **Retry не равен исправлению.** По умолчанию автоматические повторы Playwright выключены; прошедший после retry тест классифицируется как `flaky`, а не как прошедший с первого раза. Документация описывает поддержку retry, но не требует безусловно включать его. [Playwright: Retries](https://playwright.dev/docs/test-retries).
- **Основание для разделения циклов — стоимость обратной связи.** Mike Wacker описывает медленную локализацию ошибок через полную цепочку и предлагает узкие integration tests, когда они ловят тот же дефект. Из этого не следует универсальное правило «E2E только в конце тикета». [Google Testing Blog](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html?hl=uk_UA).

### Выбор для проекта по обсуждению

Пользователь выбрал финальный E2E как проверку завершённой задачи: реализация всего тикета закончена, соответствующие проверки нижних уровней зелёные, найденные дефекты исправлены. Во время обычных правок обратную связь дают адресные unit/integration checks. Полный pipeline после каждого редактирования и E2E для несвязанных изменений только документации, комментариев или опечаток в этот цикл не входят.

При падении финального прогона полезны разбор причины, исправление и повтор затронутой проверки, затем весь небольшой финальный smoke-набор на итоговом состоянии задачи. Это продолжение финального этапа. Возможность точечного запуска при написании E2E не отменяет выбранное пользователем ограничение: более ранний браузерный запуск требует его явного запроса. Бесконтрольные повторы «до зелёного» не считаются исправлением; это подход проекта, а не запрет Playwright на retries.

Связанные согласованные границы: три существующих mock-сценария переносятся на реальный локальный API без дублирования; миграции автоматически не применяются; данные прогона учитываются manifest, очистка адресная и допускает повторный запуск. Эти решения не устанавливают обязательность CI.

### Текущее ограничение scripts

Сейчас [web package.json](../../../apps/web/package.json) определяет `test` как `vitest run && playwright test`, а [корневой package.json](../../../package.json) — как `turbo run test`. Поэтому обычный корневой `pnpm test` уже включает браузерный набор и не является быстрым контуром. План разделения общих scripts предполагает отдельный явный запуск браузера и исключение его из default test; изменения scripts здесь не выполнялись.
