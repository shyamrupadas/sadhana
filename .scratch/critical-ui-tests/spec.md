# Критичные UI-тесты Sadhana

Status: ready-for-agent

## Исходный запрос

> $grill-with-docs Нужно завезти в репозиторий UI-тесты как в референсе ../shlokahub 1) Всю инфраструктуру тестов, настройки, правила, скиллы, MCP. 2) Написать несколько самых критичных для работы тестов по каждой из категории. Важный момент, он уже есть в референсе, но его нужно еще усилить здесь: тестов нужно писать мало. Не писать тесты на каждую фигню. Только на критичные вещи, которые в случае поломки могут сломать пользовательские пути. Поэтому не нужно писать тесты просто ради тестов. Только самый критичный функционал. Очень критично подходить к выбору, какой тест писать, а какой нет. И в случае сомоений - советоваться с человеком.

После обсуждения пользователь уточнил: категории референса служат для выбора уровня проверки, а не задают квоты тестов; браузерные тесты не запускаются в CI; в первый набор входят регистрация, полный цикл отметки привычки, ночной сон и один интеграционный тест отката неуспешной отметки. Реализацию этой спецификации пользователь пока не поручал.

## Постановка проблемы

Веб-приложение Sadhana пока не имеет автоматических UI-тестов. Поломка входа, регистрации, отметок привычек или записи сна может закрыть основной пользовательский путь или создать ложное впечатление, что данные сохранились. При этом большой набор мелких проверок повысит стоимость поддержки и затруднит поиск действительно важных регрессий.

## Решение

Добавить адаптированную из ShlokaHub инфраструктуру Vitest, React Testing Library и Playwright Test, правила отбора тестов и небольшой первый набор проверок. Проверять наблюдаемое поведение через действующие страницы и маршруты с точными подменами API. Новые тесты добавлять только тогда, когда без них остаётся существенный риск для основного пользовательского пути или достоверности сохранённых данных.

## Пользовательские истории

1. Как новый пользователь, я хочу зарегистрироваться и попасть на главную страницу, чтобы начать вести ежедневные записи.
2. Как зарегистрированный пользователь, я хочу войти в приложение, чтобы получить доступ к своим данным.
3. Как пользователь без действующей сессии, я хочу при открытии защищённой страницы попадать на страницу входа, чтобы личные данные оставались закрытыми.
4. Как вошедший пользователь, я хочу выйти из приложения, чтобы завершить доступ к своим данным на устройстве.
5. Как вышедший пользователь, я хочу, чтобы защищённая страница оставалась недоступной при повторном открытии, чтобы выход имел ожидаемый эффект.
6. Как пользователь, я хочу создать привычку, чтобы отслеживать её по дням.
7. Как пользователь, я хочу отметить привычку как выполненную, чтобы запись дня отражала мой ответ.
8. Как пользователь, я хочу отметить привычку как не выполненную, чтобы отличать отрицательный ответ от отсутствия ответа.
9. Как пользователь, я хочу вернуть привычку в состояние «не отмечена», чтобы исправить ошибочную отметку.
10. Как пользователь, я хочу после обновления страницы видеть сохранённые отметки привычек, чтобы доверять записи дня.
11. Как пользователь, я хочу, чтобы отклонённая сервером отметка не оставалась показанной как сохранённая, чтобы не полагаться на ложные данные.
12. Как пользователь, я хочу записать вечерний отбой и утренний подъём в одну запись дня, чтобы учесть ночной сон через полночь.
13. Как пользователь, я хочу после обновления страницы видеть сохранённые данные сна и длительность, чтобы продолжать учёт без потери информации.
14. Как разработчик, я хочу запускать быстрые UI-тесты отдельно от браузерных, чтобы быстро проверять локальные изменения.
15. Как разработчик, я хочу запускать критичные браузерные сценарии одной командой, чтобы передать проверку другому участнику без ручной настройки.
16. Как разработчик, я хочу получать явную ошибку на неожиданный API-запрос в тесте, чтобы фикстура не скрывала изменение поведения приложения.
17. Как разработчик, я хочу выбирать самый низкий достаточный уровень проверки, чтобы защищать поведение без лишнего дублирования.
18. Как разработчик, я хочу видеть правило отбора тестов и необходимость консультации при сомнениях, чтобы набор оставался небольшим.
19. Как сопровождающий CI, я хочу продолжать запускать существующие проверки API и контракта вместе с быстрыми UI-тестами, чтобы добавление браузерных тестов не убрало прежнюю защиту.
20. Как сопровождающий CI, я хочу оставлять Playwright вне обязательного запуска CI, чтобы сохранить согласованный порядок проверок из референса.

## Решения по реализации

- Считать ShlokaHub референсом для устройства тестовой инфраструктуры, документации и команд. Адаптировать его конфигурацию к React Router, пакетам и API Sadhana; не копировать тесты и фикстуры дословно.
- Добавить Vitest с окружением DOM, React Testing Library и Playwright Test с браузером Chromium. Разделить команды быстрых и браузерных тестов. Локальная общая команда запускает оба набора, как в референсе.
- Добавить минимальные общие средства для рендера страницы с нужными провайдерами и для точных подмен HTTP-запросов. Не вводить новые production-интерфейсы только ради тестов.
- Основной шов проверки — действующее приложение через маршрутизатор в браузере. Единственный дополнительный шов первого набора — страница ежедневных записей с её провайдерами и подменённым API для проверки ошибки сохранения.
- Браузерные тесты подменяют API и не подключаются к локальной или удалённой базе. Неожиданный запрос должен давать диагностичный отказ.
- Перенести в правила Sadhana классификацию уровней, команды, размещение тестов и проектный навык написания тестов из референса, усилив критерий ценности теста: защищать лишь критичный путь или достоверность пользовательских данных; при сомнении обсуждать сценарий с человеком до добавления теста.
- Не создавать тесты «по несколько на категорию». Категории определяют подходящий уровень; отсутствие теста на уровне допустимо, если отдельного критичного риска на нём нет.
- Сохранить существующую конфигурацию Playwright MCP: она уже соответствует тестовой части референса. Playwright MCP не заменяет пакет и runner Playwright Test. Для ручного прохода через браузер использовать `chrome-devtools` MCP согласно инструкции проекта, кроме случаев, когда применяемый навык требует Playwright.
- CI продолжает проверять API, контракт, lint, типы и сборку; добавить быстрые UI-тесты, но не запускать в CI Playwright. Так как локальная общая команда включает браузерные тесты, CI должен вызывать нужные быстрые проверки явно.
- Не менять продуктовые маршруты, схему данных, HTTP-контракт, серверные обработчики и сгенерированные артефакты ради этой инфраструктуры.

## Решения по проверке

- Хороший тест проверяет видимое пользователю поведение или публичный контракт: доступ к странице, состояние отметки, сохранённые данные, реакцию на отказ. Он не проверяет внутреннее состояние React, число вызовов хуков, CSS-классы или снимок разметки сам по себе.
- Использовать самый низкий достаточный уровень. Не дублировать одно поведение на уровнях Vitest и Playwright без отдельного риска, который нижний уровень не видит.
- Первый браузерный набор содержит пять тестов: перенаправление гостя с защищённой страницы; регистрация с переходом на главную; вход, выход и повторная недоступность защищённой страницы; создание привычки и цикл «не отмечена → выполнено → не выполнено → не отмечена» с проверкой каждого сохранённого состояния после обновления страницы; вечерний отбой и утренний подъём через полночь с проверкой сохранённых данных сна и длительности после обновления страницы.
- Первый интеграционный тест проверяет откат отметки привычки после отказа API. Отдельный тест такого же механизма для сна пока не нужен.
- Для браузерных тестов использовать доступные пользователю элементы и точные подмены API; фикстура должна сохранять данные между запросами и обновлением страницы настолько, насколько требует сценарий. Не обращаться к настоящему backend или production Neon.
- Существующие тесты маршрутов API и пакета контракта остаются защитой серверного поведения и общего HTTP-контракта. Образцы для UI-уровней — тесты регистрации, входа и пользовательских путей ShlokaHub; для ошибки сохранения — его интеграционные RTL-тесты.
- При реализации запускать целевые тесты, затем предписанные проектом `pnpm lint`, `pnpm build` и `pnpm test`; сделать короткий ручной проход затронутых веб-сценариев через `pnpm dev:web`. Проверить, что CI сохраняет все прежние быстрые проверки и не вызывает Playwright.

## Вне области работы

- Реализация до отдельного поручения пользователя; эта спецификация только фиксирует решение.
- Тесты статистики сна, переименования и удаления привычек, дневного сна, PWA, визуальных деталей и вариантов валидации форм без отдельного подтверждения их критичности.
- Проверка каждого вспомогательного компонента или каждой ветки кода ради количества тестов либо процента покрытия.
- Полноценные тесты с настоящим backend, базой данных и развёрнутым окружением.
- Изменение production-кода для удобства тестирования, если существующие швы достаточны.
- Изменение существующих MCP-серверов без необходимости, а также копирование не относящегося к тестам MCP из референса.
- Создание тикетов, коммита или изменение git index в рамках этой спецификации.

## Дополнительные замечания

- Термины «привычка», «отметка привычки», «запись дня» и «данные сна» используются в смысле глоссария Sadhana.
- Текущие пользовательские пути проходят через регистрацию и вход, защищённую главную страницу, таблицу привычек и данных сна. В проекте уже есть тесты API и контракта; UI-тестов пока нет.
- В референсе браузерные тесты не входят в CI перед выкладкой, хотя локальная общая команда их запускает. В Sadhana нынешний CI вызывает общую команду, поэтому при реализации это место потребуется адаптировать без потери прежних проверок.
- Статус `ready-for-agent` означает, что спецификация достаточно определённая для последующей декомпозиции; пользователь прямо отложил реализацию.
