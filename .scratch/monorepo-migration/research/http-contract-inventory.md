# Инвентаризация фактического HTTP-контракта

Исследование для решения «Фактический HTTP-контракт и расхождения с YAML». Источники: маршруты и сервисы `../sadhana-backend`, OpenAPI YAML в обоих репозиториях и вызовы текущего web-клиента. Это статический разбор исходников, без запросов к работающему серверу и без изменения API. Ссылки ниже имеют вид `файл:строка`.

## Границы и общие правила

В обоих репозиториях YAML для `main.yaml`, четырёх `endpoints/*.yaml` и `shared/responses.yaml` побайтово совпадает (`diff -qr`); из файлов деревьев `schema` отличаются только сгенерированные `generated.ts`. Поэтому ссылки на YAML backend ниже относятся и к зеркальному файлу `src/shared/api/schema/...` web-репозитория. Все 14 путей перечислены в `../sadhana-backend/src/schema/main.yaml:14-62`; реализация автозагружается из `../sadhana-backend/src/app.ts:26-32`. Короткие пути в таблице имеют корень `../sadhana-backend/src/`: `auth/index.ts`, `habits/index.ts`, `sleep-records/index.ts`, `sleep-stats/index.ts` лежат в `routes/`, остальные — в указанных `services/` или `utils/`.

Защищённые операции используют `preHandler: authenticate`: он проверяет access JWT, требует `type: 'access'` и получает `userId` из токена; неудача даёт `401 {message:'Invalid or expired token',code:'UNAUTHORIZED'}` (`../sadhana-backend/src/middleware/auth.ts:5-20`; определения ошибки — `../sadhana-backend/src/utils/errors.ts:22-25`). Web отправляет `Authorization: Bearer ...` в защищённых вызовах, всегда включает credentials, а auth-запросы отправляет через отдельный публичный клиент (`src/shared/api/instance.ts:7-25,27-55`). `POST /auth/refresh` использует только cookie, без bearer (`../sadhana-backend/src/routes/auth/index.ts:123-164`; `src/shared/model/session.ts:45-47`). CORS разрешает credentials и перечисленные origins (`../sadhana-backend/src/plugins/cors.ts:4-28`).

У четырёх групп маршрутов свой обработчик ошибок: `AppError` превращается в `{message,code}` со статусом ошибки, прочие исключения — в `500 {message:'Internal Server Error',code:'INTERNAL_ERROR'}` (`../sadhana-backend/src/routes/auth/index.ts:25-35`, `habits/index.ts:10-20`, `sleep-records/index.ts:10-27`, `sleep-stats/index.ts:10-20`). Ошибки проверки Fastify/Ajv не являются `AppError`, поэтому по тексту обработчика попадают в ветку 500. Это воспроизведено локально через `inject` на той же установленной версии Fastify с эквивалентным `setErrorHandler` и отсутствующим обязательным полем: ответ `500 {"message":"Internal Server Error","code":"INTERNAL_ERROR"}`. Полный backend при этом не запускался. YAML перечисляет лишь часть возможных ошибок (`../sadhana-backend/src/schema/shared/responses.yaml:1-32`).

Типы тел в таблице: `AuthResponse` = обязательные `accessToken:string`, `user:{id:string,email:string}` (`../sadhana-backend/src/services/auth.service.ts:30-39,65-73,104-109`); `HabitDefinition` = обязательные `key,label,createdAt` (`../sadhana-backend/src/routes/habits/index.ts:29-40`); `DailyEntry` = обязательные `id,date,sleep,habits`, где `sleep` содержит обязательные, но nullable `bedtime,wakeTime,napDuration,duration`, а элементы `habits` имеют `key:string,value:boolean` (`../sadhana-backend/src/routes/sleep-records/index.ts:36-73`; YAML `../sadhana-backend/src/schema/endpoints/sleep-records.yaml:1-77`). Дата в пути и `id/date` ответа задаются шаблоном `YYYY-MM-DD`, отметки времени — `YYYY-MM-DD HH:mm`; это шаблоны, не проверка календарной корректности (`../sadhana-backend/src/routes/sleep-records/index.ts:42-56,92-98`).

## Расхождения и указания для TypeSpec

1. **Обязательность полей `SleepDataInput`.** YAML требует `bedtime`, `wakeTime`, `napDuration` (`../sadhana-backend/src/schema/endpoints/sleep-records.yaml:27-45`); маршрут требует лишь `napDuration`, а сервис явно переводит отсутствие двух времён в `null` (`../sadhana-backend/src/routes/sleep-records/index.ts:180-194`; `services/sleep-records.service.ts:260-265`). При правиле сохранения поведения TypeSpec должен сделать `bedtime?` и `wakeTime?` с nullable-значениями, а `napDuration` оставить обязательным nullable integer ≥ 0. Web сейчас посылает все три поля (`src/features/main/main.page.tsx:143-149,185-191,262-268`), поэтому клиент не выявляет расхождение.
2. **Список записей ограничен пятью днями.** YAML называет операцию «Get all sleep records» и не описывает предел (`../sadhana-backend/src/schema/endpoints/sleep-records.yaml:95-109`). SQL выбирает только диапазон `today-4 … today` в Москве (`../sadhana-backend/src/services/sleep-records.service.ts:25-36`); отдельный запрос для статистики выбирает всю историю (`services/sleep-records.service.ts:82-89`). TypeSpec должен описать предел в документации операции, если маршрут остаётся прежним.
3. **Семантика `checkYesterday` уже, чем её описание.** YAML обещает проверку наличия вчерашних данных сна (`../sadhana-backend/src/schema/endpoints/sleep-records.yaml:227-237`), реализация требует именно пару «позавчерашний bedtime + вчерашний wakeTime» (`../sadhana-backend/src/services/sleep-records.service.ts:524-555`). В TypeSpec указать эту точную семантику.
4. **Auth cookie не описана как выход.** Три auth-маршрута выставляют/ротируют `refreshToken` (`../sadhana-backend/src/routes/auth/index.ts:74,117,157-164`), YAML указывает только входной cookie параметр у refresh (`../sadhana-backend/src/schema/endpoints/auth.yaml:87-102`). TypeSpec должен задать входной cookie и `Set-Cookie` в успешных ответах всех трёх операций, с реальными атрибутами; bearer для этих операций не требовать.
5. **Побочные эффекты операций привычек в YAML не раскрыты.** `POST /habits` идемпотентен по производному ключу и при совпадении возвращает прежнее определение с `201` (`../sadhana-backend/src/services/habits.service.ts:35-47`); `PATCH /sleep-records/{date}/habits/{habitKey}` допускает отсутствующий ключ и создаёт запись дня (`services/sleep-records.service.ts:329-362,386-393`); `DELETE` при существующем дне и отсутствующем ключе успешен (`services/sleep-records.service.ts:437-448`). TypeSpec должен отражать эти условия в описании операций и фактические статусы.
6. **Статусы ошибок задокументированы выборочно.** YAML для `PATCH` дневной привычки перечисляет 400/401/404 (`../sadhana-backend/src/schema/endpoints/sleep-records.yaml:185-197`), но 404 сервис не создаёт (`../sadhana-backend/src/services/sleep-records.service.ts:329-362`); у всех групп возможен 500 из общего обработчика, не перечисленный в YAML (`../sadhana-backend/src/routes/sleep-records/index.ts:10-27` и аналогичные обработчики выше). Для TypeSpec зафиксировать подтверждённые ветки AppError и общую ошибку 500, а статус ошибок валидации проверить отдельно до фиксации контракта.
7. **Обработка полей сна имеет дополнительную семантику.** `napDuration=0` сохраняется как `null`; `duration` вычисляется из `bedtime` предыдущего дня и `wakeTime` текущего, а отсутствие любого времени даёт `null` (`../sadhana-backend/src/services/sleep-records.service.ts:20-23,40-73,242-265`; `../sadhana-backend/src/utils/datetime.ts:37-66`). YAML показывает лишь типы и минимум ноль (`../sadhana-backend/src/schema/endpoints/sleep-records.yaml:1-45`). TypeSpec может документировать нормализацию и происхождение вычисляемого поля, сохранив JSON-форму.

## Неоднозначности для решения владельца

Это вопросы о будущем контракте; текущая реализация выше установлена по исходникам. Их следует вынести в отдельные билеты, если выбор нельзя сделать правилом «сохранять фактическое поведение».

- **Ошибки валидации:** считать ли фактическую ветку `500` для невалидных тел/путей частью сохраняемого контракта или разрешить исправление на `400` при переносе? Локальная проверка Fastify с эквивалентным обработчиком подтверждает `500`, но полный backend без доступа к базе не запускался (`../sadhana-backend/src/routes/sleep-records/index.ts:10-27,173-194`; аналогичные error handlers). По уже принятому правилу сохранения поведения TypeSpec не должен обещать `400` как фактический ответ до отдельного исправления API.
- **Неизвестный `habitKey` у PATCH дневной записи:** зафиксировать разрешённые произвольные ключи либо предусмотреть будущую проверку существования привычки/404? Сервис сейчас не вызывает `HabitsService`, просто добавляет ключ (`../sadhana-backend/src/services/sleep-records.service.ts:329-362`).
- **`GET /sleep-records` и название `getAll`:** пять дней — намеренная граница публичного ресурса или временная оптимизация под главный экран? Контракт без query-параметров не позволяет запросить историю, тогда как статистика читает её целиком (`../sadhana-backend/src/services/sleep-records.service.ts:25-36,82-89`; YAML `../sadhana-backend/src/schema/endpoints/sleep-records.yaml:95-109`).
- **Двойное использование `id` и `date`:** сохранять публичное `id=date` в `DailyEntry`, хотя в таблице `id` хранится `${userId}-${date}`? Все ответы сервиса подставляют `row.date` в оба поля (`../sadhana-backend/src/services/sleep-records.service.ts:65-73,176-184,303-311`), а БД имеет отдельный `id` (`services/sleep-records.service.ts:272-279`). Правило сохранения поведения отвечает «да» для текущей миграции; изменение потребовало бы отдельного решения.
- **Параметры времени и даты:** достаточно ли формата regex без календарной и зональной проверки для публичного контракта? Маршрут проверяет только шаблон (`../sadhana-backend/src/routes/sleep-records/index.ts:173-193`), расчёт использует `dayjs` (`../sadhana-backend/src/utils/datetime.ts:37-66`). При сохранении поведения не следует обещать строгую проверку действительных дат.

## Метод и ограничения

Сверены все определения путей в `main.yaml` с четырьмя файлами маршрутов, сервисами, общими middleware, обоими деревьями YAML и вызовами в `src/`. `diff -qr` показал равенство YAML. Минимальная проверка Fastify через `inject` подтвердила преобразование ошибки валидации в 500 при таком обработчике. Проверка не запускала полный backend и не доказывает, что развёрнутая версия совпадает с текущим исходным деревом.
