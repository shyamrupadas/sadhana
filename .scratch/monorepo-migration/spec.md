# Монорепозиторий Sadhana с общим API-контрактом

Status: awaiting-human-review
Accepted: 2026-10-06

## Problem Statement

Фронтенд Sadhana и его Fastify API живут в разных репозиториях, используют разные пакетные менеджеры и хранят отдельные копии OpenAPI. Одинаковые YAML уже расходятся с фактическим HTTP-поведением, а сгенерированные TypeScript-файлы двух сторон отличаются. Разработчику приходится согласовывать изменения API вручную, а при переносе кода легко нарушить авторизацию, сценарии сна и привычек, сборку или независимый выпуск приложений.

Рабочая база Neon уже содержит пользовательские данные и результаты шести исторических SQL-миграций. Нынешний мигратор не ведёт журнал и повторно исполняет все SQL-файлы, поэтому его нельзя просто включить в автоматический выпуск Railway. Нужен переход к одному репозиторию и контракту с проверяемым порядком переключения без потери данных, прежних адресов и возможности условного отката.

## Solution

Разместить web, API и общий контракт в одном pnpm workspace. TypeSpec становится единственным редактируемым источником публичного HTTP-контракта; из него детерминированно получаются OpenAPI и типизированные артефакты для React и Fastify. Новый web использует именованный `ApiClient`, а Fastify реализует единый `ApiHandlers`, сохраняя действующие маршруты, runtime-валидацию, cookie и пользовательское поведение.

Web по-прежнему выпускается GitHub Actions на существующий VPS, API — действующим сервисом Railway, база остаётся в Neon. Перед переключением новый мигратор проходит репетицию на временной ветке Neon; в production он однократно учитывает подтверждённые SQL 001–006 без их повторного выполнения. Сначала автоматически выпускается web и проверяется со старым API, затем после проверки готовности на монорепозиторий переключается Railway. Результат принимается по HTTP, в браузере и по состоянию БД.

## User Stories

1. Как пользователь, я хочу открывать Sadhana по прежнему адресу, чтобы миграция репозиториев не меняла привычный вход в приложение.
2. Как пользователь, я хочу видеть свои прежние записи дня, привычки и статистику, чтобы переход не терял мои данные.
3. Как пользователь, я хочу регистрироваться с прежним поведением формы и ошибок, чтобы новый web и API не меняли сценарий создания аккаунта.
4. Как пользователь, я хочу входить с прежними учётными данными, чтобы продолжить пользоваться приложением после выпуска.
5. Как пользователь, я хочу оставаться в сессии после обновления access token, чтобы истечение токена не прерывало работу.
6. Как пользователь, я хочу выходить из интерфейса прежним способом, чтобы завершать работу с текущего устройства.
7. Как пользователь, я хочу видеть свои привычки и добавлять новые, чтобы вести ежедневный учёт без изменения поведения.
8. Как пользователь, я хочу переименовывать и удалять привычки, чтобы управлять ими после перехода.
9. Как пользователь, я хочу видеть записи сна за доступные дни, чтобы прежние данные оставались доступны.
10. Как пользователь, я хочу сохранять время сна и дневной сон, чтобы расчёт длительности работал по прежним правилам.
11. Как пользователь, я хочу отмечать, менять и снимать отметку привычки в записи дня, чтобы её состояние сохранялось и обновлялось на экране.
12. Как пользователь, я хочу видеть проверку вчерашнего сна по прежним правилам московских дат, чтобы подсказка не изменила смысл.
13. Как пользователь, я хочу видеть статистику сна за неделю, месяц и год, чтобы данные и пустые состояния отображались как раньше.
14. Как пользователь, я хочу видеть загрузку, ошибки и откат оптимистичного изменения при сбое запроса, чтобы интерфейс не показывал несохранённые данные как успешные.
15. Как пользователь установленной PWA, я хочу получить обновлённую версию без битых ресурсов и потери навигации, чтобы пользоваться приложением после публикации.
16. Как разработчик web, я хочу получать типизированные методы API из общего контракта, чтобы не поддерживать собственную копию схемы.
17. Как разработчик API, я хочу реализовывать все публичные операции через общий типизированный интерфейс, чтобы пропуск или несовпадение операции обнаруживались до выпуска.
18. Как разработчик API, я хочу сохранить runtime-проверки запросов Fastify, чтобы типы TypeScript не ослабили проверку входящих HTTP-запросов.
19. Как разработчик, я хочу запускать оба приложения одной командой и каждое отдельно, чтобы работать с нужной частью системы.
20. Как разработчик, я хочу, чтобы изменение контракта пересобиралось в режиме разработки и подхватывалось обоими приложениями, чтобы не выполнять полную ручную сборку после каждой правки.
21. Как разработчик, я хочу собирать и проверять web и API независимо и вместе, чтобы изменение одного пакета не требовало ненужного выпуска другого.
22. Как ревьюер, я хочу видеть в CI устаревшие или новые незафиксированные generated-артефакты, чтобы исходник TypeSpec и используемый код не расходились.
23. Как ревьюер, я хочу видеть проверку реального HTTP-поведения, cookie и ошибок, чтобы компиляция типов не маскировала регрессию API.
24. Как оператор, я хочу применять миграции по журналу и контрольным суммам, чтобы повторный запуск не преобразовывал старые данные повторно.
25. Как оператор, я хочу, чтобы параллельные запуски мигратора не выполняли один SQL дважды, чтобы выпуск не повредил БД.
26. Как оператор, я хочу остановить выпуск при ошибке миграции до старта нового API, чтобы не принимать трафик неподготовленной версией.
27. Как оператор, я хочу проверить мигратор на временной изолированной ветке Neon, чтобы удостовериться в порядке учёта старых миграций до записи в рабочую базу.
28. Как оператор, я хочу выпускать web через прежний VPS и API через прежний Railway-сервис, чтобы сохранить адреса, переменные и доступы.
29. Как оператор, я хочу, чтобы локальные изменения web и API запускали только соответствующий выпуск, а изменение общего контракта — оба, чтобы независимые релизы оставались предсказуемыми.
30. Как оператор, я хочу получить зелёный CI и проверенный Docker-образ до переключения Railway, чтобы настройка нового Git-источника опиралась на проверенную сборку.
31. Как владелец, я хочу увидеть новый web в работе со старым API до переключения Railway, чтобы проверять переход по одному действующему компоненту за раз.
32. Как владелец, я хочу иметь отдельный контрольный рубеж перед изменением production-настроек Railway, чтобы выполнить переключение только после проверки готовности.
33. Как владелец, я хочу сам проверить запись через свою учётную запись после переключения API, чтобы подтвердить сквозной сценарий без отдельного тестового пользователя в production.
34. Как оператор, я хочу знать точные условия возврата прежнего web или API, чтобы не откатить приложение поверх несовместимого состояния Neon.
35. Как сопровождающий проект, я хочу сохранить прежние границы фронтенд-модулей и пересмотреть ADR об API-контракте, чтобы новая структура оставалась понятной после миграции.

## Implementation Decisions

### Границы переноса и workspace

- Монорепозиторий содержит приватные пакеты `@sadhana/web`, `@sadhana/api` и `@sadhana/api-contract`; оба приложения прямо зависят от контракта через `workspace:*`. Web сохраняет существующие слои `app`, `features`, `shared`, Fastify — текущие сервисы, маршруты и SQL. Нового верхнеуровневого слоя фронтенда нет.
- При реализации записать актуальный SHA локального backend-репозитория и перенести отслеживаемые исходники этого коммита без Git-истории, локальных секретов и артефактов сборки. Исторические SQL 001–006 не редактировать. Старые отдельные lockfile исключаются из итогового workspace.
- Закрепить Node 24 и точную версию pnpm через `packageManager`; установка в CI идёт из корня по одному lockfile с `--frozen-lockfile`. Общие `build`, `lint`, `typecheck`, `test` выполняются через Turbo. Отдельные команды доступны для сборки и разработки web и API; root `dev` запускает оба приложения. Сборка, тесты и typecheck приложения сначала строят его workspace-зависимости. На чистой установке контракт собирается до watcher-ов, а последующие изменения подхватываются без ручной полной сборки.
- Root `test` охватывает быстрые тесты пакетов; браузерные E2E не входят в него. Существующие версии прикладных зависимостей сохраняются, пока перенос не требует совместимого обновления. Из референса не переносится глобальный `injectWorkspacePackages`: API упаковывается отдельно для production-образа.

### Контракт и потребители

- Единственный редактируемый источник контракта — TypeSpec. Он описывает фактические 14 операций Sadhana без нового префикса путей. OpenAPI 3.0 и типы/клиент/интерфейс обработчиков являются производными, коммитимыми артефактами. Старые независимые YAML и сгенерированные типы удалить после сравнения покрытия и успешной проверки обоих приложений; пересмотреть прежний ADR, который называл YAML источником типов.
- Генерация последовательно компилирует TypeSpec и строит `paths`, `components`, `operations`, именованный `ApiClient`, `ApiClientError` и единый `ApiHandlers`. Для типов OpenAPI используется `openapi-typescript`; проектный генератор добавляет методы и обработчики поверх этих типов, не повторяя упрощённый преобразователь схем референса. Неподдержанная конструкция останавливает генерацию, а не превращается в `any` или неверный примитив. Публичные экспорты пакета явные.
- Контракт сохраняет обязательные и nullable поля, параметры path/query/cookie, все фактические успешные статусы, пустой `204`, тела ошибок и `Set-Cookie` успешных auth-ответов. Описания отражают предел пяти московских дней у списка записей, проверку пары «отбой позавчера — подъём вчера», нормализацию нулевого дневного сна и другие подтверждённые условия. Неверные запросы сейчас могут стать `500` из-за существующего обработчика ошибок Fastify; исправление на `400` не входит в перенос.
- Web использует сгенерированный `ApiClient`: успех возвращает типизированное тело, `204` — `undefined`, HTTP-ошибка выбрасывает `ApiClientError` со статусом и телом. Пустой или не-JSON ответ не должен скрывать исходный HTTP-статус ошибкой разбора. `AbortSignal` и сетевая ошибка сохраняют отдельную семантику. Транспорт клиента настраиваемый и не содержит прикладной сессии в generated-коде.
- В общем API-слое web остаются публичный и защищённый транспорт либо эквивалентное разделение. Оба отправляют `credentials: include`; защищённый транспорт асинхронно обновляет access token через существующую модель сессии, добавляет bearer и сохраняет исходы 401/503. Параллельные запросы разделяют один refresh. HttpOnly cookie обрабатывается браузером и не читается клиентским JavaScript.
- Сценарные React Query hooks остаются внутри соответствующих фич. Их перевод на `ApiClient` сохраняет видимые состояния, ошибки, отмену, повторные запросы, оптимистичное обновление и откат; прежние ключи кэша без параметров остаются стабильными, включая ключ списка записей сна. Общий клиент не импортирует фичи или app; внешние импорты фич используют их публичные точки входа. После проверки удалить прежние клиентские библиотеки fetch/React Query OpenAPI; типизированные MSW-моки можно сохранить.
- API реализует все 14 операций через один `ApiHandlers` с явными вариантами `{status, body}` и нужными заголовками. Прикладной контекст передаёт уже проверенного пользователя и сведения для cookie без зависимости интерфейса от Fastify. Тонкие Fastify-адаптеры сохраняют методы, пути, inline JSON Schema, authentication pre-handler, CORS, cookie и прежние обработчики ошибок. Типизированный контракт не заменяет runtime-проверку. Refresh token не попадает в JSON-ответ.

### База данных и выпуск

- Постоянный мигратор использует журнал `schema_migrations`, упорядоченные уникальные идентификаторы, SHA-256 точных байтов SQL, session-level advisory lock через прямое соединение Neon и отдельную транзакцию для каждого нового SQL вместе с записью в журнал. Повторный запуск пропускает совпадающие записи; неизвестная версия, пропуск или изменение применённого файла дают ошибку. Ошибка запуска завершает процесс ненулевым кодом. Время ожидания и выполнения ограничено.
- Production уже соответствует SQL 001–006 по проведённой инвентаризации. Перед автозапуском мигратора повторно сверить отсутствие промежуточного изменения схемы/формата данных, затем однократно добавить записи о подтверждённых 001–006 без выполнения их SQL, отметив ретроспективный учёт без выдуманной даты первоначального исполнения. Сначала выполнить эту процедуру и два повторных запуска на временной ветке Neon, полученной от production; на пустой локальной PostgreSQL проверить обычное применение SQL. После подтверждения выполнить начальное заполнение журнала в той же production-ветке, куда подключён Railway.
- API собирается многоэтапным Dockerfile из корня workspace на Node 24 и закреплённом pnpm. Для изолированной упаковки production-зависимостей используется `pnpm deploy --prod --legacy` без глобального `injectWorkspacePackages`; точную закреплённую версию и состав образа проверить в CI. В production-образ упакован только API с необходимым контрактом, runtime-зависимостями и SQL, без web и инструментов сборки; сборка не исполняет миграции. Railway запускает собранный API, а собранный мигратор — отдельной Pre-Deploy Command перед активацией версии. Ошибка Pre-Deploy останавливает выпуск. Отдельный direct Neon URL нужен только мигратору; существующий pooled `DATABASE_URL` приложения сохраняется.
- Из `master` web выпускается прежним GitHub Actions → SSH → VPS с `rsync --delete` артефакта web в прежний каталог. Production-конфигурация Vite переносится вместе с web-пакетом; встроенный API URL, домен, SSH host key и существующие секреты сохраняются. Workflow использует root pnpm workspace, проверяет артефакты контракта и web до копирования, затем выполняет HTTP smoke check. Ошибка до копирования не меняет VPS; после начала копирования требуется повторный выпуск исправленного или известного рабочего коммита.
- Действующий Railway project/environment/service сохраняет домены, порт 8080, переменные, регион и одну реплику. Источник Git переключается на монорепозиторий `master` с корнем workspace, корневым Dockerfile, healthcheck `/`, Wait for CI, Pre-Deploy Command и watch paths всех реальных входов сборки API. GitHub Actions CI запускается на PR и каждом push в `master`, напрямую регенерирует контракт и отклоняет изменённые **и новые** generated-артефакты, затем выполняет lint/typecheck/build/test и проверку Docker-образа. Пропущенный workflow с path-фильтром не является единственным обязательным CI-gate. Сбой web workflow на общем коммите может задержать Railway через Wait for CI; это принятое ограничение.
- Триггер web охватывает web, контракт, общие входы сборки и workflow; Railway watch paths охватывают API, контракт, Docker и общие входы сборки. Изменение одного приложения не выпускает другое, изменение контракта или общих входов запускает оба, одни документы не запускают выпуск. При реализации перечни сверяются с фактическими скриптами и конфигурациями.
- Первый общий коммит автоматически выпускает новый web при старом API. После проверки этой переходной пары и отдельного ручного рубежа готовности выполняются начальное заполнение журнала production и перепривязка действующего Railway-сервиса. Для уже опубликованного коммита явно запускается `Deploy Latest Commit` и сверяется SHA; далее работает Git autodeploy. В этом структурном выпуске нет новой предметной SQL-миграции. Успех подтверждается проверкой web, API, cookie/PWA и состояния Neon; запись через собственную учётную запись проверяет владелец.
- До переключения API web можно восстановить по прежнему рабочему выпуску. После переключения web откатывается только на версию, проверенную с новым API, без побочного отката общего контракта или API; иначе выпускается исправление вперёд. Railway позволяет выбрать прежний API deployment, но его совместимость с текущими схемой и JSON-данными Neon проверяется до отката. Откат образа не откатывает PostgreSQL; при несовместимости нужен forward fix либо отдельный контролируемый план восстановления.

## Testing Decisions

- Владелец подтвердил 2026-10-02 объём проверок: автоматические тесты HTTP-поведения API и мигратора, ручной браузерный проход для web/PWA перед приёмкой. Автоматические браузерные E2E в эту миграцию не входят.
- Хороший тест наблюдает публичный результат: HTTP-статус, тело, заголовки/cookie, изменение и чтение данных, состояние UI. Не закреплять тестами расположение внутренних адаптеров, вызов конкретного сервиса или текст generated-кода. Компиляция `ApiHandlers` и чистый результат генерации служат отдельными статическими воротами.
- Основной автоматический шов API — запрос к собранному Fastify-приложению через его HTTP-интерфейс с изолированной PostgreSQL. Уже есть тесты маршрутов через Fastify `inject`; расширить этот подход для auth, всех 14 операций, runtime JSON Schema и сопоставления с TypeSpec/OpenAPI. Особо проверить optional/nullable сон, `204`, все три `Set-Cookie`, отсутствие refresh token в JSON, авторизацию, ошибки и подтверждённые расхождения старого YAML. Мигратор проверять через PostgreSQL-эффекты и журнал: чистая база, ретроспективный учёт, повтор, контрольные суммы, ошибка и конкурентный запуск.
- Генератор и `ApiClient` проверить по публичному API на схемах/ответах, которые реально использует Sadhana: nullable и необязательные поля, несколько статусов, path/query/cookie, JSON и не-JSON, пустое тело, отмена и сетевой сбой. Проверить, что неизвестная генератору конструкция останавливает процесс. Эти тесты защищают контрактный шов, а не снимок текста generated-файлов.
- Web проверить через сценарии login/register/refresh, защищённого запроса после истечения access token, 401/503, записи сна и привычек с оптимистичным откатом и статистики. Автоматический браузерный E2E-стек не является обязательной частью root `test`; перед приёмкой выполнить короткий браузерный проход нового web со старым API и затем с новым API, включая установленную PWA, service worker, manifest и обновление ресурсов. Для production-записи используется учётная запись владельца без отдельного тестового пользователя.
- В CI выполнить чистую установку, детерминированную генерацию с проверкой новых и изменённых файлов, lint/typecheck/build/test, Docker build и запуск healthcheck образа. Проверить `dev` после чистой установки и обновление контракта без ручной полной сборки. Перед production повторить мигратор на временной Neon-ветке; после Railway Pre-Deploy проверить шесть строк журнала и отсутствие повторного исполнения исторического SQL.
- После выпуска проверить оба прежних адреса, фактически встроенный API URL web, лог и SHA обоих выпусков, healthcheck Railway, auth/cookie, пользовательские экраны и агрегаты БД. При провале любого gate дальнейшее переключение останавливается; условия отката определены выше.

## Out of Scope

- Перенос Git-истории backend и архивирование прежнего backend-репозитория: архивированием владелец займётся отдельно.
- Переписывание API на Nest, смена хостинга, Neon, доменов или секретов, изменение предметной логики и намеренное исправление существующих ошибок API, включая статус валидации.
- Новые предметные SQL-миграции в выпуске структурного переноса и полноценная гарантия безостановочной совместимости каждой будущей миграции со старым API.
- Отдельная ветка релизов, новый постоянный тестовый сервис, новый production-аккаунт для smoke check, версионные каталоги web на VPS и механизм мгновенного переключения симлинка.

- Источник решений — [карта миграции](map.md) и её именные тикеты. Подробные отклонения старого OpenAPI от реализации собраны в [инвентаризации HTTP-контракта](research/http-contract-inventory.md); фактическое состояние Railway и Neon зафиксировано в соответствующих решениях карты. - Репетиционная ветка Neon изолирована от production и не является автоматическим способом вернуть пользовательские записи после переключения. Секреты и строки подключения не размещаются в спецификации или Git.
