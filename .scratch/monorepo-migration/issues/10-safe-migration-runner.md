# 10: Безопасный мигратор с журналом

**What to build:** Оператор может применять SQL-миграции один раз, обнаруживать изменение уже применённого файла и безопасно повторять или параллельно запускать мигратор без повторного преобразования пользовательских данных.

**Blocked by:** 02 — API в общем workspace

**Status:** awaiting-human-review
Accepted: 2026-10-04

- [x] Мигратор ведёт `schema_migrations` с уникальным упорядоченным идентификатором и SHA-256 точных байтов SQL; исторические файлы 001–006 не изменены.
- [x] Отдельное прямое PostgreSQL-соединение держит session-level advisory lock; каждая новая миграция и её запись в журнал применяются одной транзакцией с ограниченными таймаутами.
- [x] Повторный запуск пропускает совпадающие файлы; изменённая сумма, неизвестная версия, пропуск в последовательности и ошибка SQL завершают процесс ненулевым кодом.
- [x] Предусмотрена отдельная однократная операция ретроспективного учёта только подтверждённых 001–006 без исполнения их SQL и без выдуманной даты первого применения.
- [x] Интеграционные проверки на изолированной PostgreSQL покрывают пустую базу, ретроспективный учёт, повтор, конкурентный запуск и ошибку; пользовательские таблицы не меняются при повторе.

## Comments

- Операция `migrate:baseline` требует явного подтверждения проверки текущей схемы и данных сна. Проверки структуры и ключей 006 выполняются в коде, а результат переноса данных 005 сверяется оператором с инвентаризацией перед запуском. Тесты использовали временную локальную PostgreSQL; production Neon не изменялась.
