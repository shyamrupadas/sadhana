# Монорепозиторий Sadhana с общим API-контрактом

Label: wayfinder:map

## Destination

Согласованная подробная спецификация перехода `sadhana` и `sadhana-backend` в одну монорепу: структура workspace, единый API-контракт и его генерация, локальная разработка, проверки, независимый выпуск фронтенда и бэкенда через прежних поставщиков и безопасный порядок переключения. По этой спецификации можно выпустить реализационные тикеты без открытых архитектурных вопросов.

## Notes

- Wayfinder здесь планирует миграцию; перенос кода и переключение production выполняются в отдельных сессиях после спецификации и применения соответствующих навыков.
- Референс: `../shlokahub` (`apps/web`, `apps/api`, `packages/api-contract`, pnpm workspaces, Turborepo). Согласован переход с Yarn/npm на pnpm. Выбран TypeSpec как единый источник: TypeSpec → OpenAPI → типизированные артефакты для обеих сторон. Подключение контракта к React и Fastify проектировать по образцу референса настолько близко, насколько это подходит существующему стеку. Если решение референса здесь неудачно или есть обоснованно лучший вариант, предупредить владельца и объяснить отличие. Переход на Nest не является требованием.
- Историю коммитов `sadhana-backend` в монорепу не переносить. При реализации проверить актуальный локальный коммит и взять его отслеживаемые исходники. Архивированием прежнего репозитория владелец займётся отдельно.
- Текущее состояние: фронтенд использует Yarn 4 и `openapi-fetch`/`openapi-react-query`; бэкенд использует npm и Fastify. YAML-файлы OpenAPI двух репозиториев совпадают, сгенерированные TypeScript-файлы отличаются. Существующий [ADR о контракте](../../docs/adr/0002-openapi-api-contract.md) закрепляет OpenAPI в фронтенде как источник типов и должен быть пересмотрен при переходе на TypeSpec. Fastify держит runtime JSON Schema прямо в маршрутах: типизация контрактом не заменяет их проверки.
- В `shlokahub` ADR требует CI-проверку актуальности generated-кода, но в просмотренных workflow вызова `contract:generate` с проверкой чистого diff нет; спецификация должна задать эту проверку явно.
- Фронтенд выпускается workflow `.github/workflows/deploy.yml` из `master`: GitHub Actions собирает Vite и копирует `dist/` по SSH на прежний VPS. Бэкенд автоматически выпускается Railway из Git; [фактические настройки сервиса сверены](decisions/09-railway-service-inventory.md). Референс раньше использовал Railway Pre-Deploy для миграций, но теперь выпускает API через Amvera; нынешний entrypoint не копировать как настройку Railway. PostgreSQL размещён в Neon.
- Сохранить поставщиков, действующие учётные данные, адреса, существующее поведение API и пользовательские сценарии. Не переносить секреты в Git; команды и рабочие каталоги должны учитывать новые пути. Существующие SQL-миграции бэкенда не редактировать. Текущий `migrate.ts` выполняет все SQL-файлы без журнала применённых версий. Изучить мигратор референса (журнал и контрольные суммы, блокировка PostgreSQL, транзакционное применение, запуск до API), при необходимости доработать мигратор Sadhana и отдельно спроектировать учёт уже выполненных миграций перед автоматизацией на Railway. Предупреждать о неподходящих решениях референса и аргументировать улучшения.
- Для решения вопросов сверяться с `../shlokahub`, `../sadhana-backend`, `docs/architecture/frontend.md`, `.agents/skills/frontend-architecture/SKILL.md`, `CONTEXT.md`, `/grilling` и `/domain-modeling`. Решения записывать в соответствующих тикетах; эта карта остаётся указателем.

## Decisions so far

- [Роль прежнего backend-репозитория после переноса](decisions/01-migration-boundaries-and-history.md): переносить исходники актуального локального коммита без Git-истории; архивирование оставлено владельцу вне миграции.
- [Структура pnpm workspace и команды сборки](decisions/02-pnpm-workspace-and-builds.md): три пакета в общем pnpm workspace, независимые и общие команды Turbo с предварительной сборкой контракта; `dev` запускает оба приложения, быстрые тесты отделены от E2E, Node 24 закреплён.
- [Перенос публичного API-контракта в TypeSpec](decisions/03-contract-source.md): фактическое HTTP-поведение описать в TypeSpec; генерировать OpenAPI, типы и `ApiClient` по схеме референса с доработанным генератором и обязательной проверкой артефактов в CI.
- [Независимый выпуск приложений прежними поставщиками](decisions/04-independent-releases.md): раздельные триггеры из `master`, web через прежний `rsync --delete`, API через корневой Dockerfile и Railway Wait for CI; откат по прежнему коммиту и deployment.
- [Фактический HTTP-контракт и расхождения с YAML](decisions/08-http-contract-inventory.md): инвентаризированы 14 операций; TypeSpec должен отразить выявленные расхождения YAML с действующим Fastify и web.
- [Мигратор Sadhana по образцу референса](decisions/06-database-migrations.md): журнал и блокировка по референсу, однократный учёт подтверждённых старых SQL, Railway Pre-Deploy и условный откат приложения.
- [Подключение общего контракта к React и Fastify](decisions/05-contract-consumers.md): web переходит на генерируемый `ApiClient` с исключениями, API реализует единый `ApiHandlers` через Fastify-адаптеры с сохранением runtime-проверок.
- [Сверка текущих настроек Railway перед переключением](decisions/09-railway-service-inventory.md): действующий сервис, переменные и адреса проверены; для монорепы нужно настроить Docker-сборку, фильтры путей, CI-gate, Pre-Deploy и healthcheck.
- [Сверка исторических миграций в production Neon](decisions/10-production-migration-inventory.md): состояние production-базы соответствует 001–006, включая признаки преобразования старых данных; проведённая сверка служит основанием для начального заполнения журнала.
- [Порядок переключения и критерии приёмки](decisions/07-cutover-and-acceptance.md): web выпускается первым и проверяется со старым API; после репетиции мигратора и ручной проверки готовности переключается Railway, затем проверяются API, PWA и Neon с условным откатом.

## Out of scope

- Перенос Git-истории бэкенда, переписывание бэкенда на Nest, изменение предметной логики, смена хостинга, базы данных, доменов или секретов ради структурного переноса.
- [Архивирование прежнего backend-репозитория](decisions/01-migration-boundaries-and-history.md): владелец выполнит его самостоятельно за пределами миграции; оно не является условием переключения.
- Полноценная совместимость последовательных версий API со схемой БД и безостановочный переход при несовместимых миграциях: отдельная будущая работа после текущей миграции монорепозитория.
