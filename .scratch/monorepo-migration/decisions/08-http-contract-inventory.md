# Фактический HTTP-контракт и расхождения с YAML

Type: research
Status: resolved
Blocked by: 03 — Перенос публичного API-контракта в TypeSpec

## Question

Какие методы, пути, параметры, обязательные и nullable-поля, статусы и тела ответов, правила авторизации и cookie фактически реализованы в 14 публичных операциях `sadhana-backend`, и где они расходятся с одинаковым YAML в двух репозиториях или с используемыми web-запросами? Зафиксировать для каждого расхождения доказательство из маршрутов, сервисов или тестов и указать, что должен описывать TypeSpec при уже выбранном правиле сохранения фактического поведения. Не менять API в рамках исследования; неоднозначности, требующие решения владельца, вынести в новые билеты.

## Answer

Полная инвентаризация 14 операций и доказательства по маршрутам, сервисам, YAML и web-вызовам записаны в [отчёте об HTTP-контракте](../research/http-contract-inventory.md). YAML обоих репозиториев совпадает, но неточно отражает обязательность полей `PUT /sleep-records/{date}`, предел пяти дней у списка, смысл проверки вчерашнего сна, выходной `Set-Cookie` у auth-ответов и несколько условий ошибок и побочных эффектов. Текущий Fastify-обработчик превращает ошибки валидации в 500; это подтверждено локальной проверкой установленной версии Fastify с эквивалентным обработчиком, без запуска полного backend.

TypeSpec должен описывать установленное фактическое поведение согласно решению [«Перенос публичного API-контракта в TypeSpec»](03-contract-source.md); менять семантику API в рамках переноса не требуется. Неоднозначности отчёта касаются возможных будущих изменений поведения и не создают новых развилок на пути к этой спецификации. При реализации проверить наиболее рискованные ответы интеграционными HTTP-проверками на собранном backend.
