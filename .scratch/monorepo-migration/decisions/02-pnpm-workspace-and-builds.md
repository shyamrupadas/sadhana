# Структура pnpm workspace и команды сборки

Type: grilling
Status: resolved
Blocked by: None

## Question

Как организовать `apps/web`, `apps/api` и `packages/api-contract`, единый pnpm lockfile, задачи Turborepo и локальные команды так, чтобы обе сборки и тесты запускались отдельно и совместно с правильным порядком зависимостей?

## Answer

- Структура: `apps/web` сохраняет существующий React/Vite-код и его внутренние слои; `apps/api` сохраняет Fastify-код и относительное расположение `src`, SQL-миграций и `dist`; `packages/api-contract` содержит общий источник и артефакты контракта. В корне — `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `turbo.json` и общие конфигурации. Старые `yarn.lock`, `.yarnrc.yml` и backend `package-lock.json` не входят в итоговый workspace. Установка выполняется из корня одним `pnpm install --frozen-lockfile` в CI.
- Приватные пакеты назвать `@sadhana/web`, `@sadhana/api`, `@sadhana/api-contract`. Оба приложения объявляют `@sadhana/api-contract: workspace:*` прямой зависимостью. Рабочие зависимости и инструменты остаются в пакетах, которые их используют; в корне — pnpm/Turbo и общие команды. `injectWorkspacePackages` из референса не копировать автоматически: необходимость изолированной упаковки API и способ установки на Railway относятся к решению «Независимый выпуск приложений прежними поставщиками».
- Закрепить Node 24 для разработки и CI (минимальную версию внутри линии 24 указать согласованно с выбранным pnpm; ориентир референса — 24.15+), точную версию pnpm зафиксировать в `packageManager`, поддерживаемой Corepack и средой выпуска. Перед переключением проверить сборку, тесты и запуск Fastify на этой версии Node. Не переносить версии TypeScript и прочих зависимостей референса без нужды: при миграции сначала сохранить совместимые версии каждого приложения.
- Корневые `build`, `lint`, `typecheck`, `test` запускают соответствующие задачи Turbo для всех пакетов. Дать явные команды/алиасы `build:web`, `build:api`, `test:api`, `dev:web`, `dev:api`; первые три выбирают нужный пакет через Turbo `--filter`, а `dev:web` и `dev:api` выбирают приложение **вместе с его workspace-зависимостями**, чтобы запустился и watcher контракта. Для `build`, `test` и `typecheck` задать `dependsOn: ["^build"]`, чтобы выбранное приложение сначала получало собранный контракт. `build` кэширует фактические выходы пакетов; `lint`, `typecheck` и `test` не объявляют файловых выходов. У каждого пакета собственные скрипты: web сохраняет проверки TypeScript и Vite-сборку, API — `tsc`, существующие `node:test`/`c8` и команду миграций. API получает отдельный `lint` по действующей ESLint-конфигурации. Не вызывать фильтрованный скрипт приложения напрямую там, где нужен граф предварительных сборок.
- `pnpm test` запускает имеющиеся быстрые тесты пакетов: сегодня это API; тесты контракта или web unit добавляются туда по мере появления. Браузерные E2E, если появятся, запускаются отдельной командой и не входят в корневой `test`. Тесты API не должны самостоятельно дублировать сборку, уже обеспеченную графом Turbo.
- `pnpm dev` запускает web и API вместе, `dev:web` и `dev:api` — по отдельности, во всех случаях после подготовки `api-contract` на чистой установке. Для `dev` задать `cache: false`, `persistent: true`, `dependsOn: ["^build"]`; watcher контракта запускать только после его собственной первой сборки, чтобы он не писал в `dist` одновременно с ней. Пакет контракта должен пересобирать свои runtime/type-артефакты при правке исходников, а Fastify — перезапускаться после пересборки своего кода. Проверить на чистом checkout и при изменении контракта, что оба приложения подхватывают новые артефакты без ручной полной сборки. Это намеренное отличие от `shlokahub`, где `dev` не ждёт сборки пакета контракта, хотя тот экспортирует `dist`.
- Генерация TypeSpec и проверка актуальности коммитимых артефактов остаются отдельной задачей `contract:generate`; точные файлы и CI-проверка определяются в билете «Перенос публичного API-контракта в TypeSpec». Правила выпуска и используемые фильтрованные команды CI определяются в билете «Независимый выпуск приложений прежними поставщиками».

Механика графа задач и локального запуска сверена с [документацией Turborepo](https://turborepo.dev/docs/crafting-your-repository/configuring-tasks) и [руководством по разработке](https://turborepo.dev/docs/crafting-your-repository/developing-applications).

## Comments

- Проверено 2026-09-30: фронтенд использует Yarn 4 (`start`, `build`, `lint`, `preview`, `api`), API — npm (`build:ts`, `dev`, `test`, `migrate`), а референс — pnpm workspaces и Turbo. Для обоих приложений в спецификации нужны отдельные команды и зависимость от сборки пакета контракта.
- У референса задача `dev` не зависит от подготовки `api-contract`, хотя пакет экспортирует файлы из `dist`. При переносе предусмотреть подготовку контракта после чистой установки и проверку повторной сборки при его изменении; не копировать эту настройку без проверки.
- Владелец подтвердил 2026-09-30 три рекомендации: корневой `dev` запускает оба приложения, корневой `test` ограничен быстрыми тестами пакетов, для workspace закрепляется Node 24.
