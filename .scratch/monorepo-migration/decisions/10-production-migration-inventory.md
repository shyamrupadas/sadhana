# Сверка исторических миграций в production Neon

Type: task
Status: resolved
Blocked by: 06 — Мигратор Sadhana по образцу референса; 09 — Сверка текущих настроек Railway перед переключением

## Question

Каково фактическое состояние production-базы Neon перед начальным заполнением журнала: какие из неизменённых SQL-миграций 001–006 можно подтвердить по схеме, данным и доступным свидетельствам прежних запусков, и есть ли расхождения, требующие отдельного решения до включения Railway Pre-Deploy?

## Answer

Проверено 2026-10-02 только чтением в транзакции `READ ONLY`. `DATABASE_URL` действующего сервиса `sadhana-backend` в Railway production указывает на Neon endpoint `ep-flat-darkness-ag44hig2-pooler.c-2.eu-central-1.aws.neon.tech`, базу `neondb`, пользователя `neondb_owner`. Локальное подключение с теми же endpoint, базой и пользователем успешно; секреты и строка подключения не сохранялись. Имя ветки в Neon Console недоступно без отдельного входа, но endpoint однозначно задаёт подключённую ветку. Production использует pooled URL: постоянному мигратору с session-level advisory lock потребуется отдельный direct URL к той же ветке.

| Файл | Вывод | Наблюдаемое свидетельство |
| --- | --- | --- |
| 001 | Подтверждена с высокой уверенностью | Есть `users` с ожидаемыми UUID, ограничениями, индексом и расширение `uuid-ossp`. |
| 002 | Подтверждена с высокой уверенностью | Есть `habits`, `daily_entries`, внешние ключи, ограничения и индексы. Первоначальный `UNIQUE (user_id, date)` сохранился вместе с новым первичным ключом, что соответствует тексту 002–003. |
| 003 | Подтверждена с высокой уверенностью | Первичный ключ `daily_entries` — `(user_id, date)`, не `id`. |
| 004 | Подтверждена с высокой уверенностью | `daily_entries.id` имеет тип `varchar(255)` без default; `sleep_data` — `jsonb`. |
| 005 | Подтверждена с высокой уверенностью по результату преобразования; точное историческое выполнение файла не удостоверено журналом | У всех 241 записей, созданных до появления 005, время `updated_at` в точности `2026-01-22 01:19:28.309871`; это соответствует единому массовому `UPDATE ... NOW()` внутри 005. У всех 241 записей с `wakeTime` есть `bedtime` предыдущего дня. Совпадение меток и расположение данных вместе дают сильное косвенное свидетельство завершённого преобразования. |
| 006 | Подтверждена с высокой уверенностью | Default `sleep_data` содержит `bedtime`, `wakeTime`, `napDuration`, `duration` с `null`; у всех 793 записей есть новые ключи, старых `napDurationMin`/`durationMin` нет. |

В базе 28 пользователей, 37 привычек и 793 записи дня; персональные значения не выгружались. У 18 записей есть `duration` при пустом `bedtime` текущего дня, однако у всех есть `wakeTime`, `bedtime` предыдущего дня и обновление после выпуска 006. Это согласуется с действующим `SleepRecordsService`, который вычисляет длительность по отбою предыдущего дня, и не является свидетельством частичного выполнения 006.

Отдельного `schema_migrations` пока нет. В истории Railway виден успешный выпуск изменения 006 от 2026-01-22, но Deploy Logs для него уже пусты; первичных логов запуска 005–006 не найдено. Поэтому начальное заполнение журнала должно честно означать **подтверждённое текущее состояние**, а не утверждение о точной дате или байтах исторического запуска. Проведённая сверка служит основанием для начального заполнения журнала; обычные пользовательские записи не требуют её повтора. Новая сверка понадобится лишь при промежуточном изменении схемы или формата данных вне согласованной миграции. При заполнении записать SHA-256 неизменённых файлов 001–006 без выполнения их SQL. На момент проверки расхождений, требующих восстановления схемы или данных, не обнаружено. Production-база не изменялась.

## Comments

- Это проверка состояния, а не запуск мигратора или переключение production. Сначала установить точную production-базу и ветку Neon по данным действующего Railway-сервиса; секреты и строки подключения не записывать в тикет.
- Выполнить чтение схемы: таблицы, первичные и внешние ключи, индексы, тип и default `daily_entries.id`/`sleep_data`. Проверить признаки преобразований данных 005 и 006 по безопасным агрегатам и доступным журналам/истории прежних выпусков. Текущее состояние данных само по себе может не доказать точную историю выполнения 005; явно зафиксировать степень уверенности по каждому файлу.
- Зафиксировать для 001–006 вывод «подтверждена» либо конкретное расхождение с доказательством, без персональных данных и без изменения базы. При расхождении открыть отдельную развилку для способа восстановления перед начальным заполнением журнала. После подтверждения можно детализировать однократную запись исторических версий в реализационной спецификации.
