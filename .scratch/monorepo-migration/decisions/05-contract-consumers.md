# Подключение общего контракта к React и Fastify

Type: grilling
Status: resolved
Blocked by: 02 — Структура pnpm workspace и команды сборки; 03 — Перенос публичного API-контракта в TypeSpec; 08 — Фактический HTTP-контракт и расхождения с YAML

## Question

Как фронтенд и бэкенд должны потреблять артефакты `packages/api-contract` по образцу `shlokahub`: generated frontend client/types и backend operation/handler types, адаптированные к React и Fastify с сохранением runtime-валидации и поведения? Сопоставить это с текущим `openapi-fetch`/`openapi-react-query`; если решение референса здесь не оптимально, предупредить владельца и обосновать лучший вариант.

## Answer

- Владелец выбрал 2026-10-02 для обеих сторон форму референса: web вызывает сгенерированный именованный `ApiClient`, backend реализует единый сгенерированный `ApiHandlers`. Решение принято после сравнения с прямой типизацией существующих Fastify-маршрутов и с клиентом, возвращающим объединение ответов по статусам. `packages/api-contract` предоставляет явные публичные экспорты для `ApiClient`, `ApiClientError`, моделей/операций и backend-типов. Источник и генерация определены в решении «Перенос публичного API-контракта в TypeSpec»; пути Sadhana остаются без `/api`.
- В `apps/api` создать реализацию **всех 14 операций** интерфейса `ApiHandlers` на основе нынешних сервисов. Сгенерированные запросы описывают тело, path/query/cookie-параметры; ответы — различимые пары `{status, body}` и, где требуется, заголовки, в том числе `Set-Cookie`. Обработчики не должны отдавать refresh token в публичном JSON. Генератор референса надо дополнить поддержкой заголовков ответа и приложенческого контекста, не зависящего от Fastify: адаптер передаёт в обработчик проверенного пользователя и сведения, необходимые для атрибутов cookie. Нельзя делать обязательный контекст неявным или повторно проверять JWT в сервисном слое только ради интерфейса.
- Существующие Fastify-маршруты превратить в тонкие адаптеры: сохранить методы и пути, inline JSON Schema, `preHandler: authenticate`, текущие обработчики ошибок, CORS и настройку cookie; извлечь входные данные, вызвать соответствующий `ApiHandlers`-метод, перенести его статус/тело/заголовки в `reply`. Валидация Fastify остаётся действующей runtime-границей; TypeScript-типы её не заменяют. Для исключений `AppError` и неожиданных ошибок сохранить текущие статусы и JSON-форму. При переносе не менять ошибочное, но фактическое превращение ошибок валидации в 500; возможное исправление API — отдельная работа. Интеграционными HTTP-проверками сверить runtime JSON Schema и ответы с TypeSpec, особенно optional/nullable поля, auth cookie, 204 и ошибки из инвентаризации.
- Сгенерированный `ApiClient` возвращает типизированное тело успешного ответа (`undefined` для 204) и выбрасывает `ApiClientError` со статусом и телом для HTTP-ошибки. Это соответствует референсу и нынешней семантике TanStack Query. Генератор должен корректно обрабатывать пустые и не-JSON ответы, не выдавая ошибку разбора JSON вместо исходного HTTP-статуса. Отмену через `AbortSignal` и сетевые ошибки передавать отдельно от HTTP-ошибок. Добавить настраиваемый `fetch`/транспорт и опции запроса; привязку к сессии не помещать в generated-код.
- В `apps/web/src/shared/api` собрать два клиента или эквивалентное разделение транспорта: публичный для login/register/refresh без bearer и защищённый для остальных операций. Оба отправляют `credentials: 'include'`; защищённый транспорт перед запросом асинхронно вызывает существующий `session.refreshToken()`, добавляет bearer и сохраняет текущие исходы 401/503 при невозможности получить токен. Сохранить единственный параллельный refresh и обработку очистки сессии. `Set-Cookie` обрабатывает браузер, клиент не читает HttpOnly cookie из ответа.
- Заменить вызовы `openapi-react-query` в существующих feature-моделях на явные `useQuery`/`useMutation` поверх `ApiClient`, сохранив пользовательские сценарии, состояние загрузки, сообщения ошибок, `onSuccess`, `onError`, отмену запросов, оптимистичный откат и повторные запросы. Ключи кэша без параметров оставить прежними, особенно `['get', '/sleep-records']`, который используется прямым обновлением кэша. Клиент и базовый транспорт живут в `shared`, сценарные hooks и их ключи — в соответствующих `features`, согласно фронтенд-архитектуре. `openapi-fetch` и `openapi-react-query` удалить после проверки поведения; `openapi-msw` можно сохранить для моков, типизируя его новыми `paths` из контракта.
- Это осознанно более глубокое изменение backend, чем минимальная типизация маршрутов: оно даёт единый compile-time интерфейс всех операций и более тесно повторяет `shlokahub`, но требует адаптеров Fastify. При реализации проверить пакетные экспорты, сборку обоих приложений, типизацию всех 14 обработчиков и HTTP-проверки соответствия контракта; web проверить для login/register/refresh, защищённых запросов, истёкшего токена и оптимистичных операций сна.

## Comments

- Сверка 2026-10-02: в `src/shared/api/instance.ts` защищённый `openapi-fetch` перед каждым запросом асинхронно вызывает `session.refreshToken()`, оба клиента отправляют `credentials: 'include'`, а `POST /auth/refresh` идёт через отдельный публичный клиент. Состояние сессии и одиночный параллельный refresh находятся в `src/shared/model/session.ts`. Генерируемый клиент референса поддерживает лишь синхронный access token, возвращает тело успешного ответа и выбрасывает `ApiError`; его транспорт нужно расширить для Sadhana, включая передачу `AbortSignal`, cookie и обработку пустого/не-JSON ответа.
- `openapi-react-query` сейчас образует ключ запросов без параметров как `[method, path]`; оптимистичные обновления списка сна явно используют `['get', '/sleep-records']`. При миграции на именованные методы нужно сохранить этот ключ, отмену запросов, откат и повторный запрос. `openapi-msw` продолжает использовать сгенерированный `paths` для текущих моков и не обязан удаляться вместе с двумя HTTP-клиентскими библиотеками.
- В Fastify Sadhana логика HTTP находится в четырёх файлах маршрутов с inline JSON Schema и вызовами сервисов. В Nest-референсе есть отдельный `ApiHandlersService implements ApiHandlers`, поэтому буквальный перенос его слоя потребует перемещения логики. Текущие Fastify JSON Schema сохраняют runtime-валидацию; типы из контракта должны проверять её соответствие на уровне тестов и типизации, но не подменять её.
- На момент сверки были два выбора владельца: (1) привязать сгенерированные типы операций напрямую к существующим Fastify-маршрутам или выделить единый `ApiHandlers`-объект; (2) возвращать из `ApiClient` тело успеха с типизированным исключением либо объединение ответов по статусам. Для первого варианта первоначально рекомендовались прямые типизированные маршруты как менее затратная переделка; владелец предпочёл более сильный единый интерфейс.
- Владелец выбрал 2026-10-02 единый `ApiHandlers` для backend после сравнения вариантов. Для API это означает перенос HTTP-операций за сгенерированный интерфейс и тонкие Fastify-адаптеры с сохранением действующих JSON Schema, cookie, авторизации и сервисов. Затем владелец уточнил поведение клиента референса и выбрал такое же поведение для Sadhana.
