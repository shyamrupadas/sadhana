# Независимый выпуск приложений прежними поставщиками

Type: grilling
Status: resolved
Blocked by: None

## Question

Как фронтенд будет независимо выпускаться через существующий GitHub Actions → SSH → VPS, а бэкенд — через существующий Railway Git autodeploy из одной монорепы, включая триггеры, контекст сборки, рабочие каталоги, переменные окружения, артефакты и правила отката? Учесть, что референс сейчас выпускает API через другого поставщика: его настройки деплоя нельзя механически перенести в Railway.

## Answer

- Сохранить `master` единственной исходной веткой обоих production-выпусков. Web продолжает выпускаться GitHub Actions по SSH на действующий VPS, API — Git autodeploy действующего сервиса Railway; отдельную release-ветку Amvera из референса не вводить. Для web задать `push` с path-фильтром и `workflow_dispatch`: `apps/web/**`, `packages/api-contract/**`, общие файлы установки/сборки (`package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `turbo.json`, общие TypeScript-конфигурации) и сам workflow. Для Railway задать watch paths на `apps/api/**`, `packages/api-contract/**`, корневой `Dockerfile`/`.dockerignore` и файлы сборки/lockfile, но не `apps/web/**`. Общие изменения запускают оба выпуска, локальные изменения приложения — только его выпуск; изменения одних документов не выпускают приложения. Фильтры должны включать все реальные входы сборки, включая скрипты и конфигурации, добавленные при реализации.
- Web workflow выполняется из корня workspace: Node 24, Corepack, `pnpm install --frozen-lockfile`, прямая `contract:generate` с проверкой всех коммитимых generated-файлов, проверки web и `pnpm build:web` через граф Turbo. `VITE_API_BASE_URL` и отслеживаемый `.env.production` перенести вместе с Vite-приложением в `apps/web`, сверить фактически встроенный production API URL до публикации. По существующим `SERVER_IP`/`SERVER_USER` и SSH secrets синхронизировать **`apps/web/dist/`** через `rsync --delete` в прежний `/var/www/sadhana-app/html/`. Сохранять тот же каталог, права, адрес и SSH-проверку host key; версионные каталоги и симлинки не вводить. После копирования выполнить HTTP smoke check сайта и доступности API. Неуспешная сборка или проверка до `rsync` не меняет VPS; при неудаче после начала копирования повторно выпустить исправленный или прежний проверенный коммит. Быстрого переключения на сохранённую сборку на VPS не будет — это сознательно принятое ограничение.
- API собирать корневым многоэтапным Dockerfile по принципу `shlokahub`: Node 24 и закреплённый pnpm, установка из корневого lockfile, сборка только `@sadhana/api` с workspace-зависимым контрактом, затем изолированный production-образ без web и инструментов сборки. Контекст Docker-сборки и Railway Root Directory — корень репозитория, не `/apps/api`, иначе общий контракт и lockfile недоступны. Для упаковки использовать `pnpm deploy --prod --legacy` без глобального `injectWorkspacePackages`; это сохраняет обычные workspace-ссылки для локальных watcher-ов и создаёт переносимый runtime-пакет. Совместимость конкретной закреплённой версии pnpm и содержимое образа проверять Docker-сборкой и запуском в CI. Образ должен включать SQL-файлы по пути, который использует мигратор; в production API запускает уже собранный `dist/server.js`, без повторной компиляции при старте. Способ запуска миграций до API задаёт решение «Мигратор Sadhana по образцу референса»; не копировать entrypoint или `amvera.yaml` как настройку Railway.
- В GitHub Actions завести обязательный CI workflow на каждый push в `master` и на PR: напрямую регенерировать контракт и проверять отсутствие изменённых и новых файлов в `packages/api-contract/generated/`, запускать lint/typecheck/build/test затронутых пакетов, собирать и проверять запуск production Docker-образа API. Web workflow повторяет необходимые проверки до публикации. В Railway включить **Wait for CI** и healthcheck существующего `GET /` (после проверки, что он возвращает `2xx` в контейнере); не считать пропущенный path-filtered workflow достаточным CI-gate. Railway оценивает итог каждого GitHub Actions workflow на том же коммите: при общем изменении сбой SSH-публикации web может задержать API. Владелец принял эту связь ради прямого выпуска из `master` без отдельной ветки.
- Сохранить действующие production-переменные, секреты, домен и подключение Neon в существующем Railway-сервисе; секреты не копировать в репозиторий или Docker-образ. Fastify уже слушает `0.0.0.0` и Railway `PORT`; сверить это в финальном образе. До перепривязки Git-источника прочитать фактические настройки Railway — branch, Root Directory, build/start/pre-deploy, watch paths, healthcheck, имена переменных и домены — в отдельной задаче «Сверка текущих настроек Railway перед переключением». Не полагаться на настройки Amvera из референса.
- Откат web: вернуть известный рабочий коммит в `master` и повторить workflow; `rsync --delete` восстановит его артефакт в том же каталоге. Откат API: выбрать предыдущий успешный deployment в Railway, который восстанавливает образ и его переменные. Откат образа не откатывает PostgreSQL: миграции должны допускать работу прежней версии API или иметь отдельный заранее проверенный порядок восстановления, что определяется в решениях о миграторе и переключении. Не запускать миграции как побочный эффект Docker build.

[Railway о монорепозиториях](https://docs.railway.com/deployments/monorepo), [Dockerfile](https://docs.railway.com/builds/dockerfiles), [Wait for CI](https://docs.railway.com/deployments/github-autodeploys), [healthcheck](https://docs.railway.com/deployments/healthchecks) и [rollback](https://docs.railway.com/deployments/deployment-actions); [pnpm deploy](https://pnpm.io/11.x/cli/deploy).

## Comments

- Проверено 2026-10-01: текущий [web workflow](../../../.github/workflows/deploy.yml) выпускает `dist/` на каждый push в `master`: Node 24, Yarn install/build, `rsync --delete` в `/var/www/sadhana-app/html/` по SSH. После переноса сборка должна запускаться из корня pnpm workspace, а публиковаться должен `apps/web/dist/`. Отслеживаемый `.env.production` и значение `VITE_API_BASE_URL` следует сохранить в `apps/web` и проверить при сборке; значения секретов не просматривались.
- В `../sadhana-backend` нет файлов Railway или workflow. Нынешний `start` повторно компилирует TypeScript; для монорепы нужна отдельная сборка API и запуск собранного `dist/server.js`. Fastify слушает `PORT` на `0.0.0.0`. SQL-файлы лежат в `src/db/migrations` рядом с исходниками и должны быть доступны мигратору в runtime-образе. Railway CLI и локальной привязки проекта нет: фактические настройки сервиса надо сверить во внешней панели перед переключением.
- [Railway: shared monorepo](https://docs.railway.com/deployments/monorepo) требует сохранять корень workspace в контексте сборки; `Root Directory: /apps/api` отрежет общий контракт. Railway поддерживает watch paths для независимого триггера. [GitHub Actions paths](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) позволяют аналогично фильтровать выпуск web, но path-filtered workflow не подходит как единственная обязательная проверка PR.
- [Railway Wait for CI](https://docs.railway.com/deployments/github-autodeploys) оценивает итог каждого workflow на коммите: сбой web-публикации может заблокировать API на общем коммите, а пропущенный workflow не блокирует. [Railway rollback](https://docs.railway.com/deployments/deployment-actions) восстанавливает прежний образ и его переменные, но не откатывает состояние Neon.
- В референсе есть [корневой Dockerfile](../../../../shlokahub/Dockerfile): многоэтапная Node 24/pnpm-сборка API и контракта, `pnpm deploy` для production-образа и [entrypoint](../../../../shlokahub/docker/api-entrypoint.sh) с миграциями перед сервером. [Backend CI](../../../../shlokahub/.github/workflows/backend-ci.yml) проверяет Docker-образ и продвигает исходники в отдельную ветку для Amvera. Для Railway можно заимствовать принцип сборки образа из корня workspace, но не `amvera.yaml` и не настройки поставщика.
- Владелец подтвердил 2026-10-01 независимые path-триггеры выпусков и обязательные CI-проверки перед автодеплоем API с Railway Wait for CI. При детализации нужно учесть, что Wait for CI наблюдает весь web workflow на общем коммите и может связать выпуски при сбое SSH-публикации.
- Владелец подтвердил 2026-10-01 корневой Dockerfile для API по принципу референса, адаптированный к Railway.
- Владелец выбрал 2026-10-01 прямой Git autodeploy Railway из `master`: отдельная ветка референса была связана с Amvera и здесь считается лишним усложнением. Ограничение Wait for CI на общих коммитах доведено до владельца.
- Владелец выбрал 2026-10-01 сохранить прямой `rsync --delete` web-артефакта в действующий каталог VPS без хранения версий. [Web workflow референса](../../../../shlokahub/.github/workflows/application-production-release.yml) устроен так же: `apps/web/dist/` синхронизируется с `--delete` в `html/`, затем выполняются HTTP smoke checks. Итоговая сводка решения подтверждена владельцем.
