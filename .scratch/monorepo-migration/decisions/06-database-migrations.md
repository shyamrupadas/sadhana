# Мигратор Sadhana по образцу референса

Type: grilling
Status: resolved
Blocked by: 04 — Независимый выпуск приложений прежними поставщиками

## Question

Как адаптировать мигратор `shlokahub` для Sadhana и Railway: учесть уже применённые SQL-миграции без их повторного запуска или редактирования, вести журнал версий и контрольных сумм, исключить параллельное выполнение и определить безопасный момент запуска новых миграций? Сравнить решения референса с условиями Railway и предупредить владельца о необходимых отличиях или улучшениях.

## Answer

- Постоянный мигратор Sadhana строить по алгоритму `shlokahub`: упорядоченные уникальные идентификаторы, журнал `schema_migrations`, SHA-256, пропуск записанных миграций только при совпадении контрольной суммы, единая advisory-блокировка PostgreSQL на время прохода, отдельная транзакция для каждого нового SQL-файла вместе с записью в журнал и ненулевой код завершения при ошибке. Отклонять неизвестные записи журнала, пропуски в уже применённой последовательности и изменение применённого SQL. Использовать отдельное прямое соединение Neon для мигратора и ограниченные таймауты; session-level блокировка не должна проходить через transaction pooler. Существующие SQL-файлы 001–006 оставить без изменений и считать контрольную сумму их точных байтов, а не переносить их в TypeScript-массив референса.
- Для уже работающей production-базы выполнить **однократное начальное заполнение журнала** до включения автоматического Pre-Deploy. Сначала сверить фактическую схему и признаки преобразований данных с результатом исторических миграций и доступными свидетельствами прежних запусков; затем записать только подтверждённые 001–006 с их контрольными суммами и явной отметкой, что они были учтены задним числом, без повторного выполнения SQL и без выдуманной даты исходного применения. Если состояние не подтверждается, остановить переключение и отдельно решить расхождение. На новой пустой базе те же файлы выполняются обычным мигратором. Референсу такой шаг не требовался: журнал был введён вместе с его первыми миграциями. Фактическая сверка Neon вынесена в отдельную задачу карты.
- В Railway запускать скомпилированный мигратор как **Pre-Deploy Command** из production-образа после сборки и до старта новой версии API. При ошибке выпуск не должен активироваться; миграции не выполняются при Docker build или каждом старте контейнера. Это повторяет историческую Railway-конфигурацию `shlokahub` (`eb852da:railway.json`), а его нынешний Docker entrypoint относится к Amvera. Точный путь команды и наличие прямого Neon URL сверить с итоговым образом и фактическими настройками Railway.
- По решению владельца **не вводить обязательную совместимость каждой автоматической миграции с предыдущим API** и отдельную машинерию безостановочного перехода. Принят краткий промежуток, когда миграция уже применена, а прежний API ещё работает. Как в Railway runbook референса, откат приложения разрешён только после проверки прежнего build с текущей схемой и форматом данных Neon; при несовместимости нужен исправляющий выпуск вперёд или отдельный план восстановления. Railway не откатывает SQL при неуспешном старте нового API или откате образа. Каждая миграция атомарна отдельно, но при сбое последующей миграции уже применённые предыдущие сохраняются. Если ожидается пользовательская недоступность, выпуск организовать как контролируемое окно. Вопрос полноценной совместимости и безостановочных миграций оставить на будущую отдельную работу.

Владелец подтвердил начальное заполнение журнала и Railway Pre-Deploy 2026-10-02; политику отката и допустимый краткий промежуток старого API на новой схеме подтвердил 2026-10-02.

## Comments

- Проверено 2026-10-01: старый `../sadhana-backend/src/db/migrate.ts` сортирует и выполняет **все** SQL-файлы при каждом вызове, без журнала и блокировки. `003_fix_daily_entries_primary_key.sql` безусловно добавляет первичный ключ; `005_migrate_bedtime_to_previous_day.sql` и `006_set_duration_min_null_for_missing_times.sql` преобразуют пользовательские данные. Повторный запуск исторических файлов небезопасен. Наличие схемы само по себе не доказывает, что обе миграции данных выполнены полностью; состояние конкретной Neon-базы ещё не проверено.
- Референс `../shlokahub/apps/api/src/database/migration-runner.ts` ведёт `schema_migrations` с контрольной суммой, берёт session-level advisory lock и исполняет одну миграцию с записью в журнал в одной транзакции. Его `docker/api-entrypoint.sh` запускает мигратор при каждом старте контейнера. Для Sadhana нужно сохранить исходные SQL-файлы и считать сумму их точных байтов, не переносить их содержимое в TypeScript-массив с иной схемой хеширования. При проверке журнала также следует отклонять неизвестные идентификаторы и пропуски в последовательности.
- [Railway Pre-Deploy Command](https://docs.railway.com/deployments/pre-deploy-command) выполняется после сборки до запуска новой версии, в отдельном контейнере с переменными сервиса; ошибка останавливает выпуск, таймаут настраивается. История референса подтверждает использование этого механизма на Railway; его нынешний entrypoint относится к Amvera. Владелец согласовал Pre-Deploy для Sadhana 2026-10-02. Session-level advisory lock требует прямого соединения с Neon, а не transaction pooler: [Neon о pooled и direct URL](https://neon.com/blog/inside-lubots-database-per-tenant-architecture), [PostgreSQL об advisory lock](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS).
- На 2026-10-01 ожидалось решение владельца о первичном заполнении журнала и требовании совместимости миграций с предыдущей версией API. Эти решения зафиксированы выше; фактическая сверка production-базы остаётся отдельной задачей.
- Уточнение по истории `../shlokahub` 2026-10-01: commit `eb852da` добавил `railway.json` с `deploy.preDeployCommand: ["node apps/api/dist/database/migrate.js"]`, отдельным `startCommand` и healthcheck. Принятый тикет `.scratch/backend-railway-production/issues/02-deploy-and-verify-production-backend.md` в commit `1418d9c` фиксирует подтверждённый владельцем успешный production pre-deploy. Commit `71cf45c` позже добавил Docker entrypoint с запуском мигратора для Amvera, а `324de82` удалил Railway-конфигурацию. Значит Pre-Deploy был реально применён в референсе на Railway; нынешний entrypoint относится к другому поставщику.
- Политика отката референса точнее первоначальной рекомендации: `1418d9c:docs/operations/railway-production.md` требует проверить совместимость предыдущего API build с текущей Neon-схемой; если она нарушена, выпускать forward fix, а не выполнять Railway rollback. Ранний runbook (`eb852da`, строки 197–198) допускает редкую несовместимую миграцию в окно обслуживания. Автоматического отката SQL нет. История не подтверждает отдельный Railway-релиз с новой миграцией после первого production bootstrap: `0010` появился до принятого Railway rollout, `0011` — уже после перехода на Amvera. Поэтому нельзя утверждать, что совместимость всех Railway-миграций была практически доказана.
- Конкретный пример риска в Sadhana: commit `3bdce5c` добавил `006_set_duration_min_null_for_missing_times.sql`, который удаляет из `sleep_data` ключи `napDurationMin`/`durationMin` и записывает `napDuration`/`duration`; предыдущее API читало старые ключи. Возврат только старого образа после такой миграции не восстанавливает прежний формат данных. Это иллюстрирует, почему перед любым rollback нужна проверка совместимости не только схемы таблиц, но и сохранённых JSON-данных.
- Проверено 2026-10-02: мигратор `shlokahub` появился в commit `99b66ab` вместе с ранними миграциями `0001` и `0002`, то есть его журнал вёлся с начала этой цепочки. Обычный алгоритм `shlokahub` — блокировка, чтение `schema_migrations`, сверка SHA-256 определения, пропуск записанных и транзакция на каждый новый файл с записью в журнал. Он не содержит способа задним числом пометить ранее выполненные миграции без истории. Sadhana нужны тот же постоянный алгоритм, но с чтением неизменённых `.sql` и отдельным однократным заполнением журнала только после сверки состояния production Neon. Эта дополнительная операция решает различие исходных условий, а не меняет принцип последующих миграций.
- Обсуждалось более строгое правило для **автоматического** выпуска из `master`: до запуска Pre-Deploy требовать совместимости новой схемы и формата данных с ещё работающим предыдущим API, а также возможности вернуть его образ после выпуска. Иначе старая версия может ломаться уже во время Pre-Deploy, до активации нового API. Владелец 2026-10-02 выбрал политику референса с допустимым кратким промежутком несовместимости и условным откатом; это решение записано выше.
