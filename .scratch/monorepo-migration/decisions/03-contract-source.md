# Перенос публичного API-контракта в TypeSpec

Type: grilling
Status: resolved
Blocked by: None

## Question

Как перенести текущий OpenAPI YAML в TypeSpec по образцу `shlokahub` без изменения публичного HTTP API и как из TypeSpec получать коммитимые OpenAPI и TypeScript-артефакты с обязательной проверкой их актуальности в CI?

## Answer

- В `packages/api-contract` разместить TypeSpec как единственный редактируемый источник публичного HTTP-контракта. За исходное поведение брать фактические маршруты Fastify и используемые web-сценарии, а не считать текущий YAML безошибочным. Перенос не должен менять методы, пути, параметры, обязательность и допустимость `null`, статусы, тела ответов, авторизацию или работу `refreshToken` cookie. Инвентаризацию всех расхождений выполнить в отдельном решении до окончательного описания операций; уже известны необязательные для Fastify `bedtime`/`wakeTime` в `PUT /sleep-records/{date}` и отсутствующий в YAML `Set-Cookie` у auth-ответов.
- Выбрать вариант Б, подтверждённый владельцем 2026-10-01: по образцу `shlokahub` из TypeSpec генерировать OpenAPI, TypeScript-типы, исполняемый фронтенд `ApiClient` с именованными методами и типы операций/обработчиков для бэкенда. Отдельный публикуемый SDK не нужен. `apps/web` использует `ApiClient` через TanStack Query; существующие `openapi-fetch` и `openapi-react-query` выводятся после проверки эквивалентности поведения. Точное подключение клиента и типизированной границы Fastify определяет билет «Подключение общего контракта к React и Fastify».
- Генерировать коммитимый `packages/api-contract/generated/openapi/openapi.json` через `@typespec/openapi3` с явно закреплённой версией OpenAPI 3.0 и фиксированными `operationId`. Сохранить пути Sadhana без префикса `/api` из референса. Описать защищённые операции, cookie, статусные ответы, ограничения полей и форматы так, чтобы полученный OpenAPI отражал установленный фактический контракт. Версии TypeSpec-пакетов, `openapi-typescript` и скрипта фиксируются в workspace lockfile.
- Коммитимые TypeScript-артефакты: `generated/frontend/types.ts` с `paths`/`components`/`operations`, `generated/frontend/client.ts` с методами `ApiClient`, `generated/backend/handlers.ts` с типами операций; пакет экспортирует их через явный публичный интерфейс. Для перевода OpenAPI-схем в TypeScript использовать `openapi-typescript`; собственный генератор строит поверх этих типов методы клиента и типы обработчиков, не дублируя неполный преобразователь схем референса. Это обоснованное отличие от `shlokahub`: его генератор не учитывает все конструкции, необходимые Sadhana, включая nullable-поля. Неизвестная генератору конструкция должна останавливать генерацию с ошибкой, а не незаметно превращаться в `string` или `any`.
- `ApiClient` должен принимать настраиваемый транспорт, чтобы web сохранил `credentials: 'include'`, асинхронное обновление access token, разделение публичных и защищённых запросов, текущую обработку ошибок и отмену запроса. Конкретный адаптер сессии живёт в `apps/web`, не в generated-файлах. Проверить генератор и клиент на используемых Sadhana вариантах: nullable и необязательные поля, массивы, path/query/cookie-параметры, несколько статусов и ошибок, JSON, `204` без тела и нестандартные/пустые ответы. Типы контракта не заменяют runtime JSON Schema Fastify.
- Единая команда `contract:generate` последовательно компилирует TypeSpec и генерирует все TypeScript-артефакты детерминированно. Generated-файлы не редактируются вручную. В CI после чистой установки запускать эту команду напрямую, без возможного пропуска из-за кэша Turbo; проверять отсутствие как изменений отслеживаемых файлов, так и новых файлов во всём `packages/api-contract/generated/` (например, через `git status --porcelain --untracked-files=all -- packages/api-contract/generated`). Затем запускать проверки пакета и typecheck обоих приложений. Этот обязательный gate должен предшествовать сборке или выпуску приложений; точное размещение по workflow определяет билет «Независимый выпуск приложений прежними поставщиками».
- При реализации пересмотреть [ADR-0002](../../../docs/adr/0002-openapi-api-contract.md): источником становится TypeSpec, OpenAPI и TypeScript-файлы становятся производными. Старые независимые YAML и `generated.ts` обоих репозиториев удалить лишь после сверки покрытия и успешной проверки web/API. Требования к критериям такого сравнения дополнит билет об инвентаризации фактического HTTP-контракта.

Выбор генерируемого клиента следует приоритету владельца: одинаковая схема работы с контрактом в двух монорепозиториях. Прямое копирование генератора референса без устранения его ограничений не является частью решения.

## Comments

- Проверено 2026-09-30: оба репозитория описывают 14 HTTP-операций в YAML. Текущий web использует типы `paths`/`components` из `openapi-typescript` вместе с `openapi-fetch`, `openapi-react-query`, `openapi-msw` и `fetch` с `credentials: 'include'`; backend использует отдельную копию типов и собственные Fastify JSON Schema.
- Найдены расхождения, которые нельзя молча переносить: YAML помечает `bedtime` и `wakeTime` обязательными в `PUT /sleep-records/{date}`, а Fastify требует только `napDuration`; login/register/refresh выставляют `refreshToken` через `Set-Cookie`, чего YAML ответов не описывает. Проверка остальных операций и точных HTTP-границ потребуется при реализации или в отдельном решении после выбора базовой политики.
- Генератор референса `packages/api-contract/scripts/generate-contract.mjs` создаёт собственный HTTP-клиент и упрощённо интерпретирует OpenAPI-схемы. Его прямое копирование затронет существующий React Query-слой, cookie и обработку составных схем. Подходящий вариант для Sadhana — сохранить `openapi-typescript` для общей модели `paths`/`components`/`operations` и отдельно определить типизированную границу Fastify.
- По [документации TypeSpec](https://typespec.io/docs/emitters/openapi3/reference/emitter/) эмиттер умеет явно выпускать OpenAPI 3.0 и задавать путь JSON-артефакта. [Декораторы HTTP](https://typespec.io/docs/libraries/http/reference/decorators/) описывают cookie, а [декораторы OpenAPI](https://typespec.io/docs/libraries/openapi/reference/decorators/) позволяют закрепить `operationId`. Проверку коммитимых файлов в CI следует запускать прямой генерацией и проверкой статуса всех файлов `generated/`, включая новые, без пропуска из-за кэша Turbo.
- Открыт выбор: сохранить совместимые типы для существующего клиента или генерировать клиент по образцу референса.
- Владелец подтвердил 2026-09-30: при расхождении TypeSpec должен описывать фактическое HTTP-поведение. Выбор формы TypeScript-артефактов пока открыт; владелец запросил сравнение подходов.
- Уточнение 2026-10-01: сравниваются не два источника контракта, а два способа построить фронтенд-клиент из одного TypeSpec → OpenAPI. Вариант `openapi-typescript` генерирует только типы, HTTP выполняют библиотечные `openapi-fetch`/`openapi-react-query`; вариант референса генерирует также исполняемый `ApiClient` собственным скриптом. Второй вариант требует поддерживать сериализацию, ошибки, авторизацию, cookie и интеграцию с React Query в коде проекта. Для текущей Sadhana это отдельная ответственность без явного нового потребителя; наличие внешних SDK-потребителей могло бы изменить выбор. Официальная [схема использования openapi-fetch](https://openapi-ts.dev/openapi-fetch/) и [интеграция с React Query](https://openapi-ts.dev/openapi-react-query/) совпадают с текущим подходом; [клиентские эмиттеры TypeSpec](https://typespec.io/docs/emitters/clients/introduction/) сейчас обозначены как preview.
- Владелец уточнил 2026-10-01: отдельного SDK не планируется, но единообразие двух монорепозиториев важно; он склоняется к генерируемому клиенту референса и попросил сравнить перенос Sadhana на этот подход с переводом референса на библиотечный клиент. В `shlokahub` сейчас 28 операций, 17 production-файлов web используют `apiClient`, backend реализует сгенерированный `ApiHandlers`; в Sadhana 14 операций и 8 файлов используют текущие fetch/React Query клиенты. Поэтому буквальное выравнивание под вариант с генерируемым клиентом затрагивает меньше существующего кода, но потребует доработать генератор под контракт Sadhana, cookie и асинхронное обновление токена. Окончательное решение владельца пока открыто.
