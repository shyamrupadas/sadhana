# Порядок переключения и критерии приёмки

Type: grilling
Status: resolved
Blocked by: 01 — Роль прежнего backend-репозитория после переноса; 04 — Независимый выпуск приложений прежними поставщиками; 05 — Подключение общего контракта к React и Fastify; 06 — Мигратор Sadhana по образцу референса; 09 — Сверка текущих настроек Railway перед переключением; 10 — Сверка исторических миграций в production Neon

## Question

В каком порядке перенести код, настроить проверки, переключить оба действующих деплоя на монорепу и подтвердить совместимость API, auth/cookie, PWA и PostgreSQL без потери возможности отката, включая проверку обновлённого мигратора на Railway?

## Answer

Владелец подтвердил 2026-10-02 следующий порядок. Переключение выполняется как отдельная реализация после спецификации; этот билет определяет её шаги и условия остановки.

1. **Подготовить один проверенный снимок монорепозитория.** При переносе записать актуальный SHA локального `sadhana-backend`, взять только его отслеживаемые исходники и сохранить текущие адреса, секреты, SQL 001–006 и поведение API. В PR проверить чистую установку pnpm, прямую `contract:generate` с нулевым diff всего `generated/`, lint/typecheck/build/test workspace, все 14 HTTP-операций и соответствие Fastify JSON Schema контракту. Проверить production Docker-образ API: запуск `dist/server.js` на `0.0.0.0:8080`, `GET /` → 2xx, наличие всех SQL и собранного мигратора. В локальном/интеграционном прогоне проверить обе переходные пары: **новый web + старый API** для первого выпуска и **старый web + новый API** для возможного отката web; затем **новый web + новый API**. Не добавлять в этот структурный выпуск новую предметную SQL-миграцию: изменение схемы или формата данных потребовало бы отдельной оценки совместимости и отката.
2. **Отрепетировать мигратор на временной ветке Neon.** Создать из ветки, к которой подключён production Railway, временную изолированную ветку с текущей схемой и данными; не подменять ею рабочую базу и не выгружать персональные данные. Отдельным direct URL на этой ветке проверить однократное заполнение `schema_migrations` для подтверждённых 001–006 по SHA-256 исходных байтов SQL, без исполнения исторических файлов. Два запуска постоянного мигратора подряд должны завершиться успешно, увидеть те же шесть сумм и не изменить пользовательские таблицы. На пустой локальной PostgreSQL проверить обычное применение 001–006, а на уровне тестов — отказ при изменённой сумме, пропуске/неизвестной версии, ошибке SQL и конкурирующих запусках. Временную ветку удалить после приёмки, сохраняя её до конца переключения как точку сравнения; не считать её автоматическим откатом production-записей.
3. **Сначала выпустить web.** Первый общий коммит в `master` проходит обязательный CI и автоматически запускает обновлённый web workflow. Railway пока привязан к старому `sadhana-backend`, поэтому новый web некоторое время работает со старым API. До переключения Railway проверить GitHub Actions, публикацию именно `apps/web/dist/` в прежний каталог VPS, фактически встроенный `VITE_API_BASE_URL`, HTTP-доступность сайта и API, вход/обновление сессии и основные экраны на этой переходной паре. Если новый web несовместим со старым API, остановить переключение Railway и восстановить прежний web-выпуск по известному рабочему коммиту; причину исправить до продолжения.
4. **Провести ручную проверку готовности перед изменением Railway.** Убедиться, что CI и Docker-проверки зелёные, web работает со старым API, репетиция Neon успешна, известны SHA исходного backend и нового монорепозитория, а план возврата к прежнему deployment записан. Сверить, что production `DATABASE_URL` и новый direct URL мигратора относятся к одной ветке Neon; значения секретов не записывать в Git или отчёт. Повторно проверить, что production-схема и признаки данных не изменились после инвентаризации 001–006. Если есть расхождение, остановиться и выяснить его до записи журнала. Заполнить production `schema_migrations` подтверждёнными 001–006 один раз и проверить строки/суммы; исторический SQL не запускать.
5. **Переключить существующий API-сервис.** В том же Railway project/environment/service сохранить домены, порт, регион, одну реплику и нынешние переменные; указать монорепозиторий `master`, корень workspace, корневой Dockerfile, API watch paths, Wait for CI, Healthcheck `/` и Pre-Deploy Command собранного мигратора с direct Neon URL. Изменять эти настройки только после проверки готовности. Перепривязка источника не гарантирует выпуск уже опубликованного SHA, поэтому явно выполнить **Deploy Latest Commit**, сверить SHA, Docker build, лог Pre-Deploy и итоговый healthcheck. Pre-Deploy должен увидеть 001–006 в журнале и не выполнять их повторно. При ошибке Pre-Deploy или healthcheck новый API не принимать; прежний работающий deployment должен оставаться доступен.
6. **Принять результат на действующих адресах.** Проверить `GET /` и контрактные HTTP-сценарии, CORS и `credentials: include`, login/register/refresh с `Set-Cookie` и HttpOnly/Secure/SameSite, авторизованные запросы после истечения access token, состояние 401/503, привычки, записи сна, вчерашнюю проверку и статистику. Владелец сам проверяет запись и чтение через свою учётную запись в production; отдельную проверочную учётную запись не создавать. Для web проверить навигацию, загрузку и ошибки, оптимистичное обновление/откат сна и привычек, manifest/иконки/service worker и получение свежих ресурсов после обновления PWA. Сверить журнал миграций и агрегаты пользовательских таблиц, исключив непредусмотренное повторное преобразование данных. Зафиксировать успешные SHA и deployment IDs обоих приложений.
7. **При сбое откатывать только совместимое приложение.** До переключения API возврат web выполняется повторным выпуском известного рабочего коммита. После переключения web возвращать только к проверенной с новым API версии, не откатывая общий контракт или API побочным изменением `master`; если такой версии нет, выпускать исправление вперёд. Railway может восстановить прежний API deployment, но перед этим проверить его совместимость с текущей схемой и форматом JSON в Neon. Откат образа не откатывает миграции или пользовательские записи. При несовместимости — исправляющий выпуск вперёд либо отдельно подготовленный план восстановления в контролируемое окно. Завершить переключение только после успешной проверки обоих приложений и базы.

После переключения сохранить независимые path-триггеры web и API, описанные в решении «Независимый выпуск приложений прежними поставщиками». Для Railway проверить, что GitHub Actions на том же SHA завершились до автодеплоя. [Railway: GitHub autodeploy и Deploy Latest Commit](https://docs.railway.com/deployments/github-autodeploys); [Neon: временные изолированные ветки](https://neon.com/docs/get-started-with-neon/workflow-primer).

## Comments

- Первоначальный выбор «сначала API, затем web» пересмотрен после уточнения автоматического выпуска web; утверждён итоговый порядок в `## Answer`.
- Production Neon остаётся рабочей базой и после перехода. Владелец согласовал 2026-10-02 репетицию мигратора на временной ветке Neon с копией текущего состояния перед первым запуском в production; постоянная тестовая база не нужна.
- Владелец согласовал 2026-10-02 отдельную проверку готовности после CI и до перепривязки действующего Railway-сервиса.
- Владелец предпочёл 2026-10-02 автоматически публиковать web вместе с первым общим коммитом, без временного ручного выпуска. Итоговый порядок «web → API» и полную схему переключения он подтвердил 2026-10-02.
- Владелец сам проверит запись после переключения API через свою учётную запись; отдельную проверочную учётную запись в production создавать не нужно.
- По документации Railway перепривязка Git-источника сама по себе не гарантирует выпуск уже существующего коммита; после смены источника явно выполнить Deploy Latest Commit и сверить SHA. Далее действует autodeploy с Wait for CI: https://docs.railway.com/deployments/github-autodeploys.
- Приёмка должна покрыть HTTP-контракт 14 операций, login/register/refresh с `Set-Cookie`, защищённые запросы после истечения access token, операции сна и привычек с оптимистичным откатом, статистику, PWA-обновление и сохранность состояния Neon. Для мигратора проверить, что повторный запуск пропускает 001–006 по журналу и не исполняет их SQL снова; ошибка Pre-Deploy не активирует новый API.
