## Question

На основании диагностики, исследования и принятого макета выбрать минимальную организацию хранения и API: параметры диапазона/масштаба, ограничение объёма, поля средних и счётчиков, дни без записей, границы истории и инвалидация после изменения дня или привычки. Требуется ли миграция или хватает изменения запросов? Как сохранить временность определения процента привычек и проверяемость расчётов без дублирования бизнес-логики? Какие измеримые критерии скорости и корректности войдут в спецификацию?

## Проверенные предпосылки

2026-10-10 — решение взято в работу после разрешения всех четырёх блокирующих решений. Применены `wayfinder`, `grilling` и `domain-modeling`; два агента проверили локальный код по правилу `grilling` о сборе фактов. Новые обращения к production и БД не выполнялись.

- Для скорости достаточно устранить чтение предыдущего дня внутри цикла; миграция сна или нормализация дневных JSONB ради устранения N+1 не обоснованы. Основание — [диагностика](../research/request-latency.md) и [исследование доступа](../research/data-access.md). Скорость нового endpoint пока не измерена.
- Старый `/sleep-stats` возвращает три фиксированные сводки, использует другие периоды и выборки. Изменение смысла его ответа нельзя выдать за одну оптимизацию запроса. Новый диапазонный контракт следует описать в TypeSpec по [ADR](../../../docs/adr/0002-openapi-api-contract.md); способ перехода пока не выбран.
- В [схеме привычек](../../../apps/api/src/db/migrations/002_create_habits_and_daily_entries.sql) уже есть UUID определения, но API и дневные отметки используют только `key`. [Создание](../../../apps/api/src/services/habits.service.ts) выводит ключ из названия, переименование сохраняет его, удаление физически удаляет определение. Отметки остаются, поэтому повторное создание с тем же ключом может присоединить прежнюю историю к новому определению.
- [Запись отметки](../../../apps/api/src/services/sleep-records.service.ts) допускает неизвестный ключ. Поэтому ключ без определения сам по себе не доказывает удаление привычки. Из оставшихся отметок нельзя восстановить последнее название, даты создания/удаления или надёжно разделить повторные создания; первая/последняя отметка не являются границами активности.
- Существующий `created_at` хранится как timestamp без часового пояса, а API сериализует его как UTC timestamp. Он не фиксирует календарный день создания на устройстве пользователя. Надёжные календарные границы будущих привычек и трактовка прежних времён создания — отдельные вопросы перехода; автоматический пересчёт всей истории пока не согласован.
- [Миграция переноса отбоя](../../../apps/api/src/db/migrations/005_migrate_bedtime_to_previous_day.sql) при создании предыдущего дня копировала туда отметки текущего дня. Это риск для проверки старой истории, а не установленная проблема конкретного аккаунта; никаких автоматических исправлений на основании совпадений отметок не предлагать.
- Мутации [дня](../../../apps/web/src/features/main/model/use-sleep-records.ts) и [привычки](../../../apps/web/src/features/main/model/use-habits.ts) сейчас обновляют запросы главной, но не окна статистики. Изменение отбоя даты d затрагивает длительность d+1, включая соседний календарный период.
- Ключ [старой статистики](../../../apps/web/src/features/statistics/model/use-sleep-stats.ts) не содержит пользователя, а [выход из аккаунта](../../../apps/web/src/shared/model/session.ts) не очищает общий QueryClient. Новый кэш должен быть отделён по аккаунтам, с отменой запросов и очисткой приватных данных при смене сессии; это требуется для корректности самой новой истории.

## Предложения для обсуждения — не приняты

Минимальный технический кандидат: чтение ограниченного диапазона с предыдущей календарной датой, расчёты на API по первичным значениям, полный календарь колонок без сохранения пустых дней в БД. Формат дневных JSONB сохранить. Для привычек сохранить прежние ключи нынешних определений, новым выдавать уникальный непрозрачный ключ независимо от названия; удаление заменить архивированием с сохранением последнего названия и календарных границ активности. Перенос всех отметок на UUID и отдельная таблица отметок — более дорогие альтернативы, пока не выбранные. Это изменения будущей реализации, а не разрешение выполнять миграцию сейчас.

Кандидат обновления: после успешного изменения дня или определения привычки инвалидировать всю статистику текущего пользователя; получать новые данные для открытого окна. Ключи кэша должны различать аккаунт, масштаб, диапазон и календарную границу текущего периода. При смене локальной даты обновляются сегодняшний день и текущие агрегаты. Правила и счётчики рассчитываются на API, клиент только форматирует значения; счётчики в ячейках не показываются. Точные поля, лимиты и жизненный цикл кэша ещё требуют выбора.

## Comments

2026-10-10 — первый раунд обсуждения. Ни один вариант ниже ещё не подтверждён пользователем; `## Answer` намеренно отсутствует.

**Q1 — Минимальная организация данных.** Выбрать описанный кандидат: дневные JSONB сохраняются, расчёты выполняются на API, будущие удаления архивируют определение, новые ключи не зависят от названия и никогда не переиспользуются? Рекомендация: этот вариант; он устраняет подтверждённую причину задержки и обеспечивает будущую историю привычек без переноса всех дневных отметок на новую схему.

**Q2 — Неполная старая история.** Как показывать прежние отметки, если определение отсутствует или один ключ мог объединить несколько созданий? Рекомендация: сохранить исходные отметки и их даты, неизвестное название показывать как «Привычка без названия» с различимым обозначением строки; явно обозначать неполноту сведений. Не угадывать даты активности и не выдавать историю ключа за достоверно разделённые жизненные циклы. Процент среди сохранённых отметок можно посчитать, полноту учёта при неизвестных границах — нет. Для ключа с нынешним определением само наличие названия не доказывает непрерывность прежней истории. Альтернатива: до включения старых привычек потребовать отдельного восстановления/сопоставления; без дополнительных источников оно может оказаться невозможным. Проверка конкретных случаев — отдельная работа после выбора политики.

**Q3 — Начало доступной истории.** Если привычка появилась 1 мая, первая отметка сделана 10 мая, а первая запись сна — 5 мая, начинать таблицу 1 мая или 5 мая? Рекомендация: с наиболее ранней даты содержательных данных сна, сохранённой отметки или известного начала активности привычки; полностью пустая строка БД сама по себе начало не задаёт. В примере — 1 мая, дни без отметок остаются видны. Для недель/месяцев/лет первый период разворачивается от своей календарной границы, как уже согласовано. Если истории вообще нет, показывать сегодня с пустыми показателями сна и нулём дневного сна; не создавать записи ради показа.

**Q4 — Подгрузка непрерывной таблицы.** Что происходит, если пользователь дошёл до ещё не полученного участка? Рекомендация: заранее подгружать соседний диапазон, сохранять уже показанные ячейки и положение прокрутки. Для недоступных колонок показывать загрузку, при ошибке — повторить запрос в этой области. Не превращать сетевую ошибку в прочерки или нули: такие значения обозначают уже полученные пустые данные. Новые колонки добавлять без скачка выбранной даты и закреплённых строк. При достижении известной границы истории подгрузку прекращать.

После ответов уточнить зависящие от них поля API, размеры окон и лимиты исходных дней, календарные даты активности при переходе, поведение кэша при обновлении/ошибке и измеримые критерии скорости. Отдельно оформить ставшую определимой проверку старой истории и порядок перехода со старого API; карту пока не объявлять завершённой.
