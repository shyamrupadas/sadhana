## Question

На авторизованном аккаунте с историей примерно за год воспроизвести задержку `/sleep-stats`, отделить передачу ответа и UI от работы API; измерить выборку PostgreSQL, число последовательных SQL и время расчётов. Какие факты подтверждают причину и какой способ доступа устраняет её без изменения смысла текущего ответа? Проверки production выполнять только чтением. Реализация исправления — следующий этап.

## Answer

Диагностика 2026-10-09 подтверждает N+1: 527 записей дня → 528 последовательных SQL. Авторизованный браузер стабильно ждёт около 4,6 с до ответа 194 байта; сама общая выборка выполняется PostgreSQL за 0,541 мс. В диагностическом запуске того же сервиса на предварительно загруженных строках поиск соседней даты в памяти и расчёты заняли 207 мс, ответ строго совпал. Устранение SQL внутри цикла не требует изменения схемы; для новой статистики дополнительно нужен ограниченный диапазон с предыдущим календарным днём. Production-скорость кандидата ещё не измерена, исправление не внесено.

Подробности, воспроизведение, альтернативные гипотезы и ограничения — в [отчёте о задержке](../research/request-latency.md). Контекст: текущая ветка `master`, без коммитов и staging; диагностика БД выполнена READ ONLY, соединение закрыто.
