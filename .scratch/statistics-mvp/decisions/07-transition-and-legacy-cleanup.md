## Question

После выбора модели хранения и контрактов определить порядок перехода данных к новой статистике, архивированию и окончательному удалению. Как перенести первичные данные без изменения введённых дат/часов, очистить прежние бесхозные отметки по согласованной политике, проверить число и идентичность отметок до/после, обеспечить атомарное удаление выбранной привычки и обновление её кэша? Как перенести сохраняемую смешанную историю существующего ключа, включая отметки раньше нынешнего `created_at`, не потеряв их на фильтре даты создания и не выдумав прежние жизненные циклы? Какие проверки и порядок переключения чтения/записи нужны, чтобы две копии первичных данных не расходились? Обновление пользовательских клиентов исключено из этого решения; выпуск API без обратной совместимости принят пользователем.

## Answer

2026-10-24 — решение согласовано с пользователем в последовательных раундах. Последнее уточнение: пользователь вручную останавливает API, самостоятельно делает резервную копию production-БД, затем вливает проверенные изменения в `master`. Автодеплой Railway остаётся включённым и выполняет выпуск новой версии. Текущая сессия завершает планирование; миграции, очистка и production-выпуск не выполнялись.

### Перенос и сохранность

- На постоянной dev-БД проверить прежние тестовые данные, миграцию, ожидаемую схему, сохранность первичных значений, работу нового API и повторный запуск. В production выпускаются те же SQL; копирование production в dev не требуется.
- Сохраняются владелец и календарная дата записи, полные местные дата/часы каждого значения сна без UTC-конверсии и повторного сдвига отбоя, исходные минуты дневного сна. Производная длительность не переносится как первичный факт; новые расчёты следуют принятым правилам, а не требуют совпадения со старым `/sleep-stats`.
- Определения сопоставляются с отметками по владельцу и прежнему ключу, существующий UUID сохраняется. Все отметки существующего ключа переносятся целиком, включая явное `false` и даты раньше нынешнего `created_at`; разбиение прежних жизненных циклов не выдумывается. Расчётное начало прежней привычки — более ранняя из календарной даты исходного `created_at` без пересчёта часового пояса и первой сохраняемой отметки. Исходный timestamp сохраняется отдельно; условная граница не выдаётся за достоверно восстановленное создание. Для новых привычек сохраняется календарная дата создания с устройства. Если нет пригодной даты создания и отметок, неизвестную границу не заменять датой миграции; полнота учёта отсутствует.
- Очистка исключает только отметки без определения у того же владельца по политике [«Хранение, API и обновление статистики для MVP»](05-storage-and-api-decision.md). Сон и строки дня целиком этой очисткой не удаляются. Некорректные исходные значения или коллизии ограничений останавливают перенос до разбора, а не исправляются догадкой и не молча пропускаются.
- До запуска нового API автоматическая сверка проверяет сохраняемые записи в обе стороны: владельца, дату, идентичность привычки, значение `true`/`false`, исходные значения сна и определения. Дополнительно проверяются количества, уникальность и принадлежность владельцам. Допустимые отличия — заранее посчитанные бесхозные отметки и исключённые производные поля; одних общих количеств недостаточно. Ошибка сверки останавливает Pre-Deploy с ненулевым кодом.

### Выпуск и отказ

- Принят порядок из [инструкции production-выпуска](../release.md): ручная остановка текущего deployment через Railway Remove, подтверждение завершения транзакций/отсутствия других писателей, резервная копия пользователем по обязательному напоминанию, затем merge в `master`. До паузы и готовности копии несовместимый commit не публикуется в подключённой ветке; другого ожидающего/выполняющегося выпуска быть не должно. Отключение автодеплоя и штатный ручной Deploy Latest Commit не требуются.
- После merge Railway ждёт CI, собирает образ, выполняет production Pre-Deploy с переносом/сверкой и запускает готовую новую версию. Ожидание CI итогового commit, сборка и запуск входят в паузу. Ранее названные 10–15 минут не являются измеренным сроком или пределом. После dev-репетиции уточнить длительность преобразования; пауза заканчивается при доступности нового API, а не после последующего ручного просмотра приложения.
- Всё рабочее чтение и запись после переключения используют новую модель. Прежние пути записи отключены; две первичные копии и fallback к старым данным не поддерживаются. Старые поля/структуры удаляются только после сверки. API без обратной совместимости принят, всё обновление клиентов — за пределами задачи.
- При ошибке API остаётся остановленным. Runner не откатывает всю цепочку миграций; выясняется фактическое состояние и выполняется исправление вперёд по уже принятому [решению о dev/production](../../database-environments/decisions/05-migration-rehearsal-and-release.md). Старое приложение можно вернуть только при совместимости со схемой. Восстановление резервной копии — отдельное действие пользователя; после новых записей нельзя просто восстановить старый снимок и потерять изменения.

### Окончательное удаление

После одного подтверждения удалить выбранную привычку по устойчивому идентификатору и владельцу вместе со всеми актуальными отметками одной атомарной операцией. Изменения с другого устройства не требуют обновления или повторного подтверждения; новое определение с тем же названием не затрагивается. Конкурентная запись не должна восстанавливать удалённую привычку/бесхозные отметки. После успеха обновляются определения/счётчики и инвалидируются статистика и связанные представления по ранее согласованной политике кэша; при ошибке удаление не показывается как успешное.

## Принятые ограничения

- Целевой жизненный цикл и правило очистки хранятся в [«Хранение, API и обновление статистики для MVP»](05-storage-and-api-decision.md); этот билет определяет переход, а не дублирует политику.
- Архивирование и возврат сохраняют одну привычку и её отметки. Окончательное удаление уничтожает привычку и все её отметки после одного конкретного подтверждения с названием и количеством.
- Периоды активности не вводятся; архивные дни не исключаются из календарных расчётов.
- Очистка удаляет только отметки без определения привычки у того же пользователя. Смешанная история существующего ключа сохраняется целиком; строки сна или произвольные записи дня не удаляются этой очисткой. Подробности согласованной политики — в блокирующем решении.
- В рамках карты описать и согласовать переход. Миграции, production-записи и фактическая очистка выполняются на этапе реализации.
- 2026-10-24 — пользователь вынес всё обновление пользовательских клиентов за пределы задачи и явно принял выпуск production API без обратной совместимости. Подготовительный клиентский выпуск, форсирование обновления PWA, экраны технической паузы/обновления, перенос неотправленного ввода и поддержка прежних клиентов не являются требованиями или блокерами этого MVP. Согласованная пауза записи и сохранность серверных данных остаются в рамках перехода.

## Подготовка к обсуждению

2026-10-22 — применены `grilling` и `domain-modeling`; факты локального кода проверяются отдельно от пользовательских решений. Ниже предложения, а не согласованный ответ. Production и данные не меняются.

- В [нынешней схеме](../../../apps/api/src/db/migrations/002_create_habits_and_daily_entries.sql) определение уже имеет UUID, но прежние операции используют `key`. Соответствие для переноса — владелец и ключ; существующий UUID можно сохранить. Повторные жизненные циклы по старому ключу автоматически не разделяются.
- `created_at` определения — timestamp без часового пояса; [сервис](../../../apps/api/src/services/habits.service.ts) сериализует его через `toISOString()`. Это не надёжно известная локальная дата создания на устройстве. Исходную метку нельзя молча заменить первой отметкой или выдавать восстановленную границу за достоверное создание.
- [Runner миграций](../../../apps/api/src/db/migrate.ts) использует advisory lock между запусками runner и отдельную транзакцию на каждую миграцию. Он сам не останавливает запись API; вся последовательность миграций не является одной транзакцией. Нужны явная остановка писателей, завершение начатых запросов и проверка согласованного среза.
- В [конфигурации PWA](../../../apps/web/vite.config.ts) включён `autoUpdate`. Это не основание считать все открытые клиенты обновлёнными и продолжать принимать команды прежнего формата после переключения.
- [Контракт сна](../../../packages/api-contract/main.tsp) принимает полные местные значения `YYYY-MM-DD HH:mm` без offset. Дата такого значения может отличаться от даты записи дня; это делает и [главная](../../../apps/web/src/features/main/main.page.tsx) при вводе отбоя. Перенос должен сохранить дату и часы каждого исходного значения без UTC-конверсии; одного SQL `TIME` недостаточно. Производную длительность не переносить как первичный факт.
- Нынешний контракт мутаций не содержит версии протокола или ревизии; [HTTP-клиент](../../../apps/web/src/shared/api/instance.ts) добавляет авторизацию. Надёжное отклонение старой записи требует различимого нового контракта: нового маршрута либо обязательного поля/заголовка с проверкой на сервере. Старый DELETE не содержит нового подтверждения с именем и числом отметок. Объяснение обязательного обновления придётся заранее доставить клиенту либо обслужить отдельным переходным механизмом; само отклонение старой команды не добавит такой экран в уже загруженный код.

## Согласованные части решения

2026-10-22 — ответы пользователя на первый раунд:

- **Q1 — согласован с последующим сужением scope 2026-10-24:** пауза записи допустима; API выпускается без обратной совместимости. Пользовательское обновление клиентов выполняется отдельно и не блокирует этот переход. Обсуждавшийся подготовительный выпуск не требуется в этой задаче.
- **Q2 — согласован:** расчётное начало прежней привычки — более ранняя из сохранённой календарной даты создания без пересчёта часового пояса и первой сохраняемой отметки. Исходный timestamp сохраняется; расчётная граница не выдаётся за восстановленную достоверную дату создания. Для новых привычек сохраняется календарная дата создания с устройства.
- **Q3 — рекомендация повторного подтверждения отклонена:** после одного подтверждения окончательно удалить выбранную привычку и все её актуальные отметки, даже если с другого устройства добавлены или изменены данные. Изменение после открытия подтверждения не требует его обновления или повторного согласия. Атомарность и ограничение владельцем/устойчивым идентификатором сохраняются; новое определение с тем же названием не является выбранной привычкой.
- **Уточнение Q4:** пользователь подтвердил порядок «проверить на dev, затем выпустить те же проверенные миграции в production». Резервную копию production-БД делает сам пользователь; в конкретной инструкции выпуска нужно напоминание. Способ остановки и длительность паузы ещё обсуждаются.
- **Итог Q4:** полная недоступность API и ручная остановка пользователем приняты. Согласован порядок «остановить API → сделать резервную копию production-БД → влить проверенные изменения в `master` → дождаться автодеплоя Railway». Прежнее предложение отключать автодеплой и вручную запускать Deploy Latest Commit заменено этим порядком. Итог и границы проверки хранятся в `Answer`, действия — в [инструкции выпуска](../release.md).

## Уточнение обновления клиента — история, вне scope с 2026-10-24

Проверка и предложение ниже сохраняются как история обсуждения. Пользователь не принял этот сценарий как часть MVP: всё обновление клиентов выполняется отдельно, несовместимый API допустим. Вопросы этого раздела больше не ожидают ответа в рамках карты.

### Проверенное текущее поведение

2026-10-22 — проверены установленный `vite-plugin-pwa@1.3.0`, исходники приложения и существующие локальные артефакты `apps/web/dist`, без новой сборки и без проверки production.

- При отсутствии импорта `virtual:pwa-register` плагин использует простую регистрацию service worker. Локальные `dist/index.html` и `dist/registerSW.js` подтверждают этот путь: регистрация на загрузке окна без обработчика перезагрузки UI.
- Локальный `dist/sw.js` содержит `skipWaiting()` и `clientsClaim()`: новый worker может активироваться и перехватить запросы открытых окон. Это не заменяет уже выполняющийся JavaScript/React.
- В исходниках нет обработчика обновления SW, проверки минимально совместимого клиента или общего экрана обязательного обновления. Перезагрузка при ошибке загрузки чанка в `shared/lib/lazy-with-retry.ts` решает другой случай и не гарантирует обновление при смене API.
- [Документация Vite PWA](https://vite-pwa-org.netlify.app/guide/auto-update) также отдельно указывает необходимость клиентского virtual-модуля для перезагрузки открытого UI. Поведение установленной версии дополнительно проверено по её коду, поскольку общие описания `autoUpdate` недостаточны.
- Поэтому публикация нового frontend сама по себе не гарантирует остановку старых запросов. При отключении старого контракта уже открытый неподготовленный клиент получит ошибку; серверный ответ не может добавить в старый JavaScript отсутствующий экран обновления. Установленная PWA не требует переустановки ради обновления web-кода, но нуждается в загрузке/активации новой версии и перезапуске интерфейса. Мгновенное обновление закрытого, приостановленного или офлайн-клиента не гарантируется.

### Предложение пользовательского сценария

Это следующий раунд, а не принятое решение:

1. До несовместимой миграции выпустить совместимое обновление клиента с проверкой совместимости, обработкой технической паузы и управляемым обновлением PWA. Пока сервер работает по-старому, этот клиент продолжает обычную работу.
2. В начале окна перехода сервер временно запрещает новые изменяющие операции и дожидается уже начатых. Подготовленный клиент показывает «Обновляем приложение. Сохранение временно недоступно»; неподтверждённый запрос не показывается как сохранённый. Уже сохранённые данные остаются на сервере. Политику ещё не отправленного ввода согласовать отдельно; внезапную перезагрузку посреди ввода не считать принятым решением.
3. После переноса и сверки подготовленный клиент при необходимости показывает «Доступна обязательная версия» и кнопку «Обновить». Кнопка проверяет/загружает новую версию, ожидает её готовности и перезапускает интерфейс в том же окне/PWA. Если загрузка не удалась, показывается повтор, а не бесконечная перезагрузка.
4. Старый несовместимый контракт после переключения не пишет в прежнее хранилище. Подготовленный клиент обрабатывает этот отказ как обязательное обновление; проверка при старте/возврате в приложение ускоряет обнаружение, серверная проверка каждой затронутой команды остаётся гарантией совместимости.
5. Подготовительный выпуск не гарантирует, что каждый пользователь успел его получить. Давно открытый клиент без механизма обновления по-прежнему может показать обычную ошибку и потребовать ручного обновления/перезапуска. Для бесшовной поддержки таких клиентов понадобятся отдельный адаптер совместимости или специально спроектированный механизм перезагрузки через SW; их нельзя считать уже существующими либо автоматически включёнными в план.

На момент предложения ожидались решения о механизме обновления, неотправленном вводе и старых клиентах. С 2026-10-24 все эти вопросы исключены из scope. В этом билете остаются критерии сверки, точка переключения и правила отката серверных данных.

## Раунд о переносе и проверке данных — история предложений

2026-10-24 — техническое предложение с учётом принятых ограничений; ещё не итоговый `Answer`.

**Q4 — Порядок переноса и граница отката.** Рекомендация:

1. До production-перехода выполнить существующую репетицию на постоянной dev-БД с совместимыми тестовыми данными, без обязательного копирования production. Зафиксировать обезличенные результаты сверки и длительность. Затем выпустить те же проверенные SQL через production Pre-Deploy; dev-проверка не заменяет перенос production-данных.
2. На время перехода остановить все затронутые серверные записи, включая изменения определений привычек и записей дня, и дождаться начатых операций. Напомнить пользователю сделать резервную копию production-БД и дождаться подтверждения: копию он делает сам. Блокировка runner сама по себе запись API не останавливает. Пока перенос и проверки не завершены, новые записи не открывать. Предлагаемая полная остановка API и границы паузы описаны в [инструкции выпуска](../release.md); они ещё обсуждаются.
3. Перенести полные местные даты и часы сна без UTC-конверсии и повторного сдвига отбоя; сохранить исходные минуты дневного сна. Производную длительность не переносить как первичный факт. Существующие определения связывать по владельцу/ключу с сохранением UUID; отметки существующих ключей переносить целиком, включая `false` и даты до нынешнего `created_at`. Расчётное начало определяется согласованным Q2. Прежние жизненные циклы не реконструировать.
4. Отдельно посчитать и исключить только бесхозные отметки без определения у того же владельца. Эта очистка не удаляет сон, определения существующих привычек или строки дня целиком. Некорректные исходные значения и коллизии целевых ограничений не исправлять догадкой и не молча пропускать: остановить переход до разбора.
5. До переключения сверить исходные и целевые данные в обе стороны: владельца, дату, идентичность привычки и boolean каждой сохраняемой отметки; исходные даты/часы и минуты сна; определения и их соответствие идентификаторам. Проверить количества `true`/`false` и бесхозных отметок, уникальность и связи владельцев. Равенства общих количеств недостаточно. Допустимая разница — только заранее посчитанные бесхозные отметки и исключение производных полей; новые расчёты проверяются по принятым правилам, а не равенством старому `/sleep-stats`.
6. После успешной сверки переключить всё чтение и запись на новую модель и открыть запись. Прежние серверные пути записи в JSONB и старую физическую модель отключить; не вести две первичные копии и не возвращаться к старому чтению при ошибке нового. Удаление старых первичных полей/структур допускается только после сверки; резервная копия не является рабочим источником. Совместимость прежнего HTTP-контракта не требуется.
7. Соблюдать существующее решение [«Репетиция миграции, сброс dev и выпуск в production»](../../database-environments/decisions/05-migration-rehearsal-and-release.md): production исправляется вперёд, автоматического отката БД нет. Прежнее приложение можно вернуть только при совместимости с достигнутой схемой. Восстановление резервной копии — отдельное согласованное действие пользователя. После появления новых записей простое восстановление старой копии не допускается: оно потеряет изменения. При сбое снова остановить запись и исправлять новую модель; обратный перенос допустим только отдельной проверенной процедурой, сохраняющей все принятые новые записи.

## Первый раунд — история предложений

**Q1 — Способ переключения.** Допустима ли запланированная пауза записи на время переноса и сверки с последующим обязательным обновлением старых клиентов? Рекомендация — да: остановить запись и дождаться начатых операций, перенести и проверить данные, включить новые чтение/запись с одним первичным источником; прежние изменяющие операции после переключения отклонять явно. Поддержка непрерывной работы старых версий потребует отдельного совместимого перехода. Длительность паузы определить репетицией на копии данных, сейчас её не обещать.

**Q2 — Расчётная граница прежней привычки.** Пример: нынешнее определение создано 20 сентября, но под его ключом сохранены отметки с 1 мая. Как считать полноту учёта, сохранив всю историю? Рекомендация — для перенесённой привычки принять условное расчётное начало как более раннюю из календарной даты сохранённого `created_at` без пересчёта часового пояса и первой сохраняемой отметки. В примере — 1 мая; до границы — «до создания», с границы — календарный знаменатель, включая пропуски. Это приближение для старой истории, не восстановленная дата создания; исходный timestamp сохранить отдельно. Если timestamp отсутствует или некорректен и нет отметок, граница неизвестна: не назначать дату миграции, полноту учёта не вычислять до отдельного правила. Альтернатива — для прежних привычек с недостоверной границей вообще не рассчитывать полноту учёта, сохраняя отметки и процент успеха. Для новых привычек записывать точную календарную дату создания с устройства; периоды активности не вводятся.

**Q3 — Изменения во время подтверждения удаления.** Если показано «Удалить привычку и все 243 отметки?», а до подтверждения на другом устройстве появились новые отметки или изменилось название, удалять ли актуальную историю сразу? Рекомендация — при изменении подтверждаемой привычки или её отметок ничего не удалять, обновить подтверждение и запросить его повторно. При отсутствии изменений определение и все отметки удаляются одной атомарной операцией, после успеха обновляется кэш. Это уточнение конкурентного случая; обычный путь сохраняет одно подтверждение.
