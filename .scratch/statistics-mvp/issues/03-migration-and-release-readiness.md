# 03: Перенос прежних данных и подготовка общего выпуска

**What to build:** Пользователь получает подготовленный единый production-переход на полностью готовую статистику: миграции сна и привычек из первых двух тикетов отрепетированы вместе со сверкой сохранности, скорость подтверждена на dev, выпуск останавливается при ошибке сверки или схемы и подготовлен согласованный порядок действий.

**Blocked by:** 01 — Статистика сна целиком; 02 — Статистика привычек и управление их историей

**Status:** awaiting-human-review

- [x] На постоянной dev-БД существующим контуром репетиции проверен весь переход со старой схемы и совместимых синтетических данных к окончательной модели. Используются миграция сна из задачи «Статистика сна целиком» и миграция привычек с согласованной очисткой из задачи «Статистика привычек и управление их историей», без повторной реализации преобразователей. Копирование production в dev не требуется.
- [x] Общая репетиция подтверждает правила сохранности обоих функциональных тикетов: полные местные дата/часы и минуты сна, владельцев, даты, UUID привычек, все true/false существующих ключей, расчётные старые границы и сохранённые исходные timestamp. Допустимы только согласованная очистка бесхозных отметок и исключение производных полей; совпадение агрегатов со старой сводкой не требуется.
- [x] В полной последовательности подтверждена автоматическая сверка в обе стороны при каждом переносе до удаления соответствующего источника. Проверяются значения и идентичность, дополнительно количества, уникальность и принадлежность. Некорректные значения, коллизии и расхождения останавливают переход; ничего не исправляется догадкой и не пропускается молча. Для этой проверки не требуется сохранять устаревающую рабочую копию данных после успешного функционального перехода.
- [x] Оставшиеся после функциональных переходов прежние поля/структуры удалены после соответствующей сверки, старые пути записи отключены. Всё рабочее чтение и запись используют новую модель без двух рабочих копий и fallback к старым данным. Финальная очистка не уничтожает перенесённые данные или новые записи, сделанные после первых двух тикетов.
- [x] Повторный запуск мигратора не меняет уже перенесённые данные и журнал применённых миграций; зарегистрированные миграции пропускаются. На dev проверены ожидаемая итоговая схема, чтение и запись нового API и продолжение после ошибки с учётом отдельной транзакции на каждую миграцию.
- [x] Перенос и сверка встроены в существующий production Pre-Deploy. Любое расхождение завершает его ненулевым кодом и не допускает запуска нового API. Перед готовностью к обслуживанию API проверяет ожидаемую схему; успешный HTTP healthcheck сам по себе не заменяет эту проверку. Поведение отказа проверено на dev без production-действий.
- [x] После переноса на dev подтверждены исходные дни, средние всех масштабов, архив/возврат/удаление, новые записи и их отображение в статистике. Пройдены автоматические проверки сохранности и небольшой сквозной браузерный набор на настоящих dev-web, API и PostgreSQL; перед ним завершены остальные необходимые проверки по порядку завершения задачи.
- [x] Длинная прокрутка на синтетической истории до десяти лет сохраняет ограниченные DOM и кэш; возврат в выгруженный блок вызывает повторную загрузку без скачка даты. На мобильной ширине проверен вид таблицы, закреплённые названия и отсутствие горизонтального переполнения страницы; ручной проход на dev имеет отдельную визуальную/исследовательскую цель.
- [x] Для обычных и предельных окон каждого масштаба полный ответ прогретого API укладывается в 1 секунду минимум в 19 из 20 последовательных повторов одного профиля в сопоставимом окружении/сети. Проверены синтетика со 100 привычками и доступная реальная история; холодный запрос измерен отдельно. Реальные данные и секреты в результаты не переносятся. Разработчик проверяет dev; проверка production после выпуска остаётся за пользователем.
- [x] Зафиксированы условия и результаты измерений: общее время, SQL и CPU расчётов, байты ответа и отображение таблицы. SQL не растёт на один запрос на день/отметку; дополнительные бюджеты объёма основаны на измерениях и не вводят скрытый предел числа привычек. Если подходящей реальной истории на dev нет, это явно указано, а её проверка не объявлена выполненной и не заменяется самовольным тестированием production.
- [x] Подготовлен порядок одного выпуска всего MVP: успешная dev-репетиция → пользователь вручную останавливает API → подтверждается завершение транзакций и отсутствие писателей → пользователь делает резервную копию → пользователь вливает проверенные изменения в master → Railway выполняет обычный автодеплой с включённой автоматикой. До остановки и готовности копии несовместимые изменения не попадают в подключённую ветку; другого ожидающего или выполняющегося выпуска нет.
- [ ] Инструкция содержит обязательное напоминание перед merge: «API остановлен. Перед слиянием коммита сделай резервную копию production-БД Neon и подтверди, что она готова». В production выпускаются те же проверенные SQL; CI итогового commit, сборка, перенос/сверка и запуск входят в паузу. Длительность SQL/сверки оценена по репетиции; 10–15 минут не объявлены гарантией или пределом.
- [x] Описан отказ с сохранением остановленного API, проверкой фактического состояния и исправлением вперёд после dev-проверки. Автоматического отката всей цепочки нет; возврат старого приложения допустим только при совместимой схеме. Восстановление резервной копии выполняет пользователь отдельно, с учётом возможных новых записей после открытия API.

## Граница подготовки и фактического выпуска

В этом тикете выполняются общая репетиция уже реализованных миграций, итоговая проверка сохранности, удаление оставшихся старых структур и необходимые проверки готовности выпуска. Он завершает подготовку всей доработки к одному production-выпуску. После первого тикета пользователь уже может локально проверить прежнюю историю сна на существующей dev-базе, после второго — привычки на той же базе. Здесь дополнительно проверяется путь от прежней схемы к окончательному результату целиком.

Полная репетиция использует предусмотренную существующим контуром подготовку старой схемы с совместимыми синтетическими данными. Это отдельная проверка выпуска, а не обязательная замена dev-истории синтетикой для демонстрации каждого функционального блока. Данные сна и привычек не переносятся заново поверх изменённого dev-состояния из устаревшей копии. Для production используется та же проверенная последовательность SQL; отдельного временного пути переноса или совместимого промежуточного релиза нет.

Изменения production-БД, остановка сервиса, резервное копирование и merge не выполняются автоматически как часть реализации этого тикета. Их проводит пользователь по согласованной инструкции. Пауза заканчивается, когда готовый новый API получает публичный трафик; последующая проверка приложения в production — ответственность пользователя. Обновление клиентов/PWA, обратная совместимость и специальные экраны паузы вне scope.

При реализации использовать действующий контур мигратора и проверок. Общий набор тестов не переписывается ради новой инфраструктуры; адресные проверки функциональных блоков дополняются общей репетицией и итоговой проверкой интеграции. Существующие SQL, уже применённые к БД, не редактируются ради удобства переноса.
