Исследование завершено в обозначенных пределах: физические замеры существующей БД, воспроизводимая синтетика Node и принципы проектирования. Это техническая рекомендация для обсуждения; окончательный выбор хранения и API остаётся открытым, миграция не выполняется. Применён навык `research`; работу выполнял фоновый агент, синтетические измерения — второй агент, READ ONLY БД — root.

**Последующее уточнение модели 2026-10-10:** пользователь разделил архивирование и окончательное удаление, потребовал очистить прежние бесхозные отметки и запретил вводить периоды активности. Дни в архиве не исключаются из расчётов. Ниже сохранены результаты исследования на прежних предпосылках; проверки включительных интервалов в синтетическом стенде не являются проверкой окончательной семантики архива. Рекомендация типизированного сна и отдельных отметок сохраняет силу по указанным проектным основаниям, но таблицы интервалов активности не требуются. Актуальные правила — в [«Правила периодов и расчётов сна и привычек»](../decisions/03-period-and-metric-rules.md) и [«Хранение, API и обновление статистики для MVP»](../decisions/05-storage-and-api-decision.md).

**Рекомендация:** выбрать целевой формат с типизированными первичными данными сна и отдельными строками отметок привычек, устойчивой идентичностью и архивом определений. Основание — ограничения целостности, принадлежность пользователю, независимые обновления и предсказуемая работа при росте привычек. Измерения не установили JSONB как текущий bottleneck и не доказывают ускорения этой миграции. Подтверждённое ускорение текущего алгоритма обеспечивают устранение N+1, подготовка дат один раз и ограничение объёма; новые физические поля не заменяют эти изменения. Предварительные агрегаты сейчас не вводить. Подробности и цена перехода — в выводе ниже.

## Что сравниваем

Три независимых решения: **формат первичных данных**, **место вычисления агрегатов**, **объём передаваемых и удерживаемых данных**. Из типизированных колонок не следует обязательная SQL-агрегация; SQL может агрегировать существующие JSONB; предварительные агрегаты можно добавить к любой схеме. Виртуализация таблицы решает отдельную задачу DOM. Поэтому сравнение «JSONB или быстрый SQL» создаёт ложную развилку.

Новый MVP не равен ускорению старого `/sleep-stats`: календарные периоды, отдельный дневной сон, привычки и независимые выборки показателей уже приняты. Старый сервис использует скользящие периоды и один фильтр полностью заполненных строк. Он загружает всю историю и выполняет отдельный запрос предыдущего дня для каждой строки. Источники: [контракт](../../../packages/api-contract/main.tsp), `SleepStats` и `SleepStatsPeriod`, строки 153–195; [сервис статистики](../../../apps/api/src/services/sleep-stats.service.ts), строки 22–84; [чтение дней](../../../apps/api/src/services/sleep-records.service.ts), строки 82–126.

Обозначения: D — календарные дни исходного диапазона, M — существующие отметки привычек в нём, H — строки привычек, P — выходные колонки периодов. Линейное чтение дней и отметок — O(D + M). Плотная матрица всех дней и всех привычек — O(D × H), даже если отметок мало. За десять лет около 3652 календарных дней; при 200 привычках это около 730 тысяч потенциальных ячеек. Это арифметика модели, а не замер времени или фактический объём аккаунта.

## Сравнение вариантов

| Вариант | Что устраняет и что остаётся | Цена и состояние доказательств |
| --- | --- | --- |
| Ограниченный JSONB → расчёт API | Убирает N+1; позволяет один проход дней и отметок; остаются передача исходного JSON из БД, декодирование и вычисления Node | Изменение запросов/алгоритма без переноса сна и отметок; будущий архив определений всё равно требует изменений. Проверять время, байты и память, особенно для лет |
| JSONB → точный self-join и агрегаты SQL | Убирает N+1 и может уменьшить передачу БД→API до P × H; остаются извлечение JSON, приведение типов и обработка M на БД | Миграция хранения не обязательна; нужны проверки новой семантики и планов, а не обещание ускорения по месту выполнения |
| Типизированный сон + отдельные отметки | Убирает повторные преобразования JSON для сна, позволяет декларативные ограничения и независимую запись отметки; остаются чтение диапазона, группировка и отдача результата | Перенос данных и контрактов; стабильная идентичность/архив и политика старых отметок обязательны. Скорость этой схемы без сопоставимого БД-стенда не доказана |
| Предварительные суммы/счётчики | Уменьшает повторное сканирование длинной истории при чтении; добавляет стоимость записи и восстановления согласованности | Нужно инвалидировать d+1, текущие периоды, архив и версии расчёта. Пока сравнивать как следующий этап, а не исходное решение |

### Ограниченный JSONB и расчёт API

В нынешней схеме есть PK `(user_id, date)` и B-tree индекс этих полей. Для равенства по пользователю и диапазона даты такая последовательность соответствует правилам использования многоколоночного B-tree. GIN предназначен для поиска внутри JSONB и не заменяет индекс диапазона пользователя/даты. [Миграция 002](../../../apps/api/src/db/migrations/002_create_habits_and_daily_entries.sql), строки 13–26; [миграция 003](../../../apps/api/src/db/migrations/003_fix_daily_entries_primary_key.sql); [PostgreSQL: Multicolumn Indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html), [JSONB indexing](https://www.postgresql.org/docs/current/datatype-json.html#JSON-INDEXING).

Кандидат: одна выборка ограниченного диапазона плюс d−1, индекс строк по дате и один проход. Не использовать Day.js внутри вложенного обхода всех периодов и привычек; один раз подготовить минуты времени и календарные ключи. Для привычек пройти существующие отметки и группировать по стабильному идентификатору; сроки активности пересекать с периодами арифметикой дат. Полный календарь нужен в ответе для дневных колонок, но пустые строки БД сохранять ради него не надо. Это вывод из требуемого результата и нынешнего кода, а не особенность JSONB.

PostgreSQL допускает совместное использование JSONB и обычных колонок. JSONB уже хранится в разобранном бинарном виде, поэтому его не следует путать с повторным разбором текстового `json` внутри PostgreSQL. Однако обновление документа блокирует целую строку. Для большого массива независимых отметок это существеннее, чем для четырёх полей сна. [PostgreSQL: JSON Types](https://www.postgresql.org/docs/current/datatype-json.html#JSON-DOC-DESIGN).

Большие значения могут сжиматься или выноситься через TOAST. Поэтому длина JSON-ответа, размер колонок БД и реальный размер отношений с индексами — разные показатели; экономию хранения нельзя выводить только из `JSON.stringify`. [PostgreSQL: TOAST](https://www.postgresql.org/docs/current/storage-toast.html).

### Выборка и агрегация SQL без смены схемы

Точное соединение — `previous.user_id = current.user_id AND previous.date = current.date − 1 календарный день`. Существующая строковая дата требует аккуратного приведения/формирования границы: для диапазонного фильтра не оборачивать индексируемую колонку без необходимости функцией. Альтернатива — `lag`, но он берёт предыдущую строку, а не обязательно соседнюю дату; использовать только с проверкой разницы дат либо после построения непрерывного календаря. [PostgreSQL: joins](https://www.postgresql.org/docs/current/queries-table-expressions.html#QUERIES-JOIN), [Window Functions](https://www.postgresql.org/docs/current/functions-window.html).

JSONB-массив отметок можно развернуть через `jsonb_to_recordset` или `jsonb_array_elements`, а затем сгруппировать. Это не даёт отдельной уникальности `(user, date, habit)` исходным элементам; дубликаты требуют проверки входных данных. [PostgreSQL: JSON Functions](https://www.postgresql.org/docs/current/functions-json.html). Нынешняя запись заменяет первый найденный объект, а существующие дубликаты сама не устраняет: [updateHabitValue](../../../apps/api/src/services/sleep-records.service.ts), строки 354–360.

Сон агрегировать отдельно от развернутых отметок: join «день × отметки» иначе повторит минуты сна по числу привычек. Каждый показатель сна имеет свой count. Для привычек хранить/отдавать `trueCount`, `falseCount`, `eligibleDayCount`; временный процент получать из них, а не сохранять как первичный факт. SQL `avg` игнорирует NULL; `sum` пустой выборки даёт NULL, поэтому ноль дневного сна требует явного `coalesce` и календарного знаменателя. [PostgreSQL: Aggregate Functions](https://www.postgresql.org/docs/current/functions-aggregate.html). `FILTER` позволяет отдельные выборки счётчиков. [PostgreSQL: aggregate expressions](https://www.postgresql.org/docs/current/sql-expressions.html#SYNTAX-AGGREGATES).

Для месяцев и лет не обязательно строить промежуточное произведение D × H: считаем отметки M и длительность пересечения активности с календарным периодом, затем собираем выход P × H. `generate_series` допустим для календаря дней/периодов; его наличие не оправдывает материализацию всех пустых отметок. [PostgreSQL: Set Returning Functions](https://www.postgresql.org/docs/current/functions-srf.html).

Возможный компромисс: SQL извлекает первичные значения/соединяет точный соседний день или возвращает неокруглённые суммы и counts; единый модуль API выводит средние и процент. Дневной и агрегированный пути должны опираться на одни определения наблюдения. Нельзя оставить старую duration/ночную шкалу на одном пути и новую логику на другом. Решение о единственном месте канонического расчёта фиксировать до реализации.

Особенность переноса duration: нынешний `dayjs(timestamp)` интерпретирует введённые местные строки в зоне процесса, а `diff` считает разницу временных точек, включая DST этой зоны. Вычитание двух SQL `timestamp without time zone` даёт разность местных часов; это не автоматически тот же результат. SQL-кандидат должен воспроизвести нынешнюю семантику и wrap/clamp либо получить отдельное согласование её изменения. Устройство пользователя не передаёт offset, поэтому нельзя выдумать часовой пояс каждой исторической ночи. [Текущий datetime.ts](../../../apps/api/src/utils/datetime.ts), строки 46–66; [PostgreSQL: date/time operators](https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-TABLE).

### Типизированный сон и нормализованные отметки

Кандидат сна: календарный `date`, nullable местные `bedtime`/`wake_time` как `timestamp without time zone`, nullable целые минуты дневного сна; не превращать часы автоматически в UTC. Нынешний контракт содержит полную местную дату и время, а длительность учитывает разность дат. Перенос в одно `time` без даты может изменить семантику и не доказан допустимым. PostgreSQL различает `date`, `time`, timestamp с зоной и без неё. [Текущий контракт](../../../packages/api-contract/main.tsp), строки 100–115; [расчёт длительности](../../../apps/api/src/utils/datetime.ts), строки 37–66; [PostgreSQL: Date/Time Types](https://www.postgresql.org/docs/current/datatype-datetime.html).

Кандидат отметок: одна строка `(user_id, date, habit_id, value boolean NOT NULL)` только для явного ответа. Отсутствие строки означает «не отмечено», `false` сохраняется отдельно. PK/UNIQUE гарантирует одну отметку на привычку в день; составной FK должен гарантировать и принадлежность определения пользователю. Архивировать определения, не каскадно удалять отметки. PK/UNIQUE автоматически создаёт индекс, FK на стороне ссылающихся строк сам по себе индекс не создаёт; дополнительные индексы выбирать по фактическим диапазонам. [PostgreSQL: Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).

Нынешняя запись отметки читает JSONB, меняет массив и заменяет также `sleep_data` последующим upsert без транзакции или `FOR UPDATE`. Два параллельных изменения способны затереть данные, прочитанные до другого изменения. Это вывод из кода, не подтверждённый production-инцидент: [sleep-records.service.ts](../../../apps/api/src/services/sleep-records.service.ts), строки 329–392. Отдельная строка отметки и upsert по её ключу убирают этот конкретный конфликт между разными привычками; атомарное изменение JSONB/блокировка строки также могут его исправить без нормализации. Сам MVCC не превращает последовательность чтение→замена в объединение изменений. [PostgreSQL: MVCC introduction](https://www.postgresql.org/docs/current/mvcc-intro.html).

Архив и устойчивый идентификатор нужны при любом формате отметок. Уже есть UUID определения, но текущий API выдаёт key, полученный из названия, а DELETE физически удаляет определение. Нормализация не восстановит потерянные названия или отдельные жизненные циклы старого key. [HabitsService](../../../apps/api/src/services/habits.service.ts), строки 35–51 и 94–105; [схема](../../../apps/api/src/db/migrations/002_create_habits_and_daily_entries.sql), строки 1–8; [вопросы перехода](../decisions/05-storage-and-api-decision.md).

Типы и ограничения дают основания для рефакторинга корректности и независимых записей. Они не доказывают, что таблица M узких строк займёт меньше места, чем сжатый JSONB в D строках: стоимость заголовков строк, UUID/FK и индексов может перекрыть сокращение повторяющихся JSON-ключей. Сравнивать отношения вместе с индексами на одинаковом распределении и длине идентификаторов, а не только сериализацию в Node. [PostgreSQL: page layout](https://www.postgresql.org/docs/current/storage-page-layout.html), [TOAST](https://www.postgresql.org/docs/current/storage-toast.html).

### Предварительные агрегаты

Материализованное представление хранит результаты и может отдавать старые данные до обновления. `REFRESH MATERIALIZED VIEW` заменяет содержимое; вариант `CONCURRENTLY` требует подходящего уникального индекса. Это не готовый механизм инкрементального пересчёта двух затронутых дней. [PostgreSQL: Materialized Views](https://www.postgresql.org/docs/current/rules-materializedviews.html), [REFRESH MATERIALIZED VIEW](https://www.postgresql.org/docs/current/sql-refreshmaterializedview.html).

Собственные таблицы сумм/счётчиков потребуют атомарного изменения/пересчёта d и d+1 после отбоя, пересечений активности, восстановления после сбоя и версии алгоритма. Нельзя хранить только округлённые средние/проценты. Полноту и знаменатель дневного сна можно вычислять из календарного диапазона; сохранённое «сегодня» устаревает без мутации пользователя. Если измерения покажут дорогой многолетний пересчёт, месячные суммы/счётчики можно сворачивать в годы; недели пересекают месяцы и требуют собственного пути или исходных дней. Это проектный вывод из [правил 03](../decisions/03-period-and-metric-rules.md), а не готовое решение PostgreSQL.

## Корректность обязательна для любого сравнения

Эквивалентность проверяется по новым правилам, а не только `deepEqual` прежнему `/sleep-stats`:

- Календарные недели с понедельника, месяцы/годы; конец вычисления задаёт местная дата клиента, без будущих наблюдений. Начало истории согласовано: ранняя дата содержательного сна, отметки или известной активности; пустая строка БД не задаёт начало. Первый агрегированный период разворачивается целиком. [Решение 05](../decisions/05-storage-and-api-decision.md), «Согласованные части».
- Ночь относится к дате подъёма. Отбой d−1 нужен для первой длительности; дырка в календаре не соединяется с предыдущей существующей строкой. Отбой d и его очистка меняют длительность d+1 даже на границе года. [Правила 03](../decisions/03-period-and-metric-rules.md), «Периоды и даты»; [текущий расчёт](../../../apps/api/src/utils/datetime.ts), строки 37–66.
- Отбой, подъём и общая длительность имеют независимые counts. Пустая длительность — NULL, не 0. Ночной отбой разворачивается около полуночи; подъём — обычное арифметическое среднее. Дневной сон делится на календарные дни рассматриваемого периода, включая отсутствующие строки; полностью пустой прошедший период даёт 0. [Правила 03](../decisions/03-period-and-metric-rules.md), «Сон».
- Не усреднять округлённые средние. 1/1 и 0/9 дают вместе 10%, а не 50%. Успех привычки при отсутствии true и false — NULL; eligibleDays считает пересечение периода с активностью от создания до удаления включительно. До/после активности отдельное «н/а». Переименование сохраняет историю, архив сохраняет последнее имя, повторное создание начинает новую. [Правила 03](../decisions/03-period-and-metric-rules.md), «Привычки».
- Нынешняя сохранённая duration не является надёжным первичным фактом: очистка bedtime не обновляет следующую строку. Все сравниваемые новые пути рассчитывают её из первичных времени и дневного сна либо доказывают согласованность производного поля при всех мутациях. [upsertSleepRecord](../../../apps/api/src/services/sleep-records.service.ts), строки 206–234.

## Виртуализация, ответ API и память клиента

Текущий макет строит всю историю и все ячейки, затем заменяет `innerHTML`; это макет поведения, не реализация виртуализации. [table-navigation.html](../prototype/table-navigation.html), `render`, строки 158–187. У пользователя уже приняты нативная непрерывная прокрутка, колонки 3 rem, закреплённые названия и обязательная виртуализация. [Решения 04](../decisions/04-table-navigation-prototype.md) и [05](../decisions/05-storage-and-api-decision.md).

TanStack Virtual поддерживает горизонтальную ось и виртуализацию сетки. Кандидат: логическое число всех доступных колонок и их фиксированная ширина, DOM только видимого диапазона плюс overscan. Названия строк остаются закреплёнными; смена масштаба/подгрузка сохраняет ориентир даты. При H=200 горизонтальная виртуализация оставляет около 200 × видимые колонки ячеек; если этого недостаточно, отдельно измерять вертикальную виртуализацию, а не заранее вводить её как требование. [TanStack Virtual: Introduction](https://tanstack.com/virtual/latest/docs/introduction).

Отдельно ограничивать:

| Слой | Кандидат ограничения | Что проверять |
| --- | --- | --- |
| БД→API | Исходные календарные дни, M отметок и выбранные поля; SQL-агрегаты могут сократить результат | SQL-время, байты, rows, RSS/heap API |
| API→клиент | P колонок и H строк; агрегаты для недель/месяцев/лет, sparse marks для дней | Размер сериализованного/сжатого ответа, декодирование |
| DOM | Видимые колонки + ограниченный overscan | Число элементов и плавность прокрутки |
| Память клиента | Ограниченное число окон/байтов по всем масштабам и диапазонам; удаление дальних данных | Heap после длинной прогулки назад/вперёд и смен масштабов |

Ограничение P не ограничивает D: окно десяти годовых колонок требует около десяти лет исходной истории. Одного `gcTime` недостаточно для постоянно активного бесконечного запроса. `maxPages` у TanStack Query ограничивает страницы infinite query, при загрузке в одну сторону удаляется противоположная; для возврата в обе стороны нужны оба вычисления page parameter. Фиксированные `useQuery`-окна с явным удалением дальних диапазонов — альтернатива. [TanStack Query: infinite query options](https://tanstack.com/query/latest/docs/framework/react/reference/interfaces/InfiniteQueryObserverOptions), свойства `gcTime`, `maxPages` и page parameters; направление удаления дополнительно проверено в установленном `@tanstack/query-core@5.104.0`, `src/infiniteQueryBehavior.ts`, строки 73–84.

Выкидывание данных не должно уменьшать логическую ширину всей истории или сдвигать scrollLeft: далёкие колонки остаются логическими позициями/заполнителями и загружаются повторно при возвращении. Ошибка загрузки — отдельное состояние, а не пустой полученный день с нулём дневного сна. Prefetch соседнего диапазона входит в тот же бюджет памяти. Это вывод из согласованного непрерывного скроллинга и ограничений данных.

Пользовательский scope, календарная дата среза и масштаб входят в ключ ответа. После успешной мутации инвалидировать prefix статистики пользователя; после смены аккаунта отменять запросы и очищать приватный кэш. У существующего QueryClient настройки по умолчанию, выход удаляет только токен, текущие мутации не инвалидируют статистику. [QueryClient](../../../apps/web/src/shared/api/query-client.ts), [session](../../../apps/web/src/shared/model/session.ts), строки 32–40; [мутации дня](../../../apps/web/src/features/main/model/use-sleep-records.ts), строки 124–205; [мутации определения](../../../apps/web/src/features/main/model/use-habits.ts), строки 10–29.

## Итоговая техническая рекомендация

Для целевой модели **рекомендованы типизированные данные сна и нормализованные отметки**. Пользователь разрешил оценивать рефакторинг и по общей логике API/БД. Здесь измерения показывают стоимость, а доменная модель определяет границы атомарного изменения и ограничения. Это вывод исследования для последующего обсуждения, не уже принятое пользователем решение о миграции.

1. **Первичные данные сна — типизированные поля записи дня.** `date DATE`, местные nullable timestamp отбоя/подъёма без автоматического UTC-пересчёта, целые минуты дневного сна с согласованными CHECK. Это фиксированная небольшая структура из контракта, а не произвольный документ. Типы позволяют БД отвергать несуществующие календарные даты и неверные типы; сон по-прежнему относится к прежним датам. Правило диапазона минут сначала согласуется с реальным вводом: не добавлять молча новый предел, которого нынешний API не гарантирует. Сохранённую duration не считать первичным фактом и не копировать её вслепую при переносе. Измеренный `pg_column_size` и схема не обещают итоговую экономию отношения.
2. **Явная отметка — собственная строка, отсутствие ответа — отсутствие строки.** Уникальность `(user_id, date, habit_id)` предотвращает дубликаты; FK с проверкой владельца предотвращает чужие/несуществующие определения для новых отметок; upsert одной строки не заменяет сон и все отметки дня. Это соответствует независимой изменяемости отметок и устраняет описанный риск read→replace. Индексы `(user_id, date, habit_id)` и, при измеренной необходимости, `(user_id, habit_id, date)` обслуживают разные направления истории; не создавать оба автоматически без проверки. Stable ID остаётся устойчивым при переименовании; последний label и календарные activeFrom/activeThrough сохраняются архивом. Эти преимущества целостности не сводятся к миллисекундам SELECT. [Глоссарий](../../../GLOSSARY.md); [PostgreSQL: constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).
3. **HTTP остаётся независим от физической схемы.** Один диапазонный контракт возвращает дневные состояния или агрегированные колонки и границы фактически рассчитанного периода. Отсутствие наблюдения и «вне активности» — состояния полученных данных; загрузка/ошибка ещё не полученного окна принадлежат транспорту и клиенту, а не успешному бизнес-ответу API. Пользователь определяется авторизацией. Лимиты ограничивают исходные дни/отметки, число выходных колонок и размер ответа; список привычек/метаданных не повторяется в каждой ячейке. Клиент форматирует и виртуализирует; канонические правила и неокруглённые счётчики принадлежат серверной стороне, без клиентского дублирования процентов/средних. Это позволяет сменить SQL-план или хранение без изменения навигации.
4. **Начать с вычисления по первичным значениям без сохранённых агрегатов.** Для ограниченного дневного окна — фиксированное число запросов и точный сосед d−1; для агрегатов — подготовка значений и один проход, используя измеренный кандидат из Node-стенда. При слишком большом объёме БД→API SQL-проекция/суммы/counts — обоснованный следующий кандидат: READ ONLY тест уже показал сокращение байтов. При переносе части вычислений в SQL единый набор семантических сценариев проверяет точную эквивалентность, включая DST, wrap/clamp и пустой календарь; не поддерживать независимо две расходящиеся бизнес-формулы. Поскольку текущий SQL CPU мал, заранее переносить все вычисления в SQL или вводить materialized views ради обещанной скорости не нужно.
5. **Обновление и память входят в архитектуру сразу.** Изменение/очистка отбоя d инвалидирует d и длительность d+1, текущие агрегаты обновляются при смене локального дня; определения/архив инвалидируют историю и метаданные. Для MVP общий user prefix допустим. Виртуализированный DOM и ограниченный кэш — два разных механизма, оба сохраняют логическую ширину истории и выбранную дату. Неполученные данные не превращаются в известные нули.

Дневной JSONB с атомарными обновлениями и проверками остаётся работоспособной альтернативой с меньшей ценой перехода. Приоритет одной только минимальной переделки сделал бы его разумным выбором. Для заданных пользователем критериев целостности, роста и готовности к рефакторингу отдельные отметки дают более ясную единицу записи; типизированный сон закрепляет уже устойчивую структуру. Это причина рекомендации целевой схемы, а не попытка приписать ей непроверенную скорость. Нормализация может увеличить число строк и индексов и не обязана экономить дисковое место.

### Цена перехода и граница изменения поведения

- Новые таблицы/колонки и constraints, перенос валидных первичных значений, перевод mutation/read-путей, TypeSpec и generated artifacts, runtime-схемы, регрессионные HTTP-проверки. Во время перехода обеспечить единственный authoritative write path или атомарное dual-write с явным окончанием; бессрочные две копии первичных данных запрещены проектной рекомендацией, иначе появляются расхождения.
- Проверить старые даты/времена и дубликаты до включения строгих ограничений. Неприемлемые строки и утраченную идентичность нельзя исправлять догадкой. Формат legacy-сохранения и отображения остаётся вопросом пользователя Q2. FK для достоверных новых отметок не должен заставлять выдумывать архивное определение, название или даты активности для прежнего неизвестного key.
- Перенос сохраняет введённые календарные дату и часы, связь ночи с днём подъёма, семантику текущей duration/DST; не «чинит» историю сменой зоны. Проверенные native Date компоненты — исследовательский кандидат только для валидных минутных строк, не разрешение заменить helpers без проверок.
- Контроль переноса: исходные mark counts и true/false по пользователю/дате/идентичности, отсутствие удаления исходных сведений, сравнение новых вычисленных значений по golden cases и выборкам, подготовленный обратимый rollout. Публичный ключ может оставаться совместимым непрозрачным ID; физический UUID не обязан становиться пользовательским параметром.

Проверка альтернативной физической схемы предпринималась: в `/opt/homebrew/Cellar/libpq/18.4/bin` найдены клиентские инструменты, включая `initdb/pg_ctl`, вне PATH, но нативный сервер `postgres` не найден. Docker установлен, но backend не запущен. Новый сервер, контейнер или WASM-PostgreSQL не устанавливался для этого необязательного расширения. Поэтому здесь нет сопоставимого замера диска/индексов/SQL/WAL новой нормализованной схемы; рекомендация основана на её явных свойствах проектирования и измеренных границах текущих путей. CPU-выигрыш, нагрузка записи, дисковый объём и HTTP новой схемы должны быть измерены в ходе реализации; решение по архитектуре не блокируется отсутствием такого стенда.

До определения SLA выполнить сопоставимые HTTP-замеры первого и повторных запросов, предельных диапазонов каждого масштаба, небольшого/большого H, sparse/dense отметок. Отдельно измерять холодный запуск, SQL, CPU, сериализацию, объём, отображение и длинную прокрутку. Диагностический порог 1000 мс старого отчёта не согласован как критерий нового MVP. Новые публичные поля вводятся через TypeSpec с генерацией, runtime-схемами и HTTP-проверками. [ADR 0002](../../../docs/adr/0002-openapi-api-contract.md).
