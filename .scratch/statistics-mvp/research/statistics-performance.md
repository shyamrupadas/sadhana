# Итоговый замер HTTP статистики на dev

Дата: 2026-10-27. Тикет: [03](../issues/03-migration-and-release-readiness.md).

## Условия и воспроизведение

- Node 24.16.0, macOS arm64, Apple M2. Настоящий API из текущих исходников по loopback HTTP и PostgreSQL проверенной dev-цели. Production не использовался.
- Отдельный синтетический аккаунт: десять лет ежедневного сна, 100 привычек, ежедневные явные true/false; 20 привычек архивные. Во всех запросах включены архивные строки. Это плотная история примерно с 365 тысячами отметок.
- Для каждого масштаба проверены обычное и предельное окна. Для недель, месяцев и лет взяты завершённые календарные периоды; четырёхлетнее окно включает 1461 день. После первого запроса выполняются 20 последовательных повторов с полным чтением HTTP-ответа, без сжатия.
- Первый запрос каждого окна приведён отдельно; это не восемь независимых холодных запусков API/Neon. Первый запрос процесса выполнен после проверки схемы и подготовки данных.
- Скрипт проверяет HTTP 200, количество колонок, четыре SQL-запроса, 100 определений и соответствие числа явных ответов календарной длине каждого периода. Аккаунты записываются в локальный журнал до создания и удаляются после прогона. Следующий запуск очищает аккаунты прерванного процесса.

Команда: `node .scratch/statistics-mvp/research/statistics-http-benchmark.cjs`.

[Скрипт](statistics-http-benchmark.cjs), [обезличенные результаты](statistics-http-results.json). Для запуска нужны существующие локальные dev-настройки и доступ к dev PostgreSQL. Скрипт не сбрасывает схему, не запускает миграции и не изменяет существующие профили.

Подходящей реальной истории на dev не обнаружено: выборка существующего профиля со сном вне синтетического домена `example.test` пуста. Замер реальной истории не выполнен и не заменён обращением к production.

В предельном дневном окне один ответ занял 3894,32 мс; в обычном месячном — 1601,68 мс. Они включены в результаты, а не исключены как выбросы. Условие 19/20 не означает отсутствие медленных ответов.

Число SQL во всех окнах — четыре. Их суммарное время p95: 547,41 мс для максимального дня, 425,60 мс для недели, 356,45 мс для месяца и 574,61 мс для года. Эта величина включает сеть БД→API и разбор ответа драйвером, а не только исполнение внутри PostgreSQL.

CPU расчётов после последнего SQL до возврата сервиса, медиана / p95: день 34,71 / 41,22 мс; неделя 26,31 / 32,90 мс; месяц 16,46 / 20,78 мс; год 13,34 / 20,52 мс. Это измерение CPU процесса; сериализация входит в полное HTTP-время, но не в этот показатель.

Размер наибольшего HTTP-ответа — 749828 байт для 48 дней и 100 привычек. Скрытый предел числа привычек или новый бюджет размера ответа не вводились. Данных недостаточно для ограничения количества привычек; объём ответа уже ограничивается окном.

## Причина изменения запроса

Исходный endpoint делал четыре SQL-запроса, но возвращал в Node.js каждую отметку диапазона. Для 100 привычек за четыре года это до 146100 строк отметок, хотя результату нужны 400 групп привычка/год. Отсутствие N+1 само по себе не ограничивало промежуточный объём.

Первый диагностический прогон показал:

- 24 недели: p95 1697,33 мс, до секунды 16/20;
- 12 месяцев: p95 5993,75 мс, до секунды 0/20;
- один год: p95 1893,05 мс, до секунды 6/20.

После подтверждения проблемы исходный прогон остановлен до завершения самого тяжёлого окна; приведённые значения сохранены из вывода, полного JSON исходного прогона нет. Два замера последовательные, поэтому влияние колебаний сети не исключено.

Запрос теперь группирует отметки по привычке и календарному периоду и возвращает счётчики true/false. Четырёхлетний диапазон даёт 400 строк отметок, а всего четыре SQL возвращают 1963 строки, включая сон, определения и границу истории. Процент успеха, полнота, неизвестное начало, дневные состояния и форма HTTP-ответа остаются в сервисе. Новых сохранённых агрегатов, индексов или миграций нет.

Изменение сокращает объём PostgreSQL→API. Число отметок, обрабатываемых PostgreSQL внутри запрошенного диапазона, не уменьшается; выигрыш не следует трактовать как ускорение каждого отдельного этапа. В дневном масштабе уменьшения количества строк отметок нет.

## Мотивация проверки схемы при запуске

Тикет требует проверять ожидаемую схему до готовности API к обслуживанию. Ранее Pre-Deploy применял миграции, а сервер мог открыть HTTP-порт и отвечать на `GET /` без проверки доступной ему схемы. Такой healthcheck подтверждал работу HTTP-сервера, но не совместимость БД с новой моделью.

Добавлена read-only проверка через runtime-соединение: журнал должен содержать всю текущую цепочку с исходными checksum; типы и обязательность полей таблиц статистики должны совпадать; должны существовать ключевые ограничения уникальности и принадлежности отметок. В числе прочего отвергаются оставшиеся старые поля `sleep_data`, `daily_entries.habits` и `habits.key`.

Рабочие точки запуска включают проверку в Fastify `onReady` до `listen()`. При ошибке сервер закрывается с кодом 1. Проверка не применяет миграции и не исправляет данные. Таймаут получения соединения — 10 секунд; SQL-проверки имеют локальный таймаут 10 секунд. Это отдельные ограничения операций, а не обещание суммарного времени старта.

Мотивация — выполнить условие тикета на том соединении, через которое API обслуживает запросы. Компромисс: старт зависит от доступности БД, а описание ожидаемой схемы нужно обновлять при следующих изменениях модели. Проверка выполняется при старте, не на каждый пользовательский запрос и не при каждом healthcheck. CI smoke с фиктивной недоступной БД теперь ожидает отказ запуска; локальный Docker-прогон не выполнен, поскольку daemon не запущен.

## Границы подтверждения

- Результат относится к локальному API и доступной dev-сети, не к production и не к статистике большой популяции запросов.
- Реальная dev-история недоступна для этого замера; личные значения, адреса и идентификаторы аккаунтов в результаты не записаны.
- Отображение таблицы измерено отдельно, см. ниже. Изменений UI нет; визуальная проверка принята пользователем. Ограниченный DOM, длинная прокрутка и повторная загрузка выгруженного окна дополнительно защищены существующим финальным E2E-сценарием. CPU/память браузера в HTTP-замере не измеряются.
- По уточнению пользователя общая `db:rehearse` уже выполнена и повторно не запускается. Хронометраж SQL/сверки этой репетиции не предоставлен; время production-паузы по HTTP-замеру не оценивается.

## Автоматические E2E

Финальный `pnpm test:e2e` с доступом к dev-БД — 5/5, около 1,1 минуты. Проверены регистрация/вход/выход, сохранение привычек с обновлением статистики и жизненным циклом, сохранение сна и длительная прокрутка с выгрузкой/повторной загрузкой и мобильной шириной. Использовались настоящий API/PostgreSQL и отдельные синтетические аккаунты с очисткой.

Первый запуск в песочнице не смог поднять API; успешный прогон выполнен с разрешённым доступом к dev. После финального E2E выполнен только read-only замер отображения без изменений кода приложения. Повторного функционального исследовательского прохода по уже принятому UI не было.
