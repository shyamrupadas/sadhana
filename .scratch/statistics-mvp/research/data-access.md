# Доступ к истории статистики: исследование для MVP

Дата: 2026-10-09. Контекст: текущая ветка `master`; работа без worktree, изменения приложения и БД не выполнялись. Исследование разрешает билет [«Стратегия доступа к дневной и агрегированной истории»](../decisions/02-data-access-research.md). Открытые доменные варианты ниже отражают состояние на момент исследования; актуальные правила впоследствии согласованы в разделе Answer билета [«Правила периодов и расчётов сна и привычек»](../decisions/03-period-and-metric-rules.md). В частности, пользователь выбрал нули для пустого дневного сна и более простой расчёт среднего времени, сохранил существующее поведение дат и исключил пометку незавершённого периода.

## Вывод

Существующая таблица «одна запись пользователя на дату» подходит для первой версии истории. Устранять следует последовательное чтение предыдущего дня для каждой строки, затем ограничить чтение нужным календарным диапазоном. Первым кандидатом рекомендую один запрос диапазона с дополнительной предыдущей календарной датой и расчёт в API через `Map<date, row>`. Внешние источники не доказывают, что нормализация JSONB или предварительные агрегаты обязательны при текущем объёме. Это техническая рекомендация исследования, а не принятие открытых правил продукта.

## Что установлено в коде и диагностике

- `getAllSleepRecordsForStats` читает все записи пользователя, затем внутри `for` выполняет `await client.query` для каждой предыдущей даты. Количество SQL-запросов — `1 + N`. Та же схема встречается при чтении пяти дней главной страницы. [SleepRecordsService](../../../apps/api/src/services/sleep-records.service.ts).
- `getSleepStats` возвращает три сводки, а не историю. Текущие «неделя» и «месяц» — окна от `now - 7 days` и `now - 30 days`, «год» — предыдущие 12 завершённых месяцев. Это отличается от таблицы календарных периодов. Для всех трёх показателей применяется общий фильтр: текущие bedtime, wakeTime, duration должны быть заполнены и duration > 0. [SleepStatsService](../../../apps/api/src/services/sleep-stats.service.ts).
- Длительность строки `d` вычисляется из отбоя `d−1`, подъёма `d` и дневного сна `d`. При отсутствии предыдущей календарной даты длительность остаётся неизвестной, а не считается от последней существующей записи. Хранимое `sleep_data.duration` при чтении пересчитывается. [Расчёт и календарные функции](../../../apps/api/src/utils/datetime.ts), [контракт SleepData](../../../packages/api-contract/main.tsp).
- В миграциях есть составной PK `(user_id, date)`, `date` хранится как `varchar(10)`, сон и отметки — JSONB. Рядом существуют дополнительные индексы. Их реальную избыточность следует проверять по каталогу БД отдельно; исследование не предлагает удалять их. [Создание таблиц](../../../apps/api/src/db/migrations/002_create_habits_and_daily_entries.sql), [изменение PK](../../../apps/api/src/db/migrations/003_fix_daily_entries_primary_key.sql).

Обезличенные замеры и воспроизведение находятся в отдельном [отчёте о задержке](request-latency.md), разрешающем [«Причина задержки текущей статистики»](../decisions/01-request-latency.md). Они подтверждают N+1 на небольшом наборе данных и сохранение прежнего ответа при поиске соседней даты в памяти. Локальное подключение и production API измеряют разные сетевые пути; скорость законченной production-реализации ещё не измерена. Таблица результатов здесь не дублируется.

## Чтение дней и соседней ночи

Рекомендованный диапазон ответа — `[from, toExclusive)`. Читать `[from−1 day, toExclusive)`, построить карту по календарной дате, вычислить duration и убрать дополнительный день из ответа. Пропуски в карте не заполнять предыдущей существующей записью. SQL для **текущей** схемы без миграции:

```sql
SELECT date, sleep_data, habits
FROM daily_entries
WHERE user_id = $1
  AND date >= $2
  AND date < $3
ORDER BY date ASC;
```

Здесь `$2` — уже вычисленная API дата `from−1` в каноническом формате `YYYY-MM-DD`, `$3` — `toExclusive`. Корректность строкового сравнения предполагает валидные одинаково форматированные даты и подходящую сортировку; TypeSpec проверяет форму строк, но не заменяет проверку календарной валидности. Составной B-tree соответствует равенству по пользователю и диапазону по дате. Не оборачивать индексируемую `date` в `date::date` внутри `WHERE` без отдельного анализа плана. [PostgreSQL: многоколоночные индексы](https://www.postgresql.org/docs/current/indexes-multicolumn.html), [CalendarDate](../../../packages/api-contract/main.tsp).

| Кандидат | Как избежать N+1 | Условия корректности и компромисс |
| --- | --- | --- |
| Диапазон + API-карта | Один запрос, поиск `map.get(d−1)` | Сохраняет существующий расчёт длительности; наиболее простой кандидат для MVP |
| `LEFT JOIN` записи на предыдущий день | Один SQL, `p.user_id=c.user_id` и точная дата `d−1` | Удобная база для последующего SQL GROUP BY; нужно сопоставить расчёт с текущими правилами |
| `lag` | Один SQL с окном | Соседняя строка не означает соседнюю календарную дату; обязательны `lag(date)` и проверка `previousDate=d−1` |

В PostgreSQL `lag` сдвигается на число **строк** в окне. Поэтому для записей 1 и 3 числа нельзя считать длительность 3 числа от отбоя 1 числа. Окно должно включать дополнительный день, а отрезание ответа происходить во внешнем запросе; при `ORDER BY date DESC` предшествующая календарная дата лежит в направлении `lead`, а не `lag`. [PostgreSQL: оконные функции](https://www.postgresql.org/docs/current/functions-window.html).

Для self-join на текущем `varchar` схема условия может быть `p.date = (c.date::date - 1)::text`; каст применяется к текущей строке, а не к индексируемому `p.date`. Это эскиз запроса, не протестированный план. После перехода на `DATE` условие проще: `p.date = c.date - 1`. Календарная арифметика `date - integer` поддерживается PostgreSQL. [PostgreSQL: функции даты и времени](https://www.postgresql.org/docs/current/functions-datetime.html).

Дни без записей должны оставаться различимыми в таблице: API либо возвращает полный календарь с пустыми ячейками, либо отдаёт явно описанный диапазон и sparse rows, а клиент дополняет календарь. Не записывать пустые дни в БД ради просмотра. При SQL-реализации календарь можно создать через `generate_series` и сделать `LEFT JOIN`. [PostgreSQL: генерация последовательностей](https://www.postgresql.org/docs/current/functions-srf.html).

## Периоды и ограниченный API

Рекомендуемый технический эскиз: `GET /statistics?granularity=day|week|month|year&from=...&toExclusive=...`. Название маршрута не принято. Один экран — фиксированное окно календаря; соседние окна вычисляются по датам, без OFFSET по существующим записям. Свайп не должен запускать полную выгрузку истории. Для недель/месяцев/лет API возвращает строки периодов, даже если часть периодов пустая.

До реализации определить допустимые выровненные границы и **два ограничения**: число возвращаемых периодов и число исходных календарных дней. Ограничение только `LIMIT 12` в ответе не ограничивает стоимость обработки 100 лет. В качестве отправной точки, а не согласованных требований: дневной запрос до 62 дней; агрегированный до 60 периодов и до 10 лет исходной истории; видимый экран обычно существенно меньше лимита. Нарушение лимита — ошибка валидации, без тихого усечения полного периода. Предельные числа должны учитывать разрешённый срок хранения истории и замеры.

Описать в ответе `from`, `toExclusive`, `granularity`, `timezone`, границы каждой строки периода, `asOfDate` для текущего неполного периода и сырые числители/знаменатели рядом с отображаемыми значениями. Границы календаря и направление чтения отделить от решения, какой день считается днём ночи. Не использовать «неделя = 7 последних дней», если продукт выбрал календарные недели.

Для SQL-группировки PostgreSQL имеет `date_trunc` по `week/month/year`; ISO-неделя связана с понедельником и может лежать в другом ISO-году, поэтому надёжный ключ строки — дата начала, а не пара «обычный год + номер недели». `date_bin` не поддерживает шаги с месяцами и годами. Часовой пояс требуется определить явно для timestamp-данных; сейчас API использует `Europe/Moscow`. [PostgreSQL: даты и календарные группы](https://www.postgresql.org/docs/current/functions-datetime.html), [текущий сервис](../../../apps/api/src/services/sleep-stats.service.ts).

Любое изменение HTTP-контракта сначала описывается в TypeSpec, затем генерируется установленной командой; generated-файлы не правятся вручную. [ADR «Использовать TypeSpec как единый источник HTTP-контракта»](../../../docs/adr/0002-openapi-api-contract.md).

## Агрегирование без потери смысла

При текущем объёме API может за один запрос читать ограниченные строки и вычислять периоды. Для многолетних окон кандидат — один SQL с exact-date self-join и GROUP BY, чтобы передавать только агрегаты. Скорость SQL-кандидата пока не измерена. Сначала нужно согласовать правила и проверить соответствие расчётов, включая существующий перенос отрицательной длительности на сутки и ограничение 0…1440 минут. [Текущая длительность](../../../apps/api/src/utils/datetime.ts).

Числа для свёртки: `durationSumMinutes`, `durationSampleCount`; для времени — сумма выбранного преобразования и отдельный count; для привычки — trueCount, falseCount и eligibleDayCount. Среднее большего периода — сумма числителей / сумма знаменателей, а не среднее округлённых средних или процентов. Например, одна группа с 1/1 и другая с 0/9 дают 10%, а не 50%. Округлять только результат для отображения. `avg` и `sum` PostgreSQL пропускают SQL NULL; пустые наборы требуют отдельной обработки, count должен считать именно выбранные наблюдения. [PostgreSQL: агрегатные функции](https://www.postgresql.org/docs/current/functions-aggregate.html).

Для сна остаются открытыми два варианта: отдельная выборка валидных значений каждого показателя или только полностью заполненные ночи. Текущий общий фильтр дополнительно требует **отбой текущего дня**, хотя duration относится к отбою предыдущего; это может исключать известную длительность. Сохранить его при диагностическом устранении N+1 можно, но для нового MVP правило надо обсудить отдельно. [SleepStatsService](../../../apps/api/src/services/sleep-stats.service.ts).

## Среднее времени около полуночи

Текущее преобразование прибавляет 24 часа ко всем значениям раньше 12:00. Поэтому 23:50 и 00:10 дают 00:00, но 11:59 и 12:01 также дают 00:00. Второй результат показывает разрыв выбранной шкалы у полудня. Это воспроизводится арифметикой текущей функции и не доказывает, какой альтернативный результат нужен продукту. [calculateAverageTime](../../../apps/api/src/utils/stats.ts).

Варианты для обсуждения:

1. **Развёрнутая шкала относительно фиксированной границы суток.** Сохранять сумму преобразованных минут и count; выбрать границу отдельно для отбоя/подъёма, задокументировать поведение около неё. Фиксированность нужна для объединения агрегатов разных периодов.
2. **Круговое среднее.** `angle=2π*minutes/1440`, накопить `sumSin`, `sumCos`, count, восстановить `atan2(sumSin,sumCos)`. Значения по обе стороны полуночи усредняются непрерывно. При близком к нулю результирующем векторе (например, 00:00 и 12:00) среднее не определяет осмысленного единственного времени; для продукта нужен порог и отсутствие значения, а не случайный час. Формула и случай нулевого вектора описаны в первичной документации SciPy; подключать SciPy к приложению не предлагается. [SciPy: circmean](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.circmean.html).

Ни один вариант не выбран этим исследованием. Также открыть вопрос: время суток усредняется по текущей Москве или по часовому поясу пользователя/события; текущие строки timestamp без offset сами не фиксируют этот выбор.

## Привычки: три состояния и история

Подтверждённое пользователем **временное** правило: `success = trueCount / (trueCount + falseCount)`, отдельно `coverage = markedDays / eligibleDays`. Пример: 4 true, 1 false, 2 не отмечено → успех 80%, полнота 5/7. Для markedDays=0 рекомендовано показывать отсутствие процента, а не 0%; это ещё предстоит подтвердить при обсуждении. False не приравнивается к отсутствующей отметке. Дневной формат использует true/false/не отмечено. Временное правило зафиксировано в [решении о расчётах](../decisions/03-period-and-metric-rules.md), три состояния определены в [GLOSSARY](../../../GLOSSARY.md); это не рекомендация внешнего источника.

В текущих данных отсутствие объекта в `habits` означает «не отмечено»; объект содержит boolean. При SQL-агрегации JSONB-массив можно развернуть в записи, но надо сохранить пустые календарные дни и не считать число строк после join числом eligibleDays. Каждая привычка должна давать не более одной отметки на дату. PostgreSQL даёт функции развёртки JSONB; текущий массив не обеспечивает такую уникальность декларативно. [PostgreSQL: JSON-функции](https://www.postgresql.org/docs/current/functions-json.html), [HabitCheck](../../../packages/api-contract/main.tsp).

**Открытый вопрос знаменателя coverage:** все прошедшие дни периода, дни после создания привычки или дни, когда привычка была активна/запланирована? Текущее created_at не описывает паузы, удаление и повторное создание. Будущие дни и период до появления привычки нельзя автоматически объявлять провалами. При изменении временного правила нужны исходные counts, а не только сохранённый процент.

**Риск идентичности:** создание генерирует key из label; переименование меняет label, сохраняя key. Удаление удаляет строку определения, но JSONB-отметки в daily_entries остаются без label. Повторное создание с тем же key может логически склеить новую привычку с прежней; разные названия также могут давать один key. Это следует из текущего кода, не из предположений о БД. [HabitsService](../../../apps/api/src/services/habits.service.ts), [generateHabitKey](../../../apps/api/src/utils/habit-key.ts).

Варианты решения истории: хранить стабильный habit_id и архив определения с active intervals; сохранять definition/key после удаления с archived_at; либо намеренно показывать только текущие привычки и явно исключать удалённые из MVP. Отдельно выбрать label в прошлом: текущее имя, последнее известное или имя на дату. Последнее потребует истории имён. **Удаление определения не означает разрешение удалить прошлые отметки**; это отдельное решение пользователя. Нормализация отметок без устойчивой идентичности сама по себе эту проблему не решает.

## JSONB, типизированные колонки и агрегаты

| Подход | Основание рассмотреть | Цена и рекомендация сейчас |
| --- | --- | --- |
| Сохранить JSONB | Малые записи по дням; меняющиеся правила | Рекомендованный старт; запросы диапазона и API-агрегаты работают без миграции |
| Сон в типизированных колонках; date как DATE | Проверки календаря и типов, SQL-арифметика, устойчивый контракт | Полезное развитие при измеренной необходимости; не средство устранения 528 round trips |
| Habit marks отдельной таблицей | FK на стабильную привычку, UNIQUE(user,date,habit), независимые обновления | Рассмотреть после решения истории/архива; не обязательная миграция для временной доли успеха |
| Материализованные/инкрементальные суммы | Измеренно дорогие многолетние группы и высокая нагрузка | Добавляют пересчёт и согласованность; пока не обоснованы |

PostgreSQL поддерживает совместное использование relational и JSONB, рекомендует предсказуемую структуру документа и предупреждает, что обновление JSONB блокирует всю строку. GIN нужен для поиска внутри документов; для чтения всех дневных записей выбранного пользователя/диапазона он не заменяет B-tree. Вывод о достаточности текущей схемы для MVP — рекомендация по локальному объёму и коду, а не универсальная гарантия JSONB. [PostgreSQL: JSON-типы](https://www.postgresql.org/docs/current/datatype-json.html).

Материализованное представление хранит результат, который может быть устаревшим до REFRESH. Для редактируемой истории, особенно соседних ночей и границ года, нужно спроектировать обновление или принять задержку видимости. Если позже вводить собственные инкрементальные таблицы, хранить sums/counts (либо sumSin/sumCos), версию расчёта и атомарный пересчёт затронутых дат, а не только округлённые показатели. [PostgreSQL: materialized views](https://www.postgresql.org/docs/current/rules-materializedviews.html).

## Кэш и инвалидация после изменения

Эскиз ключа: `['statistics', userId, {granularity, from, toExclusive, timezone, rulesVersion}]`. Включать каждый параметр, влияющий на ответ; timezone/rulesVersion могут быть фиксированными серверными метаданными, а не пользовательскими параметрами. Смена аккаунта требует очистки приватного кэша или отдельного scope; один ключ без пользователя не должен возвращать данные другого аккаунта. [TanStack Query: query keys](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys).

Для MVP проще `useQuery` на фиксированное окно с prefetch одного соседнего окна в каждую сторону. Для непрерывной ленты можно useInfiniteQuery, но управление памятью и двумя направлениями сложнее. `keepPreviousData` поддерживает переход без исчезновения старой таблицы; пока показывается placeholder, нельзя подписывать старые числа новым периодом. Рекомендовано отображать границы из фактически отображаемого ответа. [TanStack: пагинация](https://tanstack.com/query/latest/docs/framework/react/guides/paginated-queries), [prefetch](https://tanstack.com/query/latest/docs/framework/react/guides/prefetching).

| Изменение исходных данных | Какие ответы становятся устаревшими |
| --- | --- |
| Bedtime дня d, включая очистку | Дневная строка d; duration дня d+1; все календарные группы, содержащие любую из этих дат |
| WakeTime/napDuration дня d | Строка и группы дня d |
| Habit mark дня d, включая снятие | Строка и группы дня d |
| Имя, архив, даты активности привычки | Метаданные и все затронутые привычкой окна; набор определяется принятой исторической семантикой |

На границе недели/месяца/года d и d+1 могут попасть в разные периоды. Для MVP допустимо инвалидировать весь пользовательский prefix `['statistics',userId]` после успешной мутации; точечная инвалидация — последующая оптимизация. TanStack позволяет сопоставлять по prefix; invalidation помечает совпавшие запросы stale и обновляет активные. Текущий `useSleepRecords` только refetch главной таблицы, поэтому такой инвалидации статистики ещё нет. [TanStack: invalidation](https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation), [текущие мутации](../../../apps/web/src/features/main/model/use-sleep-records.ts).

`staleTime` для перелистывания настраивать явно вместе с invalidation; по умолчанию данные stale, и mount/focus/reconnect могут запускать обновление. Исторический диапазон не является неизменным: пользователь может править прошлое. Текущий QueryClient использует defaults. [TanStack: defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults), [QueryClient](../../../apps/web/src/shared/api/query-client.ts).

На сервере текущий upsert обновляет сохранённую duration следующего дня только при непустом новом bedtime. Очистка bedtime не проходит эту ветку. Чтение пересчитывает duration и маскирует проблему, но будущая агрегация непосредственно сохранённой duration может прочитать устаревшее значение. Предпочтительно рассчитывать от первичных времени/дневного сна либо явно обеспечить согласованность производного поля для всех видов правки. [upsertSleepRecord](../../../apps/api/src/services/sleep-records.service.ts).

## Neon и пределы исследования

Официальный материал Neon разделяет установление соединения, близость приложения и БД и время обработки SQL. Это подтверждает необходимость различать локальное подключение и Railway→БД; долгоживущее соединение не устраняет накопление ожиданий 527 последовательных запросов. Cold start возможен после приостановки compute, но стабильные повторные задержки и N+1 требуют собственной диагностики; отключение scale-to-zero не доказано необходимым. [Neon: факторы latency и benchmark](https://neon.com/faster). Официальная документация описывает scale-to-zero, cache и pooling; часть страниц web-инструмент не смог открыть из-за отдачи Markdown, использован доступный поисковый текст официальной документации. [Neon: manage computes](https://neon.com/docs/manage/endpoints/).

Не выполнялись: миграции, изменение production, измерение нового range/self-join/lag HTTP endpoint, проверка актуального состава production-индексов и server-side timeline Railway. Документация PostgreSQL открыта в current (18); версии production не установлены, поэтому перед реализацией нужно проверить совместимость выбранных SQL-функций. В отчёте используются официальные документы и исходный код; показатели Neon с сайта не перенесены как ожидаемое ускорение Sadhana.

## Что передать следующему решению

1. Выбрать календарные границы, часовую зону, привязку ночи к дню и выборку каждого показателя сна.
2. Пометить долю успеха привычек временной; определить eligibleDays, архив/удаление и устойчивую идентичность.
3. После макета установить окно экрана и API-лимиты; выбрать range+API как исходный кандидат либо измерить SQL-кандидат.
4. Проверить отсутствие пропускного соединения через `lag`, дополнительный день на левой границе и инвалидацию d+1 на правой.
5. Измерить один и тот же endpoint после устранения N+1 в сопоставимом окружении; только затем решать о дополнительных агрегатах или миграции ради скорости.
