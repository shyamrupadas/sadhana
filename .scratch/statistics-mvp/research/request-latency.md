# Диагностика задержки статистики

Проверено 2026-10-09. Production API — через MCP `chrome-devtools` после входа пользователя; PostgreSQL — в транзакции `BEGIN READ ONLY` с `ROLLBACK`. Код приложения, схема и данные не изменялись. Токены, cookie, email, идентификатор пользователя, строка подключения и исходные записи в отчёт не включены.

## Результат

Главная подтверждённая причина — **N+1 последовательных обращений к PostgreSQL**. На 527 записях дня текущий сервис выполняет 528 SQL-запросов. После одной выборки он отдельно запрашивает предыдущую календарную дату для каждой строки, хотя все строки уже загружены. Затем сервис трижды фильтрует историю для средних. Источники: [чтение истории](../../../apps/api/src/services/sleep-records.service.ts), метод `getAllSleepRecordsForStats`, строки 82–132; [расчёт статистики](../../../apps/api/src/services/sleep-stats.service.ts), строки 22–85.

Сама общая выборка в PostgreSQL занимает 0,541 мс. Эксперимент: оставить **тот же сервис и те же данные**, но выдавать результаты поиска предыдущего дня из предварительно загруженного `Map(date → row)`. Полученный объект статистики строго совпал с результатом текущего сервиса (`assert.deepEqual`), а расчёт занял 207 мс. Это подтверждает возможность убрать SQL внутри цикла, сохранив нынешнюю семантику. Это диагностический эксперимент, а не внесённое исправление и не замер новой версии production.

| Тот же сервис с предварительно загруженными строками в памяти | 207 мс; ответ совпадает полностью |

**Локальные 40 с и браузерные 4,6 с не смешивать:** в первом случае Node.js работает на компьютере разработчика, во втором API обращается к БД со своего сервера. Отличается сетевой путь. 534 + 207 = 741 мс — лишь сумма двух измерений локального эксперимента, а не обещание времени новой страницы. CPU-замеры единичные и зависят от прогрева; точные доли CPU в production не измерены.

Общая SQL-выборка использовала `Seq Scan → Sort`, 527 результирующих строк и 95 блоков из shared cache; сортировка в памяти. На текущем маленьком наборе это быстрый план, а не доказательство отсутствия индексов. В схеме уже есть PK `(user_id, date)` и индекс по этим полям: [миграция создания](../../../apps/api/src/db/migrations/002_create_habits_and_daily_entries.sql), [составной PK](../../../apps/api/src/db/migrations/003_fix_daily_entries_primary_key.sql). Создание ещё одного индекса не устраняет 527 сетевых обменов.

## Петля воспроизведения

Через `chrome-devtools.evaluate_script` на авторизованной странице выполнена функция ниже. Токен остаётся внутри браузера, наружу возвращаются только метрики. Порог 1000 мс — **диагностический**, не согласованный SLA MVP. Все три вызова вернули `FAIL`, HTTP 200.

```js
async () => {
  const token = localStorage.getItem('token')
  if (!token) return { error: 'No session token' }
  const results = []
  for (let i = 0; i < 3; i++) {
    const start = performance.now()
    const response = await fetch('https://api.sadhana-tracker.com/sleep-stats', {
      headers: { Authorization: `Bearer ${token}` },
      credentials: 'include',
      cache: 'no-store',
    })
    const headersMs = performance.now() - start
    const body = await response.text()
    const totalMs = performance.now() - start
    results.push({
      run: i + 1,
      status: response.status,
      headersMs: Math.round(headersMs),
      totalMs: Math.round(totalMs),
      responseBytes: new TextEncoder().encode(body).length,
      verdict: response.ok && totalMs <= 1000 ? 'PASS' : 'FAIL',
      budgetMs: 1000,
    })
  }
  return results
}
```

Локальный диагностический скрипт был запущен командой `node /private/tmp/sadhana-statistics-diagnosis.cjs`; источник сервиса загружался через `ts-node` непосредственно из текущего кода. Временный скрипт не является постоянным тестом проекта. Он считал запросы реального сервиса и подставлял только источник результатов запросов для сравнительного эксперимента; бизнес-расчёты оставались теми же. Подключение закрыто, транзакция завершена `ROLLBACK`.

## Проверенные гипотезы

1. **Последовательные SQL на каждый день — подтверждено.** Счётчик 528, почти всё локальное время внутри `await client.query`; исключение повторных обращений сохраняет результат и устраняет эту часть ожидания.
2. **Расчёты Node.js — вторичная затрата.** В памяти 207 мс; их стоит учитывать при больших диапазонах, но они не объясняют большую часть наблюдаемой задержки.
3. **Медленная основная SQL-выборка — не подтверждено на этом наборе.** Выполнение в БД 0,541 мс.
4. **Общая сеть/авторизация/передача большого ответа — не объясняют разницу.** С тем же токеном соседние endpoints около 185 мс; ответ статистики 194 байта, почти всё время до заголовков. Сеть между API и БД при этом многократно оплачивается из-за N+1.

## Путь устранения и ограничения

- Для существующего ответа: одна выборка и поиск предыдущей **календарной даты** в памяти. Не использовать просто предыдущую строку: в истории могут быть пропуски дат.
- Для новой страницы: читать ограниченный диапазон и добавить предыдущий день перед левой границей для расчёта первой ночи, либо применить self-join по точной соседней дате. Дальнейшие варианты исследуются в [исследовании доступа](data-access.md).
- Не усреднять уже округлённые недельные/месячные средние; хранить/передавать суммы и количество наблюдений, если они понадобятся для объединения периодов. Правила конкретных показателей ещё обсуждаются.
- Не считать сохранённый `sleep_data.duration` гарантированным источником истины без отдельной проверки всех путей обновления: нынешнее чтение пересчитывает его из соседних дней.
- Аналогичный запрос внутри цикла существует и для пятидневной главной, но её изменение не нужно для постановки диагноза этой статистике.
- Обнаруженные особенности текущих периодов и фильтра неполных данных — отдельные доменные вопросы, а не часть исправления производительности. Выборка всей истории не ограничена, даже когда итоговые средние используют меньший период.

Диагноз завершён; исправление, регрессионные проверки и повторный production-замер относятся к следующему этапу реализации. Численно гарантировать скорость исправленного API сейчас нельзя.
