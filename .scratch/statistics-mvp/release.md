# Выпуск новой статистики в production

Status: planned

Источник: [«Переход к новой статистике и очистка прежних данных»](decisions/07-transition-and-legacy-cleanup.md). Сценарий согласован 2026-10-24; код перехода ещё предстоит реализовать и проверить. Production-действия в рамках карты не выполнялись.

## Порядок выпуска

**Проверить на dev → вручную остановить API → сделать резервную копию production-БД → влить проверенные изменения в `master` → дождаться автодеплоя Railway.** Автодеплой остаётся включённым. Обновление клиентов выполняется отдельно; новый API может быть несовместим с прежними клиентами.

1. **Подготовить выпуск до паузы.** На постоянной dev-БД выполнить существующую репетицию: проверить миграцию прежних тестовых данных, сохранность первичных значений, новую схему, работу приложения и повторный запуск мигратора. Зафиксировать проверенную ревизию и точные SQL; в production должны попасть те же SQL. Выполнить доступные проверки ветки/PR до merge. Несовместимые изменения пока не вливать в `master`. Убедиться, что у production API нет другого ожидающего или выполняющегося deployment. Во время окна не вливать посторонние изменения и не запускать другой deployment/DB CLI.
2. **Пользователь останавливает API вручную.** Railway → production → `sadhana-backend` → **Deployments** → меню **⋯** текущего работающего deployment → **Remove**. Это останавливает deployment, сохраняя сервис, Git-подключение, настройки и Neon-БД. Дождаться `REMOVED`; убедиться в отсутствии других активных экземпляров старого API. По последней зафиксированной конфигурации реплика одна, фактическое число проверяется перед выпуском. Проверить завершение/откат оставшихся записывающих транзакций и отсутствие других писателей. До этого момента перенос не начинается.
3. **Напомнить пользователю о резервной копии.** Текст напоминания: **«API остановлен. Перед слиянием коммита сделай резервную копию production-БД Neon и подтверди, что она готова».** Копию пользователь делает сам. Копия после остановки записи включает последние принятые изменения. Пока она не готова, коммит в `master` не вливать: merge запустит автоматический выпуск без дополнительной остановки перед миграцией.
4. **Пользователь вливает проверенные изменения в `master`.** Убедиться, что итоговый commit содержит проверенные SQL без изменений и ожидаемые исходники API. Автодеплой Railway реагирует на новый commit подключённой ветки с учётом watch paths. Отключение/включение автодеплоя и штатное нажатие **Deploy Latest Commit** не нужны. По зафиксированной в репозитории конфигурации Railway ждёт CI; проверка итогового commit после merge и сборка образа происходят уже во время паузы. Если автодеплой не появился, сначала выяснить причину по истории, watch paths и CI, не запускать параллельно второй выпуск.
5. **Railway выполняет перенос и сверку.** После успешных CI/сборки выполняется существующий Pre-Deploy `node dist/db/migrate.js` из нового образа. Перенос и автоматические проверки сохранности должны входить в этот этап и завершаться до запуска HTTP-сервера. При ошибке миграции или расхождении данных Pre-Deploy выходит с ненулевым кодом, новый API не запускается. Это требование будущей реализации, а не уже существующая проверка статистики.
6. **Новый API возобновляет обслуживание.** После успешного Pre-Deploy запускается `node dist/server.js`; перед готовностью к обслуживанию новая версия должна проверить ожидаемую схему. Текущий `GET /` сам БД не проверяет и этой проверки не заменяет. Railway направляет трафик на готовую версию после успешного healthcheck. Пауза заканчивается при открытии публичного доступа к новой версии — после этого уже возможны новые записи. Последующая ручная проверка приложения подтверждает выпуск, но не задерживает открытие записи.
7. **При неудаче проверить достигнутое состояние.** Ошибка CI/сборки, Pre-Deploy или готовности новой версии оставляет API недоступным: прежний deployment уже остановлен вручную. Проверить логи и фактическое состояние БД. Если миграция началась, соблюдать существующий порядок исправления вперёд; прежний API не запускать автоматически над изменённой схемой. Восстановление резервной копии выполняется пользователем отдельным согласованным действием. После принятия новых записей нельзя восстанавливать старый снимок без сохранения этих изменений.

## Границы паузы и время

Пауза начинается при ручной остановке старого API и заканчивается, когда готовый новый API получает публичный трафик. Neon остаётся доступен резервному копированию и мигратору. Недоступны чтение, сохранение и операции авторизации через API. Специальный экран PWA и обновление клиентов находятся вне задачи; конкретную ошибку при отсутствии backend формирует инфраструктура.

Фактическая пауза включает остановку и завершение транзакций, резервную копию пользователя, время до merge, CI итогового commit, очередь и сборку Railway, перенос/сверку, запуск и healthcheck. Проверки ветки и репетиция на dev выполняются заранее, но не заменяют CI итогового commit и production-сборку после merge.

Ранее названные 10–15 минут — предварительный резерв, а не замер, обещание или верхний предел. После реализации уточнить длительность SQL/сверки по dev-репетиции и отдельно учитывать ручные шаги, CI и Railway. При ошибке или ожидании пауза продлится; автоматического возобновления по таймеру нет.

## Почему автодеплой не отключается

Remove останавливает текущий deployment. Автодеплой — отдельная настройка сервиса: он остаётся ждать нового commit подключённой ветки. В этом сценарии commit с миграцией появляется в `master` только после подтверждённой остановки API и готовности резервной копии, поэтому отключать автодеплой не требуется.

Риск преждевременного выпуска возникает, если нужный commit уже в `master`, есть другой ожидающий deployment или кто-то запускает выпуск до готовности резервной копии. Это исключается порядком действий выше.

## Ограничения остановки и обработки ошибок

- Нынешний старый API не вызывает закрытие Fastify по SIGTERM/SIGINT. Выполнявшийся HTTP-запрос может получить ошибку, а его SQL — завершиться либо откатиться. Не обещать успешного завершения каждого запроса; дождаться завершения транзакций перед копией и переносом. Обработчик graceful shutdown только в новом образе не изменит поведение старого процесса; отдельный подготовительный API-релиз этим сценарием не требуется.
- Runner использует отдельную транзакцию на каждую миграцию. Сбой поздней стадии не откатывает уже применённые предыдущие стадии; после ошибки проверяется журнал. Автоматического отката всей БД нет.
- Старые серверные пути записи в прежнюю физическую модель должны быть отключены в новой версии; две первичные копии не поддерживаются. Резервная копия не является рабочим источником.
- Проверка сценария проведена по локальной конфигурации, зафиксированной в документации, и актуальным официальным источникам. Внешние настройки Railway в этой сессии не менялись; фактические настройки проверяются перед выпуском.
