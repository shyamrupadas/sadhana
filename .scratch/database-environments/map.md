# Dev-ветка Neon и безопасная проверка миграций

Label: wayfinder:map

## Destination

Выполненный переход: локальный web и API используют отдельную dev-ветку Neon с воспроизводимыми тестовыми данными; миграции проверяются там и применяются к production существующим Railway Pre-Deploy. Путь проходит через согласованные решения, спецификацию `to-spec` и реализационные тикеты `to-tickets` с приёмкой.

## Notes

- Исходный запрос 2026-10-10: устранить использование production при локальной разработке и обеспечить проверку серьёзных миграций. Пользователь прямо включил реализацию перехода в эту карту; это переопределяет обычную границу `wayfinder` «только планирование». Построение карты само по себе не означает запуск реализации.
- Уточнения пользователя 2026-10-10: нужна именно dev-ветка **Neon**, без постоянно работающего локального PostgreSQL. Отдельный staging-сайт/API не нужен. Только тестовые данные; **копии production не использовать даже для репетиций**. Схему меняют в одной работе за раз, хотя агенты работают параллельно.
- Временный PostgreSQL в Docker для отдельных сложных тестов остаётся обычным инструментом агента; отдельное решение о нём не требуется.
- Термины в этой карте: «dev-ветка» — постоянная БД повседневной разработки; «репетиция миграции» — проверка перехода между версиями схемы на тестовых данных. Нужен ли репетиции отдельный временный экземпляр Neon или управляемое пересоздание dev, определяется в билете о порядке проверки. Развёрнутое staging-окружение не входит в цель.
- Навыки: `wayfinder`, `grilling`, `domain-modeling`; для внешних фактов `research`; после решений `to-spec → to-tickets`, для тестов `write-tests`. Трекер — локальный Markdown по `docs/agents/issue-tracker.md`. Решения в `decisions/`, доказательства в `research/`, реализационные тикеты в `issues/`.
- При создании карты разрешено исследование документации и репозитория. Создание/сброс веток БД, смена конфигурации и миграции выполняются по последующим реализационным тикетам, а не в исследовании. Не менять Git index и не коммитить без запроса пользователя.
- Внешнее исследование выполняется в отдельном worktree на ветке `research/database-environments-2026-10-10`; отчёт публикуется здесь. Не читать и не сохранять пароли, строки подключения, токены и персональные записи.
- Действующий мигратор и Railway Pre-Deploy сохраняются как исходная основа. Новая работа пересматривает прежнее ограничение «постоянная тестовая база не нужна» из [«Порядок переключения и критерии приёмки»](../monorepo-migration/decisions/07-cutover-and-acceptance.md), принятого для переноса в монорепозиторий. Прежнюю принятую историю не переписывать.
- Карту статистики не менять: проверка её будущих миграций станет одним из применений этого перехода, но её решения и реализация остаются самостоятельной работой.

## Not yet specified

- После выбора восстановления тестового состояния и защиты окружений согласовать проверяемую спецификацию и швы тестирования, затем размер и зависимости реализационных тикетов. Реализовать их с предусмотренной трекером приёмкой и включить постоянную dev-ветку в ежедневную разработку.
- Конкретные операции первого перехода зависят от выбранного способа создания ветки, команд и доступа к Neon. Уточнить при подготовке реализационных тикетов; не превращать неопределённый порядок в заранее придуманные инфраструктурные задачи.

## Out of scope

- Копирование production-данных, в том числе частичное, с очисткой после копирования или для миграционных репетиций.
- Отдельно развёрнутый staging web/API, переход на другую СУБД или хостинг, постоянная локальная БД и автоматическое создание БД для каждой работы агента.
- Реализация статистики и других предметных миграций; этот переход предоставляет способ их проверки.
- Пересмотр принятой политики краткой несовместимости при Railway Pre-Deploy и построение системы безостановочных выпусков. Если новое исследование выявит прямой конфликт с целью карты, обсудить его отдельно.
