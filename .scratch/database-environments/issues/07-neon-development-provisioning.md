# 07: Создание постоянного dev в Neon и первое заполнение

**What to build:** В нынешнем Neon-проекте появляется постоянная dev-ветка без production-строк, отдельные БД/роль и проверенная локальная конфигурация. Готовые команды собирают пустую dev-БД обычными миграциями и первоначально заполняют тестовыми профилями.

**Blocked by:** 06 — Полная репетиция перехода с проверкой результата

**Status:** ready-for-agent

- [ ] До создания ресурсов проверены фактические доступность schema-only root, квоты, отсутствие автоудаления и возможность предоставить выбранной dev-роли права для миграций, `uuid-ossp` и пересоздания отдельной БД через служебный канал. Если выбранный путь недоступен, зафиксирован конкретный факт и работа возвращена к карте, без скрытой смены проекта/копирования production.
- [ ] Создана schema-only root-ветка нынешнего проекта без production-строк на любом этапе; внутри подготовлена отдельная совершенно пустая dev-БД. Скопированная современная схема не используется для исполнения исторических миграций. Обычного клона с последующей очисткой нет.
- [ ] Создана одна новая dev-роль с отдельным паролем для API/мигратора и разрешённый служебный канал в той же ветке. Локальные команды не используют унаследованные production-роли или production-пароли; права подтверждены для операций этого перехода.
- [ ] Фактические direct/runtime хосты, порт, dev-БД, роль и служебная БД внесены в независимую несекретную конфигурацию. Direct/runtime URL, dev JWT и тестовый пароль сохранены только в игнорируемом локальном env; в тикете и результатах нет секретов или персональных записей.
- [ ] `db:status` подтверждает пустое исходное состояние; `db:migrate` собирает реальную цепочку и журнал; `db:dev-seed` заполняет три профиля с явно заданным московским днём запуска. Исторический baseline не выполняется.
- [ ] Подтверждены безопасная диагностика цели, версия/полнота журнала и соответствие сохранённых синтетических записей известному набору. Ошибочные локальные URL отклоняются штатной защитой; реальные production-подключения для этого не используются.
- [ ] Необходимая отдельно проверяемая production-конфигурация guard подготовлена/согласованно включена для действующего Railway API и Pre-Deploy перед выпуском требующего её кода. Production-секреты остаются в Railway, исторические SQL и baseline не запускаются повторно; чтение предметных production-записей не требуется.
- [ ] До проверок и действий в аккаунтах Neon/Railway, которые может выполнить и пользователь, предложен осознанный выбор: пользователь выполняет шаг сам либо делегирует агенту. Объяснены цель и ожидаемый результат; выбор соблюдён, в том числе для фактов, доступных агенту. При недостающем у агента доступе выданы конкретные действия для пользователя. Инструкция первоначальной настройки содержит безопасные идентификаторы/шаги, условия отказа и местонахождение локальных секретов без их значений.

## Проверка и границы

Внешние операции начинаются после приёмки готовых инструментов; зависимость от репетиции транзитивно включает guards, мигратор, генератор и восстановление. Не запускать сброс production, смену его паролей или копирование данных. Эта задача создаёт и наполняет dev; рабочие сценарии приложения и реальная репетиция на Neon принимаются следующей задачей.

## Участие пользователя

Когда проверку или действие можно либо поручить агенту, либо выполнить самому через аккаунт/сервис, сначала объяснить цель и ожидаемый результат и предложить пользователю выбор. Этот шаг ждёт ответа; независимая работа может продолжаться. После явного делегирования действовать в согласованном объёме без повторного запроса по тому же шагу. Это предпочтение пользователя от 2026-10-15 действует и для фактов, доступных агенту.

Уточнение пользователя от 2026-10-16: все действия с Docker и временным PostgreSQL, включая подготовку, проверки и очистку, делегированы агенту без повторных вопросов. Пользователь хочет участвовать в шагах через интерфейс Neon; для них сохраняется выбор выше.
