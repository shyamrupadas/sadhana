# 08: Включение dev в ежедневную разработку и приёмка перехода

**What to build:** Разработчик ежедневно работает через локальный web и API с постоянным Neon dev, сохраняет изменения между запусками и умеет явно восстановить исходник/проверить миграцию перед Railway-выпуском. Переход готов к итоговой человеческой приёмке.

**Blocked by:** 04 — Проверка SQL в production-образе без фиксированного количества; 07 — Создание постоянного dev в Neon и первое заполнение

**Status:** ready-for-agent

- [ ] Короткий ручной проход реального локального пути подтверждает отметку dev, вход во все три профиля, создание/изменение записи дня и отметки привычки, сохранность изменений после перезапуска web/API. Обычный запуск не мигрирует, не заполняет и не сбрасывает БД; MSW не подменяет API в этом проходе.
- [ ] После согласованной остановки работающих с dev процессов на постоянном Neon выполнена `db:dev-reseed` с явной датой: ожидаемый новый набор получен, структура и полный журнал миграций неизменны. Первичное seed по-прежнему отказывает при непустых таблицах.
- [ ] На постоянном Neon явно выполнено восстановление `public` из поддерживаемого Git-исходника внутри той же БД, без служебного подключения и CREATEDB/superuser; имя БД, роль и URL сохранены. Достигнуты ожидаемые версия/данные; текущие рабочая копия и index не изменены командой. Исходник с совместимым генератором уже сохранён обычным Git-процессом, автоматического коммита нет.
- [ ] На постоянном dev выполнена полная репетиция содержательного синтетического тестового перехода с независимым ожидаемым результатом и проверкой повторного запуска. Тестовый SQL не добавлен в выпускаемую цепочку; перед завершением dev явно возвращён к выбранной версии настоящих миграций с совместимыми профилями.
- [ ] Финальный состав production-образа после всех изменений совпадает с SQL-исходниками проверяемой сборки. Команда Railway Pre-Deploy сохранена, отдельно проверенный production-контекст работоспособен; сборка/старт API не выполняют миграции.
- [ ] Руководство описывает первичную настройку, ежедневный запуск/вход, статус/применение, допустимое старение истории, различие первичного seed, замены данных и восстановления структуры, обновление набора с сохранением полного журнала, восстановление Git-версии в той же БД, полную репетицию и повтор после изменения SQL. Указаны остановка параллельной работы перед сбросом и отсутствие атомарного восстановления прежнего dev при ошибке.
- [ ] Руководство выпуска требует проверки каждого нового SQL на dev, сохранённых записей для преобразований и повторного запуска. При неудаче production выясняется фактическое состояние и применяется проверенное исправление вперёд; совместимость старого приложения с фактической схемой проверяется до его возврата.
- [ ] В dev-ветке одна рабочая БД; служебное подключение, обязательный CREATEDB/superuser, дополнительные ручные отчёты допуска, обязательный PostgreSQL в CI, staging или копии production не введены. Пароли/URL/JWT/токены и персональные записи не публикуются в результатах ручной проверки и документации.
- [ ] Проверены все критерии принятой спецификации и необходимые targeted проверки по затронутым границам; фактически выполненные проверки и обнаруженные ограничения отражены в результате этой задачи. Статус после завершения — `awaiting-human-review`; приёмку задачи и всего перехода выполняет пользователь.

## Проверка и границы

Эта задача проверяет взаимодействие повторно принятых по редакции от 2026-10-17 возможностей тикета 05 и остальных принятых возможностей на реальном Neon и передаёт переход в повседневную работу. Она не заменяет самостоятельные проверки предыдущих задач большим новым набором E2E. Полноценная приёмка спецификации как реализованного перехода возможна после человеческой приёмки всех реализационных тикетов по правилам трекера.

## Участие пользователя

Когда проверку или действие можно либо поручить агенту, либо выполнить самому через аккаунт/сервис, сначала объяснить цель и ожидаемый результат и предложить пользователю выбор. Этот шаг ждёт ответа; независимая работа может продолжаться. После явного делегирования действовать в согласованном объёме без повторного запроса по тому же шагу. Это предпочтение пользователя от 2026-10-15 действует и для фактов, доступных агенту.

Уточнение пользователя от 2026-10-16: все действия с Docker и временным PostgreSQL, включая подготовку, проверки и очистку, делегированы агенту без повторных вопросов. Пользователь хочет участвовать в шагах через интерфейс Neon; для них сохраняется выбор выше.
