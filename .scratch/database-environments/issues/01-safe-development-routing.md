# 01: Безопасный локальный путь web → API → dev

**What to build:** Разработчик запускает локальные web и API с явно проверенной dev-конфигурацией, видит выбранное окружение и получает отказ до обращения к чужому API или БД. Production-образ и существующий Railway Pre-Deploy используют отдельно проверенный production-контекст.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [ ] Локальный путь настроен как `http://localhost:5173` → `http://localhost:8080` → dev; web использует настоящий API без MSW и показывает заметную отметку dev. Неизвестный/внешний API URL и адрес с учётными данными отклоняются до запроса; существующий `/test-api` контур остаётся изолированным.
- [ ] Независимая несекретная конфигурация разрешённой цели задаёт direct/runtime хосты, порт, БД и роль; проверяемый URL не служит её источником. Подготовлены примеры конфигурации без фактических секретов и инструкция заполнения идентификаторов после создания dev.
- [ ] До открытия соединения проверяются формат URL, цель, согласованность runtime/direct и запрещённые параметры изменения цели/области SQL. Для миграционного подключения принимается только direct; отсутствующая или чужая конфигурация приводит к отказу без запасного production URL.
- [ ] Локальный запуск фиксирует контекст dev и отклоняет конфликтующий `DB_ENVIRONMENT`. Один `NODE_ENV=production` не переключает его в production и не отменяет проверку цели; локальные env разрешаются относительно репозитория независимо от текущего каталога.
- [ ] Production API и Railway Pre-Deploy сохраняют существующие точки запуска с отдельно заданными ожидаемыми production-идентификаторами и явным контекстом. Переход конфигурации описан так, чтобы выпуск новой защиты не оставил действующий сервис без обязательных настроек. В этом тикете внешние настройки и секреты не меняются.
- [ ] Dev JWT и подключения хранятся в игнорируемой локальной конфигурации, production-секреты не используются локально. Безопасная диагностика показывает окружение/хост/БД/роль; ошибки не раскрывают URL, JWT, токены, пароли или персональные записи.
- [ ] Обычный запуск не мигрирует, не заполняет и не сбрасывает БД; обычные CORS, refresh cookie и авторизация сохраняются. Тесты и проверка запуска production-образа с фиктивной БД используют отдельную проверяемую тестовую конфигурацию и не требуют production-доступа.
- [ ] Targeted API-тесты подтверждают отказ до подключения, включая несогласованные URL и локальный `NODE_ENV=production`; web unit/component проверки подтверждают адрес API и видимую отметку. Короткий ручной проход затронутого web-поведения выполнен без подключения к production.

## Проверка и границы

Граница результата — работающий выбор окружения и отказ при ошибке, доступные для проверки на разрешённой тестовой цели. Фактические идентификаторы Neon и полноценный вход в постоянный dev проверяются при первом включении. Для изменения frontend-модулей применять frontend-architecture, для тестов — write-tests. Публичный HTTP-контракт не меняется.

## Участие пользователя

Когда проверку или действие можно либо поручить агенту, либо выполнить самому через аккаунт/сервис, сначала объяснить цель и ожидаемый результат и предложить пользователю выбор. Этот шаг ждёт ответа; независимая работа может продолжаться. После явного делегирования действовать в согласованном объёме без повторного запроса по тому же шагу. Это предпочтение пользователя от 2026-10-15 действует и для фактов, доступных агенту.
