# 06: Полная репетиция перехода с проверкой результата

**What to build:** Разработчик одной командой воспроизводит прежнюю структуру и записи внутри той же dev-БД, применяет проверяемый переход и получает успешный результат только после проверки преобразования и повторного запуска.

**Blocked by:** 05 — Восстановление dev из совместимого Git-исходника

**Status:** ready-for-agent

- [ ] `pnpm db:rehearse --allow-reset --source-ref <git-ref> --from <NNN> --to <NNN> --date <YYYY-MM-DD> --checks <name>` доступна из корня со справкой. Все аргументы обязательны; целевая версия строго новее исходной, неизвестные параметры отклоняются.
- [ ] До очистки структуры проверены dev-цель, подготовленный Git-исходник, целевая цепочка, полный именованный сценарий проверок, необходимые права и поддерживаемый состав объектов/зависимостей. Исходные и целевые SQL согласованы с областью восстановления `public` и поддерживаемыми расширениями; неподдерживаемый переход отказывает до очистки. Исходный префикс целевого SQL до `--from` побайтово совпадает с Git-версией. Исходная версия задана для фактического перехода, а не автоматически как последняя минус один.
- [ ] Целевые SQL и проверки из текущей рабочей копии фиксируются для запуска до сброса; изменение файлов не смешивает версии внутри выполнения. Отсутствующие/несовместимые проверки или несовпадающий префикс вызывают отказ до разрушительной операции.
- [ ] Сценарий использует восстановление `public` из обновлённого тикета 05, без удаления БД и служебного подключения; имя БД, роль и URL сохраняются. Замена только записей через reseed не заменяет подготовку старой структуры. Выполняется вся цепочка: восстановление исходной версии → совместимые данные → проверка исходника → целевые SQL → проверка схемы/преобразования/сохранности → повтор мигратора → проверка неизменности данных и полного журнала.
- [ ] Проверки конкретного перехода имеют независимые ожидаемые результаты и читают сохранённые записи; успешный SQL или ответы API сами по себе не означают успех. Намеренное изменение числа записей оценивается по ожидаемому результату, без универсального требования неизменности количества.
- [ ] Любая ошибка этапа или несовпадение дают ненулевой код; успех всех этапов даёт `0` и оставляет dev на целевой версии. Автоматический итог безопасно сообщает цель, commit/версии, дату и результаты; после сбоя сообщается прочитанное состояние структуры/достигнутая версия либо невозможность чтения, без заявления об удалении самой БД. Отдельный отчёт допуска не требуется.
- [ ] API-тесты подтверждают последовательность и отказы до сброса; явный PostgreSQL-прогон в отдельной заранее разрешённой изолированной БД под ролью без CREATEDB/superuser проверяет содержательный тестовый переход, отрицательный результат и отсутствие изменений при повторе. Постоянная dev-БД при `db:test` не очищается. Тестовые SQL не попадают в production-цепочку.
- [ ] Документирован небольшой контракт именованных проверок и пример добавления сценария будущей миграции. Каждый новый SQL проверяется на dev; после изменения SQL переход повторяется с исходника, несколько выпускаемых SQL можно проверять вместе. Нет новой универсальной платформы, обязательного DB-backed CI или ручного дублирования тестов.

## Проверка и границы

Применять write-tests. Дождаться повторной приёмки переоткрытого тикета 05 по редакции спецификации от 2026-10-17. Использовать восстановление структуры и мигратор из предыдущих задач; не дублировать механизмы подключения/журнала. В этой задаче команды проверяются на разрешённом временном PostgreSQL; первый фактический запуск на постоянном Neon входит в завершение перехода.

## Участие пользователя

Когда проверку или действие можно либо поручить агенту, либо выполнить самому через аккаунт/сервис, сначала объяснить цель и ожидаемый результат и предложить пользователю выбор. Этот шаг ждёт ответа; независимая работа может продолжаться. После явного делегирования действовать в согласованном объёме без повторного запроса по тому же шагу. Это предпочтение пользователя от 2026-10-15 действует и для фактов, доступных агенту.

Уточнение пользователя от 2026-10-16: все действия с Docker и временным PostgreSQL, включая подготовку, проверки и очистку, делегированы агенту без повторных вопросов. Пользователь хочет участвовать в шагах через интерфейс Neon; для них сохраняется выбор выше.
