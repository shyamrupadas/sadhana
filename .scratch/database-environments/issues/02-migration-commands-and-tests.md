# 02: Статус и применение миграций с явными PostgreSQL-проверками

**What to build:** Разработчик читает состояние dev без изменений, применяет новые миграции до выбранной версии и явно запускает PostgreSQL-проверки через команды из корня. Существующие гарантии мигратора и принятая production-история сохраняются.

**Blocked by:** 01 — Безопасный локальный путь web → API → dev

**Status:** ready-for-agent

- [ ] `pnpm db:status` только читает: выводит безопасную цель, применённые/ожидающие SQL и наличие журнала. Не создаёт журнал, не выполняет baseline/SQL и не исправляет расхождения. Пустая БД без журнала показывает все SQL ожидающими; непустая прикладная схема без журнала, разрывы/неизвестная история и изменённые checksum дают ненулевой код.
- [ ] `pnpm db:migrate [--to <NNN>]` применяет непрерывный ожидающий префикс существующим мигратором; без аргумента применяет всю цепочку. Версия ниже уже применённой или отсутствующая в цепочке приводит к отказу. Нет сброса, заполнения или production-переключателя.
- [ ] Команды используют общую dev-проверку и загрузку конфигурации, имеют `--help`, отклоняют неизвестные аргументы, безопасно обрабатывают ошибки и возвращают `0` только при выполнении контракта.
- [ ] Сохраняются checksum/порядок, отказ при изменении применённых SQL, пропуск зарегистрированных файлов, отдельная транзакция SQL вместе с записью в журнале, advisory lock и таймауты. Применение до версии и последующее продолжение используют те же проверки.
- [ ] Исторический baseline отделён от повседневных команд без удаления необходимых подтверждений/проверок. Выпущенные SQL, checksum и принятая production-история неизменны; обычное применение Railway Pre-Deploy продолжает работать.
- [ ] `pnpm db:test --target <dev|test>` явно запускает DB-backed сценарии на проверенной direct-цели. Для `test` используется независимая несекретная разрешённая цель и отдельный URL; отсутствие настройки — неуспех. Тестовые схемы изолируются и очищаются в том числе после ошибки; постоянная dev-БД не пересоздаётся.
- [ ] Механические тесты используют маленькие локальные SQL-fixtures и независимые ожидания вместо реального числа файлов или свободной версии `007`. Подтверждены порядок/журнал/checksum, повторный запуск, откат сбойного SQL, сохранение предыдущего успешного SQL и сериализация конкурирующих запусков.
- [ ] Отдельные проверки реальной цепочки с нуля, предметных преобразований и исторического baseline сохранены. Обычные workspace tests работают без Neon и не маскируют результат явно запрошенного DB-прогона пропуском.
- [ ] Документированы команды чтения/применения/тестов и подготовка/очистка тестовой цели. Targeted API-тесты и явный прогон на разрешённом временном PostgreSQL подтверждают контракт, включая read-only статус; обязательный PostgreSQL в CI не добавлен.

## Проверка и границы

Сначала сделать существующий мигратор пригодным для ограниченного применения и отдельного чтения, сохранив поведение production; затем подключить команды. Рефакторинг ограничен необходимыми возможностями и тестами этой задачи. Применять write-tests. Нового источника схемы и универсального движка репетиций нет.

## Участие пользователя

Когда проверку или действие можно либо поручить агенту, либо выполнить самому через аккаунт/сервис, сначала объяснить цель и ожидаемый результат и предложить пользователю выбор. Этот шаг ждёт ответа; независимая работа может продолжаться. После явного делегирования действовать в согласованном объёме без повторного запроса по тому же шагу. Это предпочтение пользователя от 2026-10-15 действует и для фактов, доступных агенту.
