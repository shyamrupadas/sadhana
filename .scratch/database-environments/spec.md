# Dev-ветка Neon и безопасная проверка миграций

Status: awaiting-human-review
Accepted: 2026-10-19

Первая редакция принята 2026-10-14; пользователь согласовал упрощение сброса и обновление спецификации 2026-10-17. Актуальный контракт: одна рабочая БД в dev-ветке, отдельное обновление тестовых данных и восстановление структуры внутри той же БД. Обновлённая реализация тикета 05 повторно принята пользователем 2026-10-17. Все восемь реализационных тикетов и завершённый переход приняты пользователем 2026-10-19.

## Problem Statement

Локальная разработка не должна использовать production-БД или её данные. Разработчику нужна постоянная dev-БД с реалистичной тестовой историей, которая сохраняет обычные изменения между запусками. Перед выпуском новой SQL-миграции нужно проверить переход с прежней схемы и существующих синтетических записей, а также повторный запуск мигратора.

Сейчас подключения задаются через env, но независимой проверки разрешённой цели нет. Выбор загрузки локальных секретов зависит от `NODE_ENV`. Мигратор применяет всю доступную цепочку и создаёт журнал; отдельного чтения статуса, восстановления поддерживаемого исходника и генератора данных нет. Некоторые тесты механики зависят от настоящей цепочки и версии `007`, а проверка production-образа требует ровно шесть SQL-файлов. Эти ограничения мешают безопасно проверять следующие миграции.

## Solution

Локальные web и API работают по пути `http://localhost:5173` → `http://localhost:8080` → постоянная dev-ветка Neon в нынешнем проекте. Ветка создаётся без production-строк через schema-only root. Единственная скопированная БД становится рабочей dev-БД: её скопированная прикладная структура очищается, затем собирается обычными миграциями и заполняется синтетическими данными. Дополнительная рабочая или служебная БД внутри dev-ветки не создаётся. Для API и мигратора используется одна новая dev-роль с отдельным паролем.

Разработчик видит выбранную dev-цель, получает отказ до подключения при неверной конфигурации и пользуется небольшим набором команд из корня репозитория. Обычный запуск сохраняет данные; применение миграций, первичное заполнение, замена тестового набора, восстановление структуры и репетиция выполняются явно. Замена набора меняет только прикладные записи и сохраняет схему и журнал миграций. Историческое восстановление заново собирает управляемую структуру `public` в той же БД; имя БД, роль и URL сохраняются. Для репетиции постоянный dev восстанавливается до поддерживаемого прежнего состояния, затем проверяются выпускаемые SQL и ожидаемое преобразование записей. После успешной репетиции dev остаётся на новой версии.

Production продолжает обновляться существующим Railway Pre-Deploy из собранного образа. Каждая новая миграция проверяется на dev до выпуска; при неудаче production исправляется вперёд. Обязательный PostgreSQL в CI, отдельный staging и временные Neon-ветки не вводятся.

19. Как разработчик, я хочу проверять сохранённые данные и ожидаемый результат конкретной миграции, чтобы пересчёт в API не скрывал ошибку SQL.

## Implementation Decisions

### Основа и границы модулей

- Сохраняется существующий мигратор: нумерованные SQL и `schema_migrations` остаются единственным источником структуры. Дополняются его публичные возможности чтения статуса и применения последовательного префикса до выбранной версии. Снимок актуальной схемы как второй источник не создаётся.
- Общее управление БД отвечает за загрузку и проверку конфигурации, подготовку исходника и последовательность команд. Мигратор отвечает за порядок, контрольные суммы, журнал, транзакции и блокировку конкурирующих миграторов. Генератор отвечает за синтетические записи совместимой версии; проверки перехода задают независимый ожидаемый результат.
- Сохраняются отказ при изменённых применённых SQL и неизвестной/непоследовательной истории, пропуск зарегистрированных файлов, отдельная транзакция каждого SQL вместе с записью в журнале, advisory lock и существующие ограничения времени. Сбой следующего SQL не отменяет ранее успешно зафиксированные миграции.
- Целевая версия — конец непрерывного префикса от `001`. Применение к существующей БД выполняется только вперёд. Возврат dev к прежней версии выполняется восстановлением управляемой структуры `public` из SQL, без удаления самой БД и без обратного SQL. При этом прежний журнал удаляется вместе со всей управляемой структурой, а новый создаёт мигратор; выборочное редактирование строк существующего журнала не используется. При замене только данных журнал полностью сохраняется.
- Исторический baseline отделяется от повседневных команд. Его подтверждения и проверки сохраняются; для новой dev-БД он не используется и в production повторно не выполняется.
- Публичный HTTP-контракт и предметная модель не меняются. Архивирование привычек и семантика удаления остаются вне перехода. Новый универсальный движок репетиций или замена мигратора библиотекой не требуются.

### Конфигурация и проверка цели

Далее заданы принятые вместе со спецификацией точные имена и интерфейсы; они конкретизируют ранее принятые решения.

| Настройка | Назначение |
| --- | --- |
| `DATABASE_URL` | Runtime-подключение API к dev; direct либо pooled. |
| `MIGRATION_DATABASE_URL` | Direct-подключение мигратора к той же dev-БД и роли. |
| `JWT_SECRET`, `JWT_REFRESH_SECRET` | Отдельные dev-секреты обычной авторизации. |
| `DEV_FIXTURE_PASSWORD` | Один локальный пароль трёх тестовых аккаунтов; требуется только при заполнении. |
| `VITE_API_BASE_URL` | Для обычной локальной разработки — `http://localhost:8080`. |
| `VITE_USE_MOCKS` | Для обычной разработки с Neon — `false`. |
| `DB_ENVIRONMENT` | Явный контекст `dev`, `production` либо `test`; локальные команды не выбирают его по `NODE_ENV`. Новая переменная в Railway для запуска production не требуется. |
| `MIGRATION_TEST_DATABASE_URL` | Direct-подключение только для явно запускаемых PostgreSQL-тестов. |

- Разрешённая dev-цель хранится в отдельной версионируемой несекретной конфигурации: точный direct-хост, разрешённый runtime-хост, порт, имя dev-БД и dev-роль. Управляемая область восстановления фиксирована в коде как `public`; отдельные `maintenanceDatabase`, служебный URL и право `CREATEDB` для dev-команд не требуются. Эти значения не выводятся из проверяемых URL. Фактические идентификаторы фиксируются после создания ресурсов.
- Dev-секреты хранятся в игнорируемом локальном env API; web хранит только несекретный адрес API и настройки режима. Все локальные команды разрешают пути конфигурации относительно репозитория, независимо от текущего каталога. Загрузка секретов не переключается на production от одного `NODE_ENV=production`.
- Локальные команды запуска API и управления dev имеют фиксированный контекст dev и отказывают при конфликтующем `DB_ENVIRONMENT`. У них нет аргумента переключения в production. Независимая проверка разрешённой цели обязательна для dev и тестового контура. Production API и Railway Pre-Deploy сохраняют существующие подключения и секреты; добавление dev-БД не требует новых переменных или изменения настроек Railway. Обязательный production guard с `DB_EXPECTED_*` не вводится.
- В dev и DB-backed тестах до открытия соединения проверяются корректный PostgreSQL URL, разрешённые хост/порт/БД/роль, согласованность runtime/direct целей и direct-подключение мигратора. Неожиданные параметры URL, способные изменить выбранную цель или область SQL, не принимаются. Для DB-backed тестов допустимые параметры тестовой схемы задаются самим тестовым контуром после проверки цели. Существующее требование direct-подключения production-мигратора сохраняется.
- Неизвестная или неполная конфигурация dev/тестового контура приводит к отказу. Запасного production URL, предупреждения с продолжением и подтверждения вместо проверки цели нет. Проверка защищает от случайной ошибки конфигурации; административную изоляцию она не заменяет.
- Обычный dev-web до API-запросов проверяет полный адрес `http://localhost:8080` и показывает заметную отметку dev. Внешний URL, URL с учётными данными и неизвестный адрес приводят к понятному отказу. Изолированный существующий web-test контур с `/test-api` сохраняется отдельно; его настройка не становится разрешением внешнего API в обычном dev.
- При старте API и команд выводятся окружение, хост, БД и роль без паролей. Ошибки парсинга URL, подключения, дочернего процесса и SQL проходят безопасную обработку: не выводятся полные строки подключения, JWT, токены, пароль заполнения или содержимое пользовательских записей.
- Обычный запуск API/web не применяет SQL, не создаёт тестовых пользователей и не сбрасывает данные. Сохраняются обычная авторизация, CORS и refresh cookie локального пути.

### Команды из корня репозитория

Все команды имеют `--help`, отклоняют неизвестные аргументы и возвращают `0` только при выполнении своего контракта. Для изменяющих состояние команд полная проверка цели обязательна независимо от разрешения сброса. Имена версий — трёхзначные идентификаторы миграций; `latest` допускается только там, где явно указан в таблице, и разрешается в конкретный идентификатор до работы с БД.

| Команда | Вход и наблюдаемое поведение |
| --- | --- |
| `pnpm db:status` | Только чтение dev: идентичность цели, применённые и ожидающие миграции, наличие журнала и расхождения. Отсутствие журнала в пустой БД показывает все SQL ожидающими. Непустая прикладная схема без журнала, неизвестная версия, разрыв или изменённая checksum дают неуспех. Команда не создаёт журнал, не берёт baseline и не исправляет БД. |
| `pnpm db:migrate [--to <NNN>]` | Применяет ожидающий префикс к существующему dev. Без `--to` применяет всю текущую цепочку. Версия ниже уже применённой приводит к отказу; сброс и заполнение не выполняются. |
| `pnpm db:dev-seed --date <YYYY-MM-DD>` | Первоначально заполняет БД на версии, заявленной текущим генератором. Требует локального пароля и пустых прикладных таблиц; при существующих предметных записях отказывает без перезаписи. Используется после первоначального применения SQL; не вызывается запуском приложения. |
| `pnpm db:dev-reseed --allow-reset --date <YYYY-MM-DD>` | Транзакционно заменяет все прикладные записи совместимым синтетическим набором текущего генератора. Сохраняет структуру, расширения и полный журнал миграций; SQL-миграции не применяет. Разрешение потери данных и дата обязательны; Git-ref, целевая версия и произвольные таблицы не принимаются. |
| `pnpm db:dev-reset --allow-reset --source-ref <git-ref> --to <NNN> --date <YYYY-MM-DD>` | Проверяет и готовит совместимый исходник, очищает и заново создаёт управляемую структуру `public` в той же dev-БД, применяет исходные SQL до указанной версии, заполняет синтетическим набором и проверяет исходное состояние. Все четыре аргумента обязательны; скрытых `latest` и сегодняшней даты нет. БД не удаляется. |
| `pnpm db:rehearse --allow-reset --source-ref <git-ref> --from <NNN> --to <NNN> --date <YYYY-MM-DD> --checks <name>` | Полная репетиция на постоянном dev. Исходник берётся из Git; целевые SQL и именованные проверки — из текущей рабочей копии, зафиксированной для этого запуска. Все аргументы обязательны. Цель новее исходника; проверяется весь выпускаемый переход. |
| `pnpm db:test --target <dev\|test>` | Явно запускает DB-backed проверки. Для `dev` использует разрешённый direct dev; для `test` — отдельный URL и независимую несекретную разрешённую цель, например временный Docker PostgreSQL. Отсутствие подключения приводит к неуспеху. Тестовые схемы изолируются и удаляются; команда не пересоздаёт постоянный dev. |

`db:dev-seed` сохраняет безопасный интерфейс первичного заполнения пустых прикладных таблиц. `db:dev-reseed` служит для замены имеющегося набора с сохранением структуры; `db:dev-reset` — для первоначальной сборки скопированной структуры и исторического восстановления. Эти команды не подменяют друг друга. `db:test` — явный вход в согласованные DB-backed проверки, а не новый обязательный этап CI.

### Поддерживаемый исходник из Git

- Исходник определяется Git commit, конечной версией схемы, версией генератора/целевого набора и опорной датой. Перед запуском символический `git-ref` разрешается в конкретный commit. В безопасном итоге выводятся commit, версии и дата.
- Код извлекается из локального Git в отдельный временный каталог без `checkout`, переключения ветки, изменения рабочей копии или index. Локальные env и секреты не копируются в этот каталог и не извлекаются из исторических конфигураций. Подключение выдаёт только текущая проверенная конфигурация dev.
- Совместимость набора заявляется явно для конечной версии схемы. Первый генератор поддерживает текущую схему, собранную существующей цепочкой; это не обещание заполнения всех исторических версий `001–005`. Старые версии поддерживаются только при наличии совместимого генератора или целевого набора в выбранном commit.
- Перед сбросом проверяются Git-ref, непрерывность и checksum исходной цепочки, выбранная версия, совместимость генератора и управляемой области SQL, дата, пароль заполнения, доступность зависимостей и возможность запуска подготовленного кода. Подготовка зависимостей и сборка, если необходимы, завершаются до очистки структуры. Нет неявного подменивания исторического генератора нынешним.
- Для репетиции исходный префикс целевого SQL до `--from` должен побайтово совпадать с выбранным Git-исходником. Целевая цепочка и именованные проверки фиксируются до сброса, чтобы изменения файлов во время выполнения не смешивали разные версии. Меняющийся или неподдерживаемый исходник приводит к отказу.
- Первичное заполнение может использовать генератор из текущей рабочей копии. Историческое восстановление через `--source-ref` становится доступным только после сохранения совместимого исходника в Git обычным процессом проекта; команды БД сами не создают коммиты.
- Временный код и подготовленные артефакты удаляются после завершения или ошибки. Извлечение кода не требует worktree и не изменяет существующую исследовательскую ветку.

### Обновление данных без изменения структуры

- `db:dev-reseed` использует текущий генератор и требует его явно совместимую применённую версию с неизменёнными checksum. При неподходящей истории команда отказывает до очистки; она не применяет миграции и не пытается заполнять другую версию нынешним генератором.
- До записи проверяются текущая dev-цель, обязательные `--allow-reset`, дата, локальный пароль и возможность построить набор. Пользователь предварительно останавливает API и другую работу с dev.
- Очистка всех прикладных таблиц известной совместимой версии (`users`, `habits`, `daily_entries` для первого генератора), заполнение и проверка сохранённых записей выполняются через одно соединение в одной транзакции с блокировкой записей на её время. Заполнение и проверка используют уже открытое соединение; отдельные подключения/вложенные транзакции для этих этапов не создаются. Используется явный поддерживаемый состав таблиц; произвольный список и неограниченный `CASCADE` не принимаются. Неизвестная прикладная таблица или неподдерживаемая зависимость требуют отказа до удаления записей. Для схемы `006` не поддерживаются пользовательские триггеры/правила, выражения вне поддерживаемой схемы `006` (включая defaults с sequence), дополнительные CHECK/exclusion constraints, индексы с выражениями/условиями и связи с таблицами вне заменяемого набора; полный журнал дополнительно сравнивается до коммита.
- Структура таблиц, индексы, функции, расширения, права и полный журнал `schema_migrations`, включая технические времена, сохраняются. Сбой очистки, заполнения или проверки откатывает весь новый набор и сохраняет прежние записи; в вывод не попадают данные и секреты.
- Первичное `db:dev-seed` продолжает отказывать при существующих записях. Обычный старт приложения не вызывает ни первичное заполнение, ни замену набора.

### Восстановление структуры внутри постоянной dev-БД

- Рабочая БД остаётся той же: имя, роль, endpoint и URL не меняются. Production не затрагивается. `DROP DATABASE`, `CREATE DATABASE`, служебное подключение, Neon reset/restore от production и копирование production с последующей очисткой не используются.
- Управляемая область — вся `public`: прикладные объекты, `schema_migrations` и экспериментальные таблицы/объекты. Неизвестное имя объекта внутри `public` само по себе не вызывает отказ: полный reset предназначен в том числе для удаления таких экспериментов. Для текущей цепочки поддерживается `uuid-ossp`: его объекты в `public` удаляются вместе с областью, расширение заново устанавливается обычным SQL `001`. Системные объекты и настройки уровня БД не сбрасываются.
- До очистки проверяются владение/права для восстановления `public`, установка поддерживаемых расширений и фактический состав объектов и зависимостей. Неподдерживаемые расширения, зависимости между `public` и объектами вне неё (в обе стороны), или несовместимый исходный SQL приводят к отказу до удаления. Учитываются транзитивные зависимости, включая правила представлений и принадлежность расширению. Независимые объекты других схем сохраняются; их наличие без такой зависимости само по себе не запрещает reset. `CASCADE` разрешён для всей `public`, но не для изменения внешних объектов. Новая миграция с объектами вне этой области требует явного расширения контракта восстановления, а не молчаливого неполного сброса. Поддержка исходного SQL задаётся проверенным fingerprint префикса: сейчас `001–006` из `259975c`. Другие commit с теми же байтами SQL допустимы; иной префикс требует отдельной проверки области и явного добавления поддержки до очистки, декларации генератора недостаточно.
- Очистка и создание пустой `public` с требуемым владельцем и правами выполняются в одной транзакции. Затем общий мигратор создаёт новый журнал и применяет исходные SQL до выбранной версии; исторический генератор заполняет таблицы и проверяет сохранённые записи. Владелец и необходимые права на `public` и созданные объекты задаются явно, без неявного расширения доступа; сама dev-роль сохраняется. Отдельные транзакции мигратора сохраняются; вся операция восстановления не объявляется атомарной.
- Пользователь обеспечивает остановку API и параллельной работы с dev до `--allow-reset`. Флаг разрешает потерю тестовых записей и структуры; он не заменяет проверку цели. Команды не завершают чужие процессы/соединения; advisory lock мигратора не объявляется общей блокировкой приложения. Проверяется отсутствие посторонних сессий до очистки; открытая приложением новая сессия во время восстановления не считается предотвращённой этой проверкой.
- До разрушительного этапа завершены проверка цели, подготовка исходника/проверок, инвентаризация управляемых объектов и проверка необходимых прав. Ошибка подготовки сохраняет существующую структуру и записи. Несовместимые права в Neon возвращают работу к согласованию; служебная БД или production-роль не вводятся запасным путём.
- После успешной очистки прежнее состояние автоматически не возвращается. При ошибке выводятся этап и прочитанное состояние структуры: пустая, достигнутая версия либо невозможность чтения. Недоступность соединения не объявляется удалением самой БД. Код завершения ненулевой; новый явный запуск заново восстанавливает известный исходник.

### Синтетические данные

- Три аккаунта с устойчивыми тестовыми email: пустой; обычный с привычками и месяцем записей; с привычками и двухлетней историей с пропусками. Конкретные email и состав привычек документируются вместе с генератором, без реальных адресов и production-записей.
- Заполненные профили вместе покрывают сон через полночь, неполные ночные времена, дневной сон и его отсутствие, выполненные/невыполненные/отсутствующие отметки, переходы месяцев и лет. Отдельный пример 29 февраля добавляется только при необходимости конкретной миграции.
- При первичном заполнении `--date` задаётся явно московским днём заполнения. История заканчивается этой датой и далее не сдвигается. Для репетиции фиксируется выбранная дата; старение исходного набора в повседневном dev допустимо.
- Одинаковые версия генератора и дата дают одинаковые предметные записи и устойчивые идентификаторы связей. Солёные хеши паролей, технические времена и токены не являются предметным критерием побайтовой воспроизводимости. Пароль читается из локальной конфигурации и хешируется обычным способом.
- Вход во все профили выполняется обычной формой email/пароль через настоящий API. Production-пароли, обход авторизации и автоматический вход не добавляются.
- Первичное заполнение выполняется транзакционно; ошибка не оставляет частично заполненный набор. `db:dev-seed` отказывает при существующих предметных данных; для их явной замены служит транзакционная `db:dev-reseed`. После восстановления структуры генератор запускается только после достижения совместимой схемы.
- Для каждого преобразования данных добавляются необходимые ему исходные примеры и независимые ожидаемые результаты. Проверяется состав пользователей, привычек, дат, отметок и сохранённых данных сна. Не вводится универсальная неизменность числа записей: конкретная миграция может создавать или объединять записи.

### Репетиция и выпуск

Именованный набор `--checks` объявляет поддерживаемый переход, проверку исходных записей, проверку конечной схемы/данных и сравнение состояния при повторном запуске. Отсутствие любого обязательного этапа или несовместимость перехода обнаруживаются до сброса. Это небольшой контракт тестового сценария вокруг команд, без новой платформы плагинов.

1. Проверить цель, аргументы, исходник, целевую цепочку и проверки; подготовить весь запускаемый код.
2. Восстановить управляемую структуру `public` в той же dev-БД, применить исходные SQL до `--from`, заполнить совместимыми данными с явной датой. Замена только записей через reseed для этого этапа недостаточна.
3. Проверить исходное состояние. Несовпадение останавливает репетицию до применения целевых SQL.
4. Применить целевую цепочку до `--to` общим мигратором.
5. Проверить ожидаемые схему, преобразование и сохранность данных прямым чтением сохранённых записей. Ответы API могут дополнять эту проверку, но не заменяют её.
6. Зафиксировать состояние данных и полного журнала, повторить применение до той же цели и проверить отсутствие изменений.
7. Вывести краткий безопасный итог; только все успешные этапы дают `0`. Dev остаётся на целевой версии. При ошибке сообщается достигнутое состояние, новая репетиция снова готовит исходник.

- Исходная версия соответствует фактической схеме перед выпускаемым переходом; она не вычисляется как «последняя минус один». Несколько новых SQL допустимо проверять вместе, если переход включает каждый выпускаемый файл.
- После изменения проверяемого SQL репетиция повторяется с восстановленного исходника. Применение уже записанной миграции на обновлённом dev не является повторной проверкой преобразования.
- Каждая новая SQL-миграция проходит проверку на постоянном dev перед выпуском. Для преобразования данных обязательны старые синтетические записи и проверка результата. Затронутые функции проверяются соответствующими тестами; ручного дублирования покрытых сценариев и отдельного отчёта допуска нет.
- Railway Pre-Deploy сохраняет существующую команду применения миграций из production-образа, production-подключения и переменные. Новая конфигурация разрешённой production-цели не требуется. Локальная `db:migrate` не получает production-переключатель; сборка и старт API сами SQL не применяют.
- При неудачном выпуске выясняется фактически применённая версия, исправление проверяется на dev и выпускается вперёд. Возврат приложения возможен только при совместимости с фактической схемой; автоматического отката БД нет.
- Изменение применённой миграции оформляется следующим SQL. Если ошибочен первый неприменённый файл, добавление следующего файла не разблокирует цепочку: исправление определяется по фактическому состоянию с сохранением контроля checksum и неизменности выпущенных SQL.

### Первый переход

1. Завершить реализацию команд, генератора и защит; подтвердить их поведение изолированными тестами. Не менять действующие секреты до готовности проверок.
2. Проверить фактический аккаунт Neon: выбранный проект, доступность schema-only root, квоты постоянной ветки, отсутствие автоудаления и возможность назначить отдельной dev-роли права на единственную рабочую БД, восстановление `public` и миграции с `uuid-ossp`, без `CREATEDB` и superuser. Секреты и персональные записи не включать в результаты проверки.
3. Создать schema-only root без строк production. Использовать единственную скопированную БД как рабочую dev-БД; новую прикладную или служебную БД не создавать. Создать отдельную dev-роль с новым паролем, передать ей необходимые права на эту БД и `public` только в dev-ветке. Скопированная современная структура очищается до исполнения исторических SQL.
4. Зафиксировать несекретные идентификаторы dev; сохранить direct/runtime подключения, dev JWT-секреты и тестовый пароль в игнорируемой локальной конфигурации. Production-секреты остаются в Railway.
5. Через `db:dev-reset` с совместимым сохранённым Git-исходником и явным московским днём запуска очистить скопированную `public`, собрать выбранную актуальную версию обычными SQL и заполнить её. Исходный префикс должен совпадать с SQL рабочей копии. Через `db:status` и проверку набора подтвердить версию/записи; журнал скопированной schema-only БД не выдаётся за применённую историю, baseline не выполнять.
6. Включить локальный web → API → dev, проверить обычный вход в три профиля, сохранение записи дня/отметки и сохранность изменения после перезапуска. Убедиться в отметке dev и безопасной диагностике цели.
7. Проверить явную замену тестовых данных с сохранением структуры/журнала, восстановление поддерживаемого сохранённого в Git исходника в той же БД и полный переход на синтетическом тестовом сценарии. Тестовый SQL механики не добавлять в выпускаемую цепочку только ради проверки инструментов.
8. Обновить руководство ежедневной работы и выпуска; передать результат реализации на человеческую приёмку по трекеру. Невозможность выбранного пути Neon или прав на управляемую структуру возвращается к решению, без обычного клона production, служебной БД и скрытой смены проекта.

## Testing Decisions

Применяется `write-tests`. Границы проверок соответствуют уже согласованным требованиям: backend-команды и мигратор через `node:test`, отдельные сценарии настоящего PostgreSQL, точечные web-проверки конфигурации и отметки dev. Поведение проверяется через результат команды, отказ до изменений, сохранённые записи и публичный UI; внутренние детали реализации не становятся контрактом тестов.

| Требование | Минимальная достаточная проверка |
| --- | --- |
| Отказ при чужой/неполной конфигурации | API-тесты загрузки и проверки конфигурации через fake подключения: нет соединения или записи при неверной цели, конфликте URL, pooled миграторе, отсутствующем env и одном `NODE_ENV=production`. Проверяются безопасные сообщения об ошибках. |
| Статус только читает | API-тест публичного status: отсутствующий журнал и несовместимая история; ни создание журнала, ни применение SQL не вызываются. Подтверждение read-only поведения на PostgreSQL в явном DB-прогоне. |
| Механика мигратора | Маленькие локальные SQL-fixtures с независимыми ожидаемыми результатами: порядок, checksum, журнал, префикс, повторный запуск. Настоящий PostgreSQL для транзакций, сохранения предыдущего успеха при сбое следующего SQL и сериализации конкурентных запусков. |
| Подготовка до сброса | API-тесты команд через fake операции: неправильный Git-ref, несовместимый набор, недоступный код/проверки, несовпадающий префикс, недостаточные права и неподдерживаемые расширения и внешние зависимости не вызывают очистки структуры; для reseed неизвестный состав таблиц не вызывает удаления данных. Извлечение из временного Git-fixture не меняет рабочую копию/index проверяемого репозитория. |
| Восстановление и репетиция | Явный PostgreSQL-прогон на разрешённой тестовой цели: известный исходник → данные → тестовый переход → ожидаемые записи → повторный запуск; несовпадение и ошибка каждого значимого этапа дают неуспех. Проверка восстановления `public` работает в отдельной заранее разрешённой изолированной тестовой БД: та же БД до/после, роль без `CREATEDB`/superuser, корректное восстановление владельца/прав и `uuid-ossp`, удаление экспериментальной таблицы, отказ до очистки при неподдерживаемом расширении или внешней зависимости, повтор после ошибки. Постоянный dev и его `public` при `db:test` не очищаются; временную тестовую БД готовит/убирает тестовый контур вне проверяемой команды. |
| Реальная цепочка и история | Отдельная сборка с нуля реальными SQL, целевые проверки реальных преобразований и сохранённые проверки исторического baseline. Они не заменяются механическими fixtures и не зависят от требования «всего шесть миграций». |
| Замена тестовых данных | API-тесты отказа до записи при неверной цели/истории/дате/пароле и неизвестном составе таблиц. Явный PostgreSQL-прогон подтверждает новый набор, одно соединение/одну транзакцию для очистки, заполнения и проверки, неизменность структуры и полного журнала и откат прежних записей при ошибке заполнения/проверки. |
| Генератор и вход | API-тесты известных предметных записей и воспроизводимости при одинаковой дате; явный PostgreSQL-прогон заполнения и проверки обычной авторизации. Пароль/хеши не публикуются в диагностике. |
| Dev-web | Web unit для разрешённого адреса API и отказа при внешнем адресе; web component для видимой отметки dev. Существующий `/test-api` контур и mocked E2E сохраняются. |
| Полнота образа | Сопоставление относительных имён и checksum всех упакованных SQL с исходниками именно проверяемой сборки: пропуск, лишний файл или изменение содержимого дают отказ. Количество файлов выводится из набора, не задаётся константой. |

- Предшественники: существующие API-тесты core/DB-мигратора, fake repositories backend, web Vitest/RTL и проверка production-образа в CI. Механические тесты отвязываются от реальных SQL и свободной версии `007`; проверки настоящей цепочки и принятой истории сохраняются отдельно.
- Обычные workspace tests не подключаются к Neon. DB-backed сценарии доступны явно через `db:test`; отсутствие настройки в этом запуске — ошибка, а не успешный пропуск. Временные тестовые схемы/БД очищаются в том числе после ошибки.
- Для реализации используются targeted API и web команды из testing guide; проверки imports/types и production-образа добавляются по затронутым границам. Обязательный DB-backed CI не вводится.
- При первом включении выполняется короткая ручная проверка реального локального пути и перезапуска. Для каждого последующего выпуска отдельное ручное дублирование покрытых тестами функций не требуется.
- Контракт API не меняется; генерация API-контракта требуется только если реализация обнаружит необходимое согласованное изменение его источника.

### Критерии приёмки перехода

- [x] Постоянный dev создан выбранным путём в нынешнем Neon-проекте без production-строк на любом этапе: одна рабочая БД в dev-ветке, отдельная dev-роль с новым паролем, без служебной БД и обязательного `CREATEDB`.
- [x] Разрешённые dev-идентификаторы проверяются независимо от URL; неправильная цель и конфигурация вызывают отказ до подключения, в том числе при локальном `NODE_ENV=production`.
- [x] Локальный web использует настоящий локальный API, отклоняет внешний адрес и показывает dev; API безопасно сообщает цель и использует отдельные dev JWT-секреты.
- [x] Первичное заполнение создаёт три согласованных профиля; обычный вход работает, данные сохраняются между запусками, автоматического сброса/переноса дат нет.
- [x] Команды статуса, применения, первичного заполнения, замены данных, восстановления структуры, репетиции и DB-тестов доступны из корня, имеют справку и соблюдают таблицу интерфейсов.
- [x] Status не меняет БД; применение сохраняет историю и данные; reseed транзакционно заменяет записи без изменения структуры и полного журнала; историческое восстановление заново создаёт управляемую `public` и журнал в той же БД, без выборочного удаления строк журнала и baseline.
- [x] Ошибки параметров, исходника, проверок, прав и неподдерживаемых объектов обнаруживаются до сброса; восстановление использует совместимый код из Git без изменения рабочей копии/index. Команды не удаляют БД и не используют служебное подключение; reset очищает также экспериментальные объекты внутри `public`, а зависимости за её пределами проверяет до очистки.
- [x] Полная репетиция проверяет исходник, ожидаемое преобразование сохранённых данных и повторный запуск; ошибка даёт ненулевой код, успех оставляет dev на целевой версии.
- [x] Механические SQL-тесты не зависят от числа реальных файлов/версии `007`; отдельные проверки реальной цепочки и исторического baseline сохранены; явный DB-прогон не маскирует отсутствие подключения пропуском.
- [x] Образ содержит точный набор SQL проверяемой сборки; следующая миграция не требует изменения фиксированного счётчика.
- [x] Railway Pre-Deploy, существующие production-подключения, секреты и принятая история сохранены. API и мигратор production работают без новых переменных Railway и обязательных `DB_EXPECTED_*`; правила проверки каждой новой миграции на dev и исправления вперёд документированы.
- [x] Выполнена короткая проверка реального локального пути; обновлены инструкции первоначальной настройки, ежедневной работы, сброса, репетиции и выпуска. Реализационные тикеты прошли предусмотренную трекером человеческую приёмку.

## Out of Scope

- Production-копии, включая временные, частичные, очищаемые после копирования и предназначенные для репетиции.
- Отдельный staging web/API, другой проект Neon как незаметная замена выбранного пути, другая СУБД/хостинг, постоянный локальный PostgreSQL и автоматическая БД для каждой агентской работы.
- Временные Neon-ветки для каждого прогона, автоматическая остановка чужих агентов и управление их процессами.
- Все исторические схемы и заранее заготовленные проверки любых будущих предметных миграций. Поддерживаются явно заявленные исходники и целевые сценарии.
- Реализация статистики, архивирования и изменения предметной семантики привычек/сна.
- Обязательный PostgreSQL в CI, отдельные ручные отчёты допуска к выпуску и дублирование покрытых тестами сценариев.
- Полное восстановление произвольных настроек уровня БД, неизвестных расширений и объектов вне поддерживаемой области `public`; дополнительные служебные БД для dev-команд.
- Автоматический production rollback/restore и система безостановочных выпусков. Действующая политика краткой несовместимости при Railway Pre-Deploy сохраняется.
- Независимый production guard с `DB_EXPECTED_*` и изменение переменных или настроек Railway ради подключения dev-БД.
