## Question

Как локальный путь web → API → БД выбирает dev-ветку Neon и исключает случайную запись в production при старте, миграции и восстановлении тестовых данных? Определить проверяемый признак целевой базы, согласованность pooled/direct адресов приложения и мигратора, отдельные секреты dev, поведение при недостающей/чужой конфигурации и безопасный способ видеть выбранное окружение без вывода секретов.

Не ограничиваться названием `NODE_ENV` или сменой одного URL: локальный web сейчас использует production API. Решить, какие локальные операции должны отказываться работать при неверной цели, а существующий Railway Pre-Deploy — продолжать выполнять production-миграции. Учитывать, что агенты могут параллельно работать с тестовыми данными, хотя изменения схемы идут по одному.

## Answer

Принято 2026-10-11: локальные web и API используют постоянную dev-ветку Neon; конфигурация задаётся через env. Локальные процессы проверяют выбранную цель и отказываются работать при отсутствующей или чужой конфигурации. Одного изменения URL или значения `NODE_ENV` недостаточно для защиты от случайной записи в production.

### Локальный путь

- Обычный путь разработки: web `http://localhost:5173` → API `http://localhost:8080` → постоянная dev-БД Neon. Адрес API задаётся web-конфигурацией, подключения к БД — API-конфигурацией.
- Dev-web проверяет адрес API и отказывается обращаться к внешнему API. Локальный путь поддерживается существующими CORS и refresh cookie; отдельный staging или прокси для него не требуются.
- Обычный запуск не применяет миграции, не заполняет и не сбрасывает данные. Изменения тестовых пользователей сохраняются между запусками.

### Проверяемая цель и отказ при ошибке

- Локальные команды запуска API, миграций, заполнения и восстановления данных привязаны к dev. SQL-тесты также проверяют разрешённую тестовую цель перед изменением БД.
- Ожидаемая цель задаётся отдельной несекретной конфигурацией: разрешённые runtime/direct хосты, имя БД и dev-роль. Ожидаемые значения не выводятся из URL, который проверяется; иначе случайная подстановка production URL одновременно подменит и эталон проверки.
- API использует pooled либо direct подключение к выбранной dev-БД. Мигратор использует direct подключение к той же БД и той же dev-роли. Если runtime и migration URL заданы, их цели должны быть согласованы; разные виды подключения не означают разные БД.
- Проверка URL выполняется до подключения и работы с БД. Отсутствующая конфигурация, неизвестный хост, неверная БД/роль, несогласованные runtime/direct цели или pooled URL мигратора приводят к понятному отказу. Production URL не служит запасным значением; предупреждение с продолжением работы и ручное подтверждение не заменяют проверку.
- `NODE_ENV=production` не является локальным способом обхода защиты. Production-миграции продолжают выполняться существующим Railway Pre-Deploy; его production-конфигурация проверяется отдельно, с согласованными runtime/direct целями.
- Эта защита предотвращает случайную ошибку конфигурации; административное разделение доступа не заменяется проверкой URL. Ранее принятое решение об отдельной dev-роли сохраняется.

### Секреты и диагностика

- Dev-секреты API хранятся в игнорируемом `apps/api/.env.local`; локальный адрес API — в web-конфигурации. Production-секреты остаются в Railway и не используются локальными процессами.
- Dev JWT-секреты и учётные данные БД отделены от production. Пароли, JWT, токены и полные строки подключения не попадают в Git, карту, отчёты или сообщения об ошибках.
- При старте выводятся выбранное окружение и безопасная идентичность цели (хост, имя БД и роль без секретов). В локальном интерфейсе отображается заметная отметка dev.

### Граница решения

Точные имена env-переменных, расположение несекретной конфигурации и команды фиксируются в последующей спецификации. Новое управление инфраструктурой ради выбора окружения не требуется: адреса/секреты задаются env, проверки выполняются кодом.

Выбор экземпляра и порядок репетиции, разрешённые временные цели, согласование сброса с параллельными агентами и автоматические проверки перед выпуском остаются в билете [«Репетиция миграции, сброс dev и выпуск в production»](05-migration-rehearsal-and-release.md). Допустимость временного Docker PostgreSQL как инструмента отдельных тестов, установленная картой, сохраняется; он также требует явной разрешённой тестовой цели.

Решение завершено на этапе планирования: env, код, БД и внешние настройки пока не изменялись.
