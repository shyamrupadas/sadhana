## Question

Как проверять одну серьёзную миграцию за раз: подготовить прежнюю схему с тестовой историей, применить тот же неизменённый SQL, проверить преобразование и повторный запуск, затем выпустить его существующим Railway Pre-Deploy? Выбрать между управляемым пересозданием постоянной dev-ветки и отдельным временным экземпляром Neon для репетиции; определить, что происходит с текущими тестовыми данными и параллельными агентами при сбросе.

Определить порядок при ошибке миграции в Railway Pre-Deploy, возврате Git на предыдущий коммит и применении миграции из незавершённой ветки; критерий разрешения выпуска. Учесть, что журнал и транзакции уже есть, откат приложения не откатывает БД, а транзакция каждой миграции не откатывает все предыдущие миграции цепочки. Не внедрять повторно исторический baseline.

Какие проверки обязательны автоматически, а какие выполняются при изменении схемы? В частности, CI сейчас проверяет ровно шесть SQL-файлов, а SQL-интеграционные тесты пропускаются без `MIGRATION_TEST_DATABASE_URL`; определить нужные изменения в рамках этой цели. Временный Docker PostgreSQL допустим как инструмент тестирования и не является альтернативой выбранной dev-ветке Neon.

### 2026-10-11 — Уточнение масштаба и объяснение вариантов

Пользователь попросил объяснить последствия всех трёх решений и распространённые практики: приложение небольшое, пользователей немного, сложный процесс уровня крупной компании нежелателен, безопасность важна. Это запрос контекста, а не согласие с предложениями первого раунда.

С учётом масштаба предложение по порогу Neon пересмотрено: автоматические SQL-проверки обязательны для всех миграций; отдельная репетиция Neon — для изменения/удаления существующих данных, изменения типов и ключей, новых ограничений на заполненных таблицах, потенциально долгих операций, изменений прав/расширений и любых сомнений в риске. Простые добавления независимых таблиц или необязательных полей без преобразования старых записей могут ограничиваться CI и проверкой в постоянном dev, если совместимы с действующим приложением. Классификация требует просмотра конкретного SQL, а не только имени команды. Временная ветка для рискованных репетиций и обязательный PostgreSQL в CI остаются предложениями.

Объяснены отдельные границы: ветка изолирует проверку, но не отменяет production-миграцию; успешный SQL не доказывает правильное преобразование; маленький синтетический набор не воспроизводит все аномалии/объём production; транзакция не отменяет успешно зафиксированную логическую ошибку; возврат приложения не откатывает БД. Перед рискованным выпуском нужен проверенный способ восстановления с известными ограничениями, который ещё предстоит согласовать. Наличие и параметры восстановления текущего Neon-проекта не проверены. Новых решений пока нет.

Для нового прогона прежний исходник можно восстановить пересозданием dev-БД с соответствующими миграциями и синтетическим набором. Ручные исправления dev не должны подменять SQL, который уйдёт в production.

Пользователь поставил под вопрос обязательный PostgreSQL в CI после успешной проверки на dev и указал на существующий отказ Railway выпускать приложение при ошибке миграции. Обсуждение различает защиту выпуска приложения и состояние БД: предыдущие миграции цепочки могут уже быть зафиксированы, а успешный SQL может содержать логическую ошибку. CI не является необходимым условием корректности уже проверенного неизменённого SQL; его дополнительная ценность — воспроизводимость и автоматическое обнаружение будущих регрессий мигратора/цепочки. Обязательность и объём SQL-проверок в CI пока не согласованы. Замена фиксированного числа SQL в проверке образа остаётся отдельным небольшим исправлением, необходимым для добавления следующей миграции.

### 2026-10-12 — Согласовано: сфокусированный рефакторинг управления БД

Пользователь согласовал удобные команды, воспроизводимое восстановление постоянного dev и тесты мигратора без привязки к шести историческим файлам. После ревью пользователь поручил переписать требования с учётом замечаний. Требования ниже включены в итоговое решение; реализация относится к последующей спецификации и реализационным тикетам.

#### Основа и сохраняемые свойства

- Нумерованные SQL-миграции и журнал остаются единственным источником структуры. Пустая БД собирается последовательным выполнением миграций; отдельный вручную поддерживаемый снимок актуальной схемы не добавляется.
- Сохраняются проверка порядка и контрольных сумм, отказ при изменении применённых SQL, пропуск зарегистрированных файлов, отдельная транзакция каждого SQL вместе с записью в журнале, блокировка конкурирующих миграторов и таймауты. Выпущенные SQL и принятая история production не переписываются.
- Подготовка БД до выбранной версии и применение следующих миграций используют один мигратор с одинаковыми проверками. Целевая версия задаёт конец последовательного префикса SQL, а не произвольный список файлов. Обновление существующей БД выполняется вперёд; возврат dev на прежнюю версию выполняется пересозданием, а не удалением строк журнала или обратным SQL.
- Репетиции выполняются на постоянной dev-БД Neon; потеря её тестовых данных при явном восстановлении допустима. Пользователь обеспечивает остановку работы других агентов и локальных процессов с этой БД на время сброса и репетиции. Блокировка мигратора сама по себе не останавливает API. Временный Docker PostgreSQL остаётся инструментом отдельных проверок.

#### Команды и конфигурация

- Предоставить небольшой набор команд, доступных из корня репозитория, с единым способом загрузки конфигурации и понятной справкой. Рабочие имена ниже; точные аргументы и расположение кода определяются в спецификации.
- Локальные команды используют явно проверенную dev-цель и ранее согласованную защиту окружений. Миграции используют direct-подключение. Отсутствующая или чужая конфигурация приводит к отказу до изменения БД; полные URL и секреты не выводятся.
- `db:status` — операция только чтения: показывает безопасную идентичность цели, применённые и ожидающие миграции, отсутствие журнала и расхождения порядка/контрольных сумм. Не создаёт журнал, не применяет SQL и не исправляет расхождения. Обнаруженная несовместимость возвращает ненулевой код завершения.
- `db:migrate` применяет новые миграции к существующему dev через общий мигратор. Не сбрасывает БД и не заполняет её данными; повторный запуск сверяет журнал и пропускает уже применённые файлы. Production продолжает обновляться существующим Railway Pre-Deploy из собранного образа, без локального обхода защиты dev-команд.
- `db:dev-reset` явно пересоздаёт только выбранную dev-БД, применяет миграции до выбранной версии и затем заполняет её совместимым синтетическим набором. Команда требует явного указания операции сброса, версии исходника и опорной даты; обычный запуск разработки никогда её не вызывает.

#### Поддерживаемый исходник и восстановление dev

- Воспроизводимый исходник включает Git-версию миграций и совместимого генератора/набора, конечную версию схемы и опорную дату. Одни и те же входные данные воспроизводят одинаковые предметные записи по решению «Тестовые пользователи и воспроизводимая история».
- Поддерживаются версии, для которых в Git имеется совместимый генератор или целевой тестовый набор. Поддержка заполнения всех исторических схем задним числом не требуется. Текущий генератор не считается автоматически совместимым с прежней схемой.
- До удаления БД проверяются разрешённая цель, корректность параметров, доступность исходного SQL и генератора/набора, их заявленная совместимость с выбранной версией, необходимые настройки заполнения и возможность запуска подготовленного кода. Недоступный или неподдерживаемый исходник приводит к отказу с сохранением текущей dev-БД. Заполнение начинается только после достижения выбранной версии схемы.
- Выбор исторического исходника не меняет текущую рабочую копию и Git index. Конкретный способ получения кода из Git определяется в спецификации.
- При ошибке после начала пересоздания команда возвращает неуспех и сообщает этап и фактически достигнутую версию без секретов. Пересоздание и заполнение не обещают атомарного восстановления прежнего dev; повтор операции должен позволять заново получить известный исходник.

#### Репетиция перехода

- Каждая новая SQL-миграция проверяется на постоянном dev перед выпуском в production, независимо от её предполагаемой сложности. Для преобразования данных проверяется переход с записей прежней версии, а не только работа конечной схемы. Несколько новых SQL могут проверяться одной репетицией фактического перехода, если в неё входит каждый выпускаемый файл.
- `db:rehearse` получает явно заданные исходную и целевую версии, воспроизводимый синтетический исходник и проверки результата конкретного перехода. Поскольку команда пересоздаёт постоянный dev, разрешение сброса указывается явно и не заменяет проверку dev-цели.
- До сброса проверяются входные параметры, доступность исходника и проверок, корректность целевой цепочки и совпадение её исходного префикса с выбранной прежней версией. Целевая версия должна быть новее исходной. Первая ещё не выпущенная миграция и исходник выбираются для фактического перехода, который предстоит production; автоматически считать исходником «последнюю версию минус один» нельзя.
- Порядок: восстановить прежнюю схему → заполнить совместимыми синтетическими данными → проверить исходное состояние → применить целевые SQL → сверить ожидаемое преобразование и сохранность данных → повторно запустить мигратор и проверить отсутствие дополнительных изменений данных и журнала.
- Ожидаемый результат задаётся для конкретной миграции; универсальная команда не выводит его из SQL. Проверки учитывают сохранённые записи, а не только ответы API. Если миграция намеренно меняет число записей или другие свойства, проверяется согласованный результат, а не универсальное требование неизменности.
- Полная репетиция считается успешной только после всех проверок. Отсутствие необходимых проверок обнаруживается до сброса; несовпадение результата или ошибка любого этапа дают ненулевой код завершения. Успешное исполнение SQL само по себе не означает успешную репетицию.
- Команда автоматически выводит краткий итог и диагностику для разбора ошибок: безопасную идентичность цели, версии перехода и результат проверок. Допускается проверка SQL из текущей рабочей копии. После изменения проверенного SQL переход повторяется с восстановленного исходника.
- После успешной репетиции dev остаётся на целевой версии для дальнейшей разработки и проверки функции. После ошибки сообщается фактически достигнутое состояние; новая репетиция снова готовит исходник. Ручные исправления dev не подменяют миграции, которые будут выпущены в production.

#### Условие выпуска

Миграция допускается к выпуску после успешной проверки перехода на постоянном dev: тесты подтверждают ожидаемую схему и данные, а повторный запуск не вносит дополнительных изменений. Работа затронутых функций проверяется соответствующими тестами; отдельное ручное дублирование покрытых ими сценариев не требуется. Отдельный отчёт или запись результатов в тикете/PR не являются условием выпуска. Существующие проверки CI и контроля SQL продолжают работать без дополнительного ручного этапа допуска.

#### Тесты и упаковка SQL

- Общие тесты механики мигратора используют небольшие локальные SQL-fixtures с независимыми ожидаемыми результатами. - Проверка сборки реальной цепочки с нуля и целевые проверки преобразования данных остаются отдельными сценариями с соответствующими исходниками. Отвязка механических тестов от настоящего SQL не должна удалять эти проверки или ослаблять защиту принятой истории.
- Проверки, требующие настоящего PostgreSQL, доступны для явного запуска на разрешённой тестовой цели с предусмотренными подготовкой и очисткой. Такой запуск должен отказать при отсутствии подключения, а не сообщать успешную проверку после пропуска DB-backed сценариев.
- В проверке production-образа заменить требование «ровно шесть SQL» сверкой набора файлов и их содержимого с исходниками проверяемой сборки. Добавление новой миграции не требует вручную менять ожидаемое число, а отсутствующий или изменённый SQL приводит к отказу проверки.
- Обязательный PostgreSQL в CI отложен и не является условием перехода на dev-БД. Рефакторинг тестов не вводит это требование автоматически.

#### Исторический baseline

- Отделить одноразовую операцию принятия существующей production-БД от повседневных команд, сохранив её необходимые проверки и принятую историю. Новая dev-БД собирается обычными миграциями; baseline не используется для подготовки или починки dev и не выполняется повторно в production.

#### Границы согласования

Условие выпуска сведено к успешной проверке перехода и ожидаемого результата тестами, без отдельных ручных проверок и отчётности. ## Answer

Принято 2026-10-13. Требования из раздела «Согласовано: сфокусированный рефакторинг управления БД» входят в итоговое решение.

Для преобразований готовится прежняя схема с совместимыми синтетическими данными, проверяются ожидаемый результат и повторный запуск. - Пересоздание dev выполняется явно, потеря тестового состояния допустима. Пользователь контролирует остановку параллельной работы с этой БД. При возврате Git к прежней схеме или отказе от незавершённой миграции dev пересоздаётся до поддерживаемой версии с совместимым набором; строки журнала вручную не удаляются. Обычный запуск ничего не сбрасывает.

Существующие программные проверки сохраняются; обязательный PostgreSQL в CI отложен. Проверка образа должна сверять SQL с исходниками вместо фиксированного числа шесть.

При неудачном выпуске принято **исправление вперёд**: выяснить фактически применённое состояние, устранить причину, проверить исправление на dev и повторить выпуск. Автоматическое восстановление БД к прежнему состоянию не выполняется. Возврат прежнего приложения допустим при совместимости с фактической схемой.
