## Question

Как получить постоянную dev-ветку с пустой исходной БД и отдельными учётными данными, не копируя production-записи ни на одном шаге? После исследования выбор стал конкретным: schema-only root-ветка в нынешнем проекте с новой пустой БД внутри неё либо исходная dev-ветка отдельного проекта Neon. Первый путь копирует только структуру/роли без строк, но миграции должны собирать новую пустую БД; второй не наследует структуру и роли production, но требует дополнительного проекта.

Согласовать путь, роль и разделение секретов, допустимость копирования одной структуры без записей, базовую схему из неизменённых SQL и отсутствие необходимости исторического baseline. Уточнить доступность выбранного способа на действующем тарифе при реализации; это вопрос фактов аккаунта, а не просьба к пользователю угадывать квоты. Не создавать обычную копию production с последующей очисткой.

## Answer

Принято 2026-10-11: постоянная dev-ветка находится в нынешнем проекте Neon рядом с production. Локальный API и мигратор используют одну отдельную dev-роль. Второй проект и разделение dev-доступа на runtime/migrator-роли не требуются для текущего перехода.

### Исходное состояние

- Путь создания без production-записей: schema-only root-ветка → новая совершенно пустая dev-БД внутри неё → обычные неизменённые SQL-миграции проекта → синтетические данные. Копирование структуры допустимо; копирование production-строк с последующей очисткой запрещено.
- Скопированная современная схема не служит основанием для запуска исторических преобразований. Новая пустая БД обеспечивает воспроизводимую сборку и заполнение `schema_migrations` самим мигратором; исторический baseline не нужен.
- У постоянной dev-ветки не должно быть автоматического удаления. Наличие квот и доступность schema-only проверяются при реализации; невозможность выбранного пути требует возвращения к решению, а не скрытой подмены обычным клоном production.

### Доступы

- Одна новая dev-роль создаётся только в dev-ветке, с собственным паролем и правами, достаточными для API и миграций выбранной dev-БД. Локальные процессы не используют унаследованные production-роли или production-пароли.
- Мигратор подключается через direct URL; API может использовать pooled URL той же БД и той же dev-роли. Два вида подключения не означают две роли.
- Dev-секреты отделены от production-секретов и не попадают в Git, карту или отчёты. Конкретное хранение конфигурации, проверка целей команд и отказ при ошибочной конфигурации относятся к билету [«Выбор dev-окружения и защита локальных команд»](04-environment-routing-and-guards.md).

### Основание выбора и границы

Один проект упрощает повседневное управление; ветки уже изолируют изменения БД. Цена выбранного пути — дополнительная пустая БД при первоначальной настройке и общие настройки/квоты уровня проекта. Для нынешнего масштаба отдельное административное разделение проектов и ограничение DDL отдельной runtime-ролью не выбраны.

Состав синтетических данных определяется в билете [«Тестовые пользователи и воспроизводимая история»](03-synthetic-fixtures.md); восстановление состояния и временный экземпляр для репетиции — в билете [«Репетиция миграции, сброс dev и выпуск в production»](05-migration-rehearsal-and-release.md). Тариф, права роли на `uuid-ossp` и фактические настройки аккаунта ещё не проверены. Решение принято на этапе планирования; внешние ресурсы и конфигурация не изменялись.
