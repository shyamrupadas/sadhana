## Question

Какой воспроизводимый набор полностью тестовых пользователей, привычек и записей дня нужен для повседневной разработки и репетиций миграций? Согласовать обычные и граничные сценарии, короткую и длинную историю, способ входа, привязку дат к текущему дню, восстановление исходного состояния и набор проверяемых инвариантов до/после миграции.

Пользователь запретил копирование production даже для репетиций. Несколько заполненных дней не доказывают корректность миграции на длинной истории; определить минимальное достаточное покрытие без имитации всех будущих предметных миграций. Обсудить, какая версия набора соответствует прежней схеме, чтобы репетиция действительно проверяла преобразование существующих записей, а не только создание пустых таблиц или заполнение уже новой схемы.

## Answer

Принято 2026-10-11: постоянная dev-БД первоначально заполняется один раз полностью синтетическими данными трёх тестовых пользователей. Генератор хранится вместе с кодом и позволяет воспроизвести известный исходный набор для проверки миграций. Копии production не используются.

### Пользователи и сценарии

- Пустой профиль: заранее созданный аккаунт без привычек и записей дня, для проверки начала работы после входа.
- Обычный профиль: привычки и месяц недавних записей дня.
- Профиль с длинной историей: привычки и два года записей с пропусками дней.
- Заполненные профили вместе покрывают сон через полночь, неполные ночные времена, дни с дневным сном и без него, отметки «выполнено», «не выполнено» и отсутствие отметки, переходы месяцев и лет.
- Набор соответствует действующей схеме и поведению приложения. Архивирование привычек и изменения семантики удаления не добавляются в рамках этого перехода. Двухлетний диапазон не гарантирует наличие 29 февраля; при необходимости конкретная миграция получает отдельный целевой пример такого календарного случая.

### Вход

Все три аккаунта создаются при первоначальном заполнении. Вход выполняется обычной формой email/пароль через настоящий API. Один отдельный тестовый пароль задаётся локально при заполнении и хранится вне Git; обход авторизации не требуется. Пароль, токены и строки подключения не публикуются в тикетах или отчётах.

### Повседневное состояние dev

При первоначальном заполнении история заканчивается московским днём запуска генератора. После этого даты не сдвигаются и набор автоматически не перезаписывается. Добавленные через приложение записи, изменения привычек и другие обычные изменения сохраняются между запусками разработки.

Старение начальных записей допустимо: после их выхода из пятидневного окна ежедневного учёта свежие данные вводятся обычным способом. Восстановление исходного набора при необходимости — отдельная явная операция; оно не является частью обычного запуска разработки.

### Воспроизводимость и исходник миграции

- Одинаковая версия генератора и явно указанная опорная дата воспроизводят одинаковые исходные предметные записи. Для первоначального dev заполнения опорная дата — день запуска; для повторения известного исходника дата задаётся явно. Это правило запуска генератора, а не отдельный постоянно обновляемый режим dev.
- Версия генератора хранится в Git вместе с соответствующей версией схемы. Для будущей миграции исходный набор готовится под прежнюю схему и её семантику; после заполнения применяется проверяемая миграция. Наполнение уже новой схемы не заменяет проверку преобразования существующих записей.
- Под конкретную миграцию добавляются необходимые ей целевые примеры и ожидаемый результат. От текущего универсального набора не требуется заранее имитировать все будущие предметные миграции или все исторические форматы.
- Набор должен позволять сверить состав пользователей, привычек, дат, отметок и данных сна с известным исходником, затем проверить сохранение данных и именно ожидаемое преобразование. Число записей дня не считается универсально неизменным: миграция может намеренно создавать или объединять записи. Для преобразований сна проверяемый результат учитывает сохранённые данные, поскольку API может пересчитывать длительность при чтении.
