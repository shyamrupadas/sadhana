# Dev-ветка Neon без production-данных

Проверено 2026-10-10 по официальной документации Neon и исходникам Sadhana. Исследование не использовало аккаунт Neon, секреты, подключения к БД или пользовательские записи; внешние ресурсы не создавались. Это факты и предложение для обсуждения, а не выбранное инфраструктурное решение.

## Создание

Обычная ветка Neon наследует схему **и данные** источника; изменения в ней не изменяют источник. Создание без явно заданного родителя использует default-ветку проекта. Обычная ветка от production с последующей очисткой нарушает требование пользователя уже при создании. [Manage branches](https://neon.com/docs/manage/branches).

**Schema-only** копирует структуру без строк во всех таблицах всех БД, включая `schema_migrations`. Получается самостоятельная root-ветка без родителя и общей истории. Функция отмечена Beta; документирован Console и API `branch.init_source: "schema-only"` вместе с явно заданным `parent_id`. [Schema-only branches](https://neon.com/docs/guides/branching-schema-only).

CLI документирует `neon branches create --schema-only`. В руководстве schema-only осталась противоречащая этому фраза о будущей поддержке CLI; при реализации проверить установленную версию и `--help`, не предполагать доступность флага. [CLI branches](https://neon.com/docs/cli/branches).

В проверенном публичном интерфейсе не найден документированный способ создать произвольную **пустую root-ветку** существующего проекта: root-типы перечислены как исходная ветка проекта, schema-only и backup. Это ограничение подтверждённого интерфейса, не утверждение о невозможности внутреннего API. [Branch types](https://neon.com/docs/manage/branches#root-branch).

Есть два подтверждённых пути к пустой БД для мигратора:

| Путь | Что даёт | Дополнительная работа |
| --- | --- | --- |
| Schema-only root-ветка в нынешнем проекте → новая пустая БД внутри неё | Нет production-строк; остаётся одна постоянная dev-ветка в нынешнем проекте | Создать отдельную dev-роль; скопированную схему не использовать как миграционное основание |
| Новый проект Neon с исходной root-веткой, названной dev | Отдельная исходная БД и роли без наследования production; дочерние ветки только от тестовой основы | Дополнительный проект и его настройки |

Neon поддерживает создание/удаление БД внутри выбранной ветки через Console, API и SQL. Для гарантированно пустого основания подходит `CREATE DATABASE … TEMPLATE template0`; это предложение для реализации, команду здесь не выполняли. [Manage databases](https://neon.com/docs/manage/databases), [PostgreSQL CREATE DATABASE](https://www.postgresql.org/docs/current/sql-createdatabase.html). Новый проект создаёт свою root-ветку, БД и роль, не являясь клоном другого проекта. [Manage projects](https://neon.com/docs/manage/projects).

## Почему schema-only недостаточно для миграционной истории

По [мигратору проекта](../../../apps/api/src/db/migrate.ts) обычный `apply` исполняет всё, чего нет в журнале, сверяя последовательность и SHA-256. Если `schema_migrations` вообще отсутствует, но `users` уже существует, он останавливается. Если таблица журнала скопирована schema-only и пуста, эта защита не срабатывает: мигратор считает `001–006` неприменёнными.

По SQL проекта [001](../../../apps/api/src/db/migrations/001_create_users_table.sql)–[002](../../../apps/api/src/db/migrations/002_create_habits_and_daily_entries.sql) создают таблицы с `IF NOT EXISTS`, [003](../../../apps/api/src/db/migrations/003_fix_daily_entries_primary_key.sql) удаляет именованный `daily_entries_pkey` и заново добавляет составной PK, [005](../../../apps/api/src/db/migrations/005_migrate_bedtime_to_previous_day.sql) переносит bedtime между днями, [006](../../../apps/api/src/db/migrations/006_set_duration_min_null_for_missing_times.sql) меняет JSON-поля. Запуск старых преобразований на современной структуре не равен сборке исторической схемы. С пустыми таблицами некоторые проблемы не проявятся; после seed повторное `005` способно менять уже современные записи. Поэтому нельзя ни засевать такую БД перед историческим `apply`, ни считать успешный запуск доказательством истории.

Режим `baseline-confirmed-001-006` предусмотрен для проверенной существующей схемы и данных и записывает историю ретроспективно без исполнения SQL. Для новой dev-БД проще **пустая БД → обычный мигратор `001–006` → seed современной формы**; baseline здесь не нужен. Для репетиции будущей миграции нужно состояние *предыдущей* версии и синтетические случаи, затем переход новой миграцией; сборка сразу конечной схемы проверяет другое.

## Роли и подключения

Обычное ветвление наследует роли и пароли; schema-only также копирует роли. Изоляция hostname сама по себе не делает общий пароль безопасным: подстановка production-host может открыть production. Для dev нужны отдельная роль и новый пароль, существующие только на dev; не выдавать локальным процессам унаследованный production-пароль. Роли и сброс паролей ограничены веткой; создание через SQL позволяет выдавать права явно, а Console/API автоматически дают членство `neon_superuser`. [Manage branches](https://neon.com/docs/manage/branches), [Manage roles](https://neon.com/docs/manage/roles).

Protected production на платных тарифах генерирует новые пароли при создании веток от него. Это дополнительная возможность, а не замена отдельной dev-роли; конкретное поведение schema-only credentials надо проверить при создании, не предполагать. [Protected branches](https://neon.com/docs/guides/protected-branches).

Для `MIGRATION_DATABASE_URL` нужен **direct** URL: мигратор держит сессионный `pg_advisory_lock`, а transaction pooling Neon не поддерживает сессионные advisory locks. Сам мигратор отвергает hostname с `-pooler` и порт 6432. Runtime может использовать pooled URL той же dev-БД; обе строки должны указывать один dev endpoint/database. [Connection pooling](https://neon.com/docs/connect/connection-pooling).

## Восстановление и срок жизни

Schema-only root нельзя сбросить через reset-from-parent. **Restore** из другой ветки переносит и схему, и данные; restore из production запрещён условиями карты. [Schema-only branches](https://neon.com/docs/guides/branching-schema-only). Reset обычной дочерней ветки тоже полностью заменяет её схемой и данными родителя; разрешён только заведомо тестовый источник. [Reset from parent](https://neon.com/docs/guides/reset-from-parent).

Варианты внутри разрешённой схемы: пересоздавать только dev-БД и выполнять мигратор/seed; либо хранить тестовую основу и сбрасывать её дочернюю dev-ветку; либо восстанавливать собственную тестовую историю в пределах history window. При пересоздании всей ветки потребуется заново получать endpoint/credentials. Restore может создавать backup-ветки, расходующие root allowance; это не бессрочное хранилище эталонного seed. [CLI restore](https://neon.com/docs/cli/branches#restore), [Branch types](https://neon.com/docs/manage/branches#backup-branch).

При создании через Console по умолчанию включено удаление через 1 день: **у постоянной dev-ветки expiration отключить явно**. Для временной репетиции можно задать TTL. [Manage branches](https://neon.com/docs/manage/branches).

## Лимиты и расходы

Публичная документация сейчас указывает Free: 10 веток/project, 100 CU-hours/project/месяц и 1 GB/project; Launch: 10 включённых веток, $0.106/CU-hour; Scale: 25 веток, $0.222/CU-hour. Платное storage — $0.35/GB-month; дополнительные child-ветки — $1.50/branch-month с почасовым расчётом. Scale-to-zero прекращает compute-начисления в простое, но постоянная ветка продолжает хранить данные. History: Free до 6 часов/1 GB изменений, Launch до 7 дней, Scale до 30; это не гарантированные сроки выбранного проекта. [Neon plans](https://neon.com/docs/introduction/plans).

Специальное руководство schema-only указывает root allowances Free/Launch/Scale **3/5/25**, максимумы storage schema-only **1/3/20 GB**; эти специальные лимиты проверять отдельно от общих обещаний unlimited storage платного тарифа. Аккаунт, legacy-тариф, действующая загрузка и доступная квота не исследовались; итоговую стоимость обещать нельзя. [Schema-only allowances](https://neon.com/docs/guides/branching-schema-only#schema-only-branch-allowances).

## Минимум для следующего решения

Предложение: одна постоянная dev-ветка, отдельная dev-роль, пустая dev-БД, обычные SQL-миграции и воспроизводимый синтетический seed; первый путь таблицы сохраняет нынешний проект. Новый проект — альтернатива, если нужна административная изоляция или нежелательно копирование структуры/ролей. Оба пути остаются Neon. Способ репетиции — управляемое пересоздание dev-БД либо краткоживущий экземпляр от тестовой основы — ещё требует согласования; исследование его не выбирает.

Небольшой seed проверит заданные правила преобразования, но не докажет время миграции, блокировки и отсутствие неизвестных аномалий на объёме production. Docker PostgreSQL остаётся обычным инструментом сложных тестов, без отдельного инфраструктурного решения.
