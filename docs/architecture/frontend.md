# Frontend Architecture

Status: stable

[ADR-0001](../adr/0001-frontend-layers.md) фиксирует выбор трех слоев фронтенда. Этот документ описывает их текущие ответственности и интерфейсы модулей. При изменении архитектуры поддерживай его согласованным с `eslint.boundaries.js`.

## Слои

- `src/app/`: запуск приложения, провайдеры, маршрутизация, защита маршрутов и композиция фич.
- `src/features/<feature>/`: страницы, состояние и поведение одного пользовательского сценария. Сейчас есть фичи `auth` и `main`.
- `src/shared/`: общий UI, API-инфраструктура, модели сессии и маршрутов, общие утилиты.

Расширяй структуру внутри этих слоев, когда появляется конкретная ответственность. Новый верхнеуровневый слой требует пересмотра ADR-0001.

## Зависимости и интерфейсы

- `shared` не импортирует `features` и `app`; `features` не импортирует `app`.
- `app` собирает фичи. Зависимости между фичами должны быть редкими и проходить через публичный интерфейс импортируемой фичи.
- Извне фичу импортируют через `index.ts`, `index.tsx` или маршрутный `*.page.tsx`. Файлы внутри одной фичи могут импортировать ее внутренние файлы напрямую.
- Внутренние `ui`, `model`, `lib` и `api` фичи остаются деталями реализации. Внешний интерфейс должен быть небольшим и намеренным.

`eslint.boundaries.js` сейчас проверяет направление зависимостей и входные точки фич. Сверяй другие утверждения об автоматических ограничениях с действующим lint-конфигом.

## Развитие модулей

Выбирай самую простую структуру, при которой модуль остается понятным:

1. Один файл для небольшого экрана или поведения.
2. Плоские соседние файлы, когда у helper, теста или дочернего UI появляется отдельная ответственность.
3. Группы `ui`, `model`, `lib` или `api`, когда плоскую структуру становится трудно читать.
4. Внутренние подмодули, когда фича объединяет несколько связанных сценариев с полезным общим интерфейсом.

Тесты и вызывающий код должны использовать публичный интерфейс модуля. Вводи новую точку разделения только при реальной вариативности или отдельной ответственности.

## Архитектурные изменения

При переносе без изменения поведения сохраняй маршруты и параметры, ключи запросов и хранилища, HTTP-вызовы, OpenAPI-контракт и сгенерированные файлы, видимое поведение и дизайн. Переноси по одной точке разделения модулей и обновляй импорты через их интерфейсы. Намеренное изменение поведения фиксируй отдельно от структурного переноса.
