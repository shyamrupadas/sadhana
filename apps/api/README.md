# Sadhana API

SQL-миграции 001–006 и принятая production-история сохранены. Обычный запуск API не применяет миграции, не создаёт пользователей и не сбрасывает данные.

## Локальный dev

Локальный путь: `http://localhost:5173` → `http://localhost:8080` → отдельная dev-БД. Web использует настоящий API (`VITE_USE_MOCKS=false`) и показывает отметку DEV. Другой адрес, учётные данные в URL или включённый MSW останавливают dev-web до API-запросов. Контур тестов запускается отдельно в режиме Vite `test` с `/test-api`.

В `config/database-targets.json` зафиксирована постоянная schema-only ветка `dev` нынешнего Neon-проекта `sadhana-tracker`: точные direct/runtime хосты, порт, единственная рабочая БД `neondb` и отдельная роль `sadhana_dev`. Это несекретные идентификаторы, которые сохраняются в Git и сверяются независимо от URL. Runtime использует разрешённый pooled-хост либо direct; мигратор — только direct. Служебная БД, её URL и право `CREATEDB` не нужны. Первоначальную сборку скопированной схемы выполняют явной командой reset ниже; обычный старт этого не делает.

Полный сценарий нового ноутбука — в [корневом README](../../README.md#новый-ноутбук-или-чистый-clone). Восстановите `apps/api/.env.dev.local` из Bitwarden либо создайте из шаблона и заполните по комментариям. Существующий настроенный файл не перезаписывайте:

```sh
cp -n apps/api/.env.example apps/api/.env.dev.local
chmod 600 apps/api/.env.dev.local
```

`.env.dev.local` игнорируется Git. Путь к файлу и конфигурации цели определяется относительно пакета API, независимо от текущего каталога. Dev-файл обязателен: оба URL и оба JWT-секрета должны быть заданы в нём. Унаследованные секреты не используются как запасные значения. Шаблон использует `sslmode=verify-full` (также разрешены `require` и `channel_binding=require`). Остальные query-параметры, включая `host`, `database`, `user`, `options`, отклоняются; отключение TLS через URL запрещено.

Пароль БД уже входит в `DATABASE_URL` и `MIGRATION_DATABASE_URL`; отдельно дублировать его в коде не требуется. В этом же локальном файле хранятся отдельные `JWT_SECRET`, `JWT_REFRESH_SECRET` и `DEV_FIXTURE_PASSWORD` для трёх тестовых профилей. Для резервной копии используйте менеджер паролей; не публикуйте полный URL или env-файл в тикетах, логах и скриншотах. Production-секреты остаются в Railway.

Из корня: `pnpm dev` запускает web и API, `pnpm dev:api` — API, `pnpm dev:web` — web. API по умолчанию слушает порт 8080. Локальные API-entrypoints `dev`, `start` и `migrate` фиксируют `DB_ENVIRONMENT=dev`: конфликтующее значение приводит к отказу. `NODE_ENV=production` не выбирает production-конфигурацию и не отключает защиту цели. При старте выводятся окружение, хост, БД и роль; URL и секреты в диагностику не попадают.

Обычные CORS, вход по email/паролю и refresh cookie локального пути сохраняются. Перезапуск не меняет записи. Полноценный вход в постоянный dev и сохранность изменений проверяются при включении ежедневной разработки (тикет 08).

## Ежедневная работа

Запустите `pnpm db:status`, затем `pnpm dev` из корня и откройте `http://localhost:5173`. Проверьте отметку DEV и dev-цель в стартовой диагностике API. Входите обычной формой в один из [трёх синтетических профилей](#синтетические-dev-профили), используя локальный `DEV_FIXTURE_PASSWORD`.

При ожидающих SQL примените их явно через `pnpm db:migrate`. Обычный запуск сохраняет текущие изменения. История может стареть: её даты не сдвигаются при старте. Для нового набора используйте reseed с явной датой; для восстановления структуры — reset из совместимого Git-исходника. Перед reseed/reset/репетицией остановите API, web и другую работу с dev. При отказе из-за оставшихся сессий установите их источник и дождитесь закрытия; команды не завершают чужие соединения.

## Первоначальная настройка Neon

Постоянная ветка [dev](https://console.neon.tech/app/projects/old-hill-95915061/branches/br-dry-dew-agidrqr3) создана 2026-10-17 как `Schema-only`, без родителя, с `Expires: Never`. Не создавайте её повторно и не используйте restore/reset от production. Единственная рабочая БД — `neondb`; дополнительная прикладная или служебная БД не нужна. История настройки и проверок находится в [тикете 07](../../.scratch/database-environments/issues/07-neon-development-provisioning.md).

При повторении настройки ресурсов сначала проверьте доступность schema-only, root-квоту и общие лимиты выбранного проекта; отключите автоудаление до Create. Отсутствие выбранного режима или нужных прав требует остановки и согласования, без обычного клона production. Создавайте dev-роль через SQL **с новым паролем сразу**, до передачи ей владения БД: у роли без пароля SQL Editor не сможет подключиться после смены владельца, а Console Reset не задаёт её первый пароль. Не используйте скопированные роли для локальных команд. У `sadhana_dev` должны быть LOGIN, владение `neondb` и `public`, возможность установки доверенного `uuid-ossp`, но не CREATEDB, superuser или членство в `neon_superuser`. [Правила ролей Neon](https://neon.com/docs/manage/roles#manage-roles-with-sql).

Перед первым заполнением остановите API и другую работу с dev, подготовьте локальный env и проверьте совпадение SQL рабочей копии с сохранённым совместимым Git-исходником. Текущий генератор поддерживает схему `006` и записывает московское время в формате HTTP-контракта `YYYY-MM-DD HH:mm`. В примере `HEAD` выбирает последний коммит: генератор и SQL должны быть сохранены в нём, незакоммиченные изменения reset не использует. Пример первого запуска с московским днём 2026-10-17:

```sh
pnpm db:dev-reset --allow-reset --source-ref HEAD --to 006 --date 2026-10-17
pnpm db:status
```

Дата всегда задаётся явно; при первом заполнении используйте фактический московский день запуска. Reset проверяет цель, исходник, права, расширения, зависимости `public` и отсутствие чужих сессий **до очистки**. Отказ на этапе подготовки сохраняет прежнюю структуру: выясните причину, не отключайте guard. Настройки прав по умолчанию внутри `public` относятся к очищаемой схеме; зависимости за её пределами запрещены. Успех создаёт новый журнал обычными SQL и проверяет все сохранённые синтетические записи. Скопированная schema-only структура не считается применённой историей; baseline не выполняется. Имя БД, роль и endpoint сохраняются.

Первое восстановление выполнено 2026-10-17: схема `006`, 3 пользователя, 4 привычки и 656 синтетических записей дня. Журнал содержит реальные применения `001–006`, ожидающих миграций нет. В новом clone или на новом ноутбуке подключайтесь к существующему dev без повторного reset.

## Production

Точки запуска образа сохраняются: `node dist/server.js` и Railway Pre-Deploy `node dist/db/migrate.js`. Образ задаёт `DB_ENVIRONMENT=production`; добавлять эту переменную в Railway не требуется. Production использует существующие `DATABASE_URL`, `MIGRATION_DATABASE_URL`, JWT-секреты и настройки сервиса. Локальные env-файлы не загружаются.

Независимая разрешённая цель проверяется только в dev и тестовом контуре. Переменные `DB_EXPECTED_*` в production не нужны. Сохраняются проверка PostgreSQL URL, согласованность БД/роли обоих подключений и требование direct-подключения мигратора. Добавление dev-БД не требует изменения переменных Railway, запуска deployment, повторного baseline или сброса production.

## Миграции PostgreSQL

Команды для dev из корня:

```sh
pnpm db:status
pnpm db:migrate
```

Все команды имеют `--help` и фиксированный dev-контекст без production-переключателя. `db:status` читает согласованный снимок в read-only транзакции: показывает наличие журнала и идентификаторы применённых/ожидающих SQL. Пустая схема без журнала допустима; непустая схема без журнала, разрыв, неизвестная версия и изменённый checksum дают отказ без исправлений.

`db:migrate --to NNN` применяет непрерывный префикс до существующей трёхзначной версии; без `--to` — всю цепочку. Версия ниже применённой отклоняется. Для возврата к прежней версии используйте явное восстановление dev ниже. Алиас `pnpm --filter @sadhana/api migrate` сохраняется.

В dev мигратор проверяет оба URL и независимую разрешённую цель, создаёт `schema_migrations`, сверяет SHA-256 и применяет новые SQL. `--help` описывает вход; неизвестные аргументы отклоняются. При ошибке драйвера/SQL возвращается ненулевой код без содержимого SQL и пользовательских записей. Сохраняются транзакция каждого файла с журналом, advisory lock и ограничения времени. Обычная миграция не пересоздаёт БД и не заполняет данные.

Исторический baseline отделён от dev. Его проверки и явное подтверждение сохранены в `node dist/db/migrate.js --baseline-confirmed-001-006` (либо `migrate:baseline`) с `MIGRATION_BASELINE_CONFIRMATION=reviewed-current-schema-and-sleep-data-001-006` и существующим direct production-подключением. Он только фиксирует подтверждённые 001–006, не исполняя SQL; `applied_at` остаётся пустым. Для новой dev-БД baseline не используется, в принятом production повторно не выполняется. Исторический контекст: [инвентаризация production Neon](../../.scratch/monorepo-migration/decisions/10-production-migration-inventory.md).

## Синтетические dev-профили

После обычных миграций до `006` выполните из корня:

```sh
pnpm db:dev-seed --help
pnpm db:dev-seed --date 2026-10-16
```

Для первого заполнения укажите фактический московский день запуска. Дата обязательна и должна быть реальной календарной датой `YYYY-MM-DD` (год от `0003`, чтобы вместить двухлетнюю историю). Для воспроизведения исходника укажите прежнюю опорную дату. Неизвестные аргументы и production-переключатель отклоняются. Команда использует общую проверку dev-цели и direct-подключение; SQL сама не применяет.

Задайте `DEV_FIXTURE_PASSWORD` **только в игнорируемом `apps/api/.env.dev.local`**. Унаследованное значение переменной не заменяет локальный пароль. Минимум — 6 символов, максимум — 72 байта UTF-8 (граница bcrypt). Один выбранный локально пароль подходит для всех трёх аккаунтов; пароли и хеши в вывод не попадают. Входите через обычную форму email/пароль в dev-web с настоящим API. Профили:

| Email | Содержимое |
| --- | --- |
| `empty@example.test` | Нет привычек и записей дня. |
| `daily@example.test` | «Прогулка» (`walk`), «Чтение» (`reading`), месяц ежедневных записей. |
| `history@example.test` | Те же привычки, два календарных года истории, каждый седьмой день пропущен. |

Текущий генератор явно поддерживает схему `007` с проверенными checksum всей применённой цепочки; состав набора версии `2` не изменился. Для восстановления `006` используется совместимый Git-исходник `e232bb629fa98b7455886c572e7341a4e8180a4c` с генератором версии `2`. Другие схемы также требуют совместимого генератора из соответствующего Git-исходника. Все прикладные таблицы должны быть пустыми. Повторный запуск отказывает, сохраняя имеющиеся записи. Заполнение и проверка записанных данных выполняются в одной транзакции, с блокировкой прикладных записей на её время; ошибка откатывает весь набор. Не запускайте параллельно миграции или работу приложения.

Оба диапазона начинаются на следующий день после даты, отстоящей от опорной на один месяц либо два года (с ограничением числа последним днём месяца), и заканчиваются опорным днём включительно. Опорный день не пропускается даже в длинном профиле. Например, для `2026-01-02` обычный профиль содержит 31 день с `2025-12-03`, длинный — диапазон с `2024-01-03` с пропусками. Даты/времена имеют московское смещение `+03:00`, расчёт не зависит от часового пояса компьютера. В полях `bedtime` хранится отбой текущего дня в 23:00, в `wakeTime` — подъём в 07:00; сохранённая `duration` учитывает отбой **предыдущего дня**. Первый день и подъём после пропуска не имеют известной ночной длительности.

От начала каждого диапазона цикл из семи дней задаёт неполные времена: во втором дне нет подъёма, в третьем нет отбоя; в пятом — дневной сон 30 минут, в остальных его нет (`null`). Отметки повторяют трёхдневный цикл: прогулка выполнена/чтение не выполнено; обе отсутствуют; прогулка не выполнена/чтение выполнено. Так покрываются сон через полночь, неполные времена, дневной сон и переходы месяцев/лет. Данные полностью синтетические; архивирование не добавляется.

Версия и дата воспроизводят одинаковые предметные записи, UUID пользователей/привычек и ID записей дня. Технические времена и отдельные солёные bcrypt-хеши с cost `10` не входят в побайтовую воспроизводимость. Обычный старт API/web не вызывает генератор и не сдвигает даты: изменения через приложение сохраняются. Публичные `devFixtureVersion`, `buildDevFixtures`, `seedDevFixtures` и `verifyDevFixtures` в `src/db/dev-fixtures.ts` позволяют следующему тикету восстановить совместимый Git-исходник и сверить пользователей, привычки, даты, отметки и сохранённые данные сна; проверка исходника читает согласованный read-only снимок и не пересчитывает результат через API.

## Обновление тестовых записей

Для замены текущего тестового набора без изменения структуры остановите API и другую работу с dev, затем выполните:

```sh
pnpm db:dev-reseed --help
pnpm db:dev-reseed --allow-reset --date 2026-10-17
```

Оба аргумента обязательны. `--allow-reset` разрешает потерю существующих прикладных записей; дата задаёт конец новой синтетической истории. Команда использует текущий генератор и совместимую применённую версию с проверенными checksum. Она не применяет SQL и не принимает Git-ref, версию или произвольный список таблиц. `db:dev-seed` сохраняет отказ при непустых таблицах.

Через одно соединение в одной транзакции выполняются проверка истории, блокировка таблиц, очистка `users`, `habits`, `daily_entries` без CASCADE, заполнение и сверка сохранённых записей. Ошибка вставки или сверки откатывает всю замену, сохраняя прежний набор. До очистки проверяются отсутствие посторонних сессий, известный состав таблиц и поддерживаемые зависимости. Пользовательские триггеры/правила, выражения вне поддерживаемой схемы `006` (включая defaults с sequence), дополнительные CHECK/exclusion constraints, индексы с выражениями/условиями, внешние FK и неподдерживаемые виды таблиц вызывают отказ. Перед коммитом дополнительно сравнивается полный журнал. Структура, расширения и журнал миграций, включая технические времена, сохраняются.

## Восстановление структуры dev из Git

Для возврата к известной структуре и данным остановите API и другую работу с dev, затем выполните из корня:

```sh
pnpm db:dev-reset --help
pnpm db:dev-reset --allow-reset --source-ref HEAD --to 006 --date 2026-01-02
```

Все четыре аргумента обязательны. `--allow-reset` разрешает потерю всей прикладной области `public`, включая экспериментальные таблицы, функции, данные и прежний журнал. Сама БД, её имя, endpoint и роль сохраняются. Команда не принимает имя БД/схемы, production-переключатель, `latest` или неявную дату. Символический ref разрешается один раз в commit; итог содержит этот commit, версию генератора, схему и дату. Исходник должен быть заранее сохранён обычным коммитом проекта; команда сама коммиты не создаёт. Для восстановления другого состояния замените `HEAD` нужным совместимым коммитом или тегом.

Поддерживаемый формат исходника — `src/db/dev-fixtures.ts` с `devFixtureVersion` и публичными `buildDevFixtures`, `validateFixtureDate`, `validateFixturePassword`, `seedDevFixtures`, `verifyDevFixtures`, его модули `src/db/migrate.ts`, `src/config/environment.ts` и непрерывная SQL-цепочка того же commit. `devFixtureVersion.schema` должна совпадать с `--to`. Область SQL разрешается отдельным fingerprint проверенного префикса `001–006` из `259975c`: допустим другой commit с теми же байтами SQL. Изменённый или новый префикс требует проверки области и явного добавления поддержки в `git-fixture-source.ts` до очистки; одного заявления генератора недостаточно. Исходники выборочно извлекаются через локальный Git во временный каталог; ветка, рабочая копия и index сохраняются. Исторические env и конфигурации целей не извлекаются. Заполнение/проверка выполняются кодом выбранного commit.

Используются установленные зависимости API: декларации `pg`, `bcrypt`, `dotenv` сохранённого `package.json` должны совпадать с текущими. Нужны dev-зависимости, включая `tsx`; production-образ для локального сброса не предназначен. Новые локальные зависимости вне поддерживаемого формата требуют явной поддержки. До очистки проверяются SQL, версия, дата, пароль, загрузка исторических модулей, построение набора и работа bcrypt. Исторический процесс не наследует секреты окружения; URL и пароль получает через stdin, вывод не публикуется. Временный каталог очищается после успеха и ошибки.

Перед очисткой проверяются фактическая БД/роль, владение `public`, право CREATE в этой БД, доступность доверенного `uuid-ossp` и отсутствие посторонних сессий. Поддерживаются штатный `plpgsql` в `pg_catalog` и `uuid-ossp` в `public`. Неподдерживаемое расширение или зависимость между `public` и внешними объектами, включая транзитивные связи в обе стороны, приводят к отказу до очистки. Проверка учитывает внутренние объекты, например правила представлений и принадлежность расширениям. Независимые внешние объекты сохраняются; экспериментальные объекты внутри `public` удаляются. Новое подключение после проверки сессий она не предотвращает: пользователь должен остановить параллельную работу.

В одной транзакции повторяется проверка и выполняются `DROP SCHEMA public CASCADE` и `CREATE SCHEMA public AUTHORIZATION CURRENT_USER`. Владелец получает права на новую `public`, дополнительные роли не наделяются доступом. Затем общий мигратор создаёт журнал и применяет исторические SQL; `001` заново устанавливает `uuid-ossp`. Заполнение и read-only проверка подтверждают исходные записи. Подключения мигратора/исторического кода получают фиксированный `search_path=public` только после проверки исходного URL. Пользовательские URL с `options` по-прежнему запрещены.

`DROP DATABASE`/`CREATE DATABASE`, служебное подключение, CREATEDB/superuser, baseline, обратный SQL и завершение чужих процессов не используются. Ошибка подготовки сохраняет прежнее состояние. После успешной очистки автоматического возврата нет: ошибка сообщает этап (`clear`, `migrate`, `seed`, `verify`) и прочитанную версию/пустую структуру либо невозможность чтения. При устранении причины повторите явное восстановление. Для проверки выпускаемого перехода используйте полную репетицию ниже.

Первоначальная настройка Neon использует эту же команду для очистки скопированной schema-only структуры и сборки одной рабочей БД. Постоянная dev-ветка, одна рабочая БД и права отдельной роли уже подготовлены в тикете 07. Повторное создание ресурсов для ежедневной работы не требуется. Docker подтверждает механику PostgreSQL; доступность ресурсов и прав конкретного аккаунта проверяется отдельно при первоначальной настройке.

## Репетиция перехода

Остановите API и другую работу с dev. Репетиция очищает всю `public` в той же БД и оставляет её на проверенной целевой версии:

```sh
pnpm db:rehearse --help
pnpm db:rehearse --allow-reset --source-ref <saved-commit> --from 006 --to 007 --date 2026-01-02 --checks <name>
```

Все аргументы обязательны, `--to` строго новее `--from`; `latest`, неизвестные и повторные параметры запрещены. Исходная версия задаётся по фактической схеме перед выпуском, включая несколько новых SQL при необходимости. Совместимый Git-исходник готовится тем же способом, что для reset. До очистки проверяются цель, пароль/дата, исходник, побайтовое совпадение целевого префикса до `--from`, полнота сценария, проверенная область целевого SQL и права/зависимости `public`. Целевые SQL копируются во временный каталог, сценарий читается в память; последующее редактирование файлов не меняет запущенную репетицию. Рабочая копия и index не переключаются.

Небольшой контракт именованных проверок — файл `apps/api/src/db/rehearsal-checks/<name>.json`. Имя содержит только латинские буквы, цифры, `_` и `-`. Обязательны точные `from`/`to`, непустые массивы `source`, `schema`, `data`, `preservation`. Каждый элемент содержит один SQL-запрос `sql` и независимый ожидаемый массив строк `rows`. Все запросы выполняются в read-only транзакции с `search_path=public`; опорная дата доступна как `current_setting('sadhana.fixture_date')`. Запрос должен явно упорядочить строки. Ошибки сравнения не печатают записи или SQL.

Необязательный `preserveTables` перечисляет прикладные таблицы (`users`, `habits`, `daily_entries`), которые миграция обязана сохранить целиком. На этапе `source` сохраняется полный снимок всех полей их строк, а на этапе `preservation` он сравнивается с фактическим состоянием, включая солёные хеши паролей и технические времена. Журнал миграций в этот список не входит; его неизменность при повторном запуске проверяется отдельно.

Для миграции удаления дублирующих индексов предусмотрен сценарий с фиксированной опорной датой:

```sh
pnpm db:rehearse --allow-reset --source-ref e232bb629fa98b7455886c572e7341a4e8180a4c --from 006 --to 007 --date 2026-01-02 --checks duplicate-indexes
```

Он проверяет удаление только согласованных индексов/ограничения, сохранение первичного ключа записи дня и UNIQUE email, все предметные значения исходного набора и полные строки трёх прикладных таблиц. Команда, как и другие репетиции, очищает текущий dev; API и параллельную работу с ним нужно остановить заранее.

Пример для **будущей** миграции, добавляющей `users.profile_kind` со значением из локальной части тестового email (такой SQL пока не добавлен в production-цепочку):

```json
{
  "from": "006",
  "to": "007",
  "source": [{
    "sql": "SELECT email FROM public.users ORDER BY email",
    "rows": [{"email":"daily@example.test"},{"email":"empty@example.test"},{"email":"history@example.test"}]
  }],
  "schema": [{
    "sql": "SELECT data_type FROM information_schema.columns WHERE table_schema='public' AND table_name='users' AND column_name='profile_kind'",
    "rows": [{"data_type":"text"}]
  }],
  "data": [{
    "sql": "SELECT email, profile_kind FROM public.users ORDER BY email",
    "rows": [{"email":"daily@example.test","profile_kind":"daily"},{"email":"empty@example.test","profile_kind":"empty"},{"email":"history@example.test","profile_kind":"history"}]
  }],
  "preservation": [{
    "sql": "SELECT count(*)::int AS count FROM public.habits",
    "rows": [{"count":4}]
  }]
}
```

При добавлении сценария отдельно проверьте область всей целевой цепочки: только управляемая `public`, штатный `plpgsql` и `uuid-ossp`, без внешних объектов/настроек БД. Добавьте проверенный fingerprint префикса в `reviewedSqlPrefixes` в `src/db/dev-sql-scope.ts`. Это явный допуск после ревью SQL, а не самодекларация сценария. Без него переход откажет до очистки. До появления следующей прикладной миграции встроенного production-сценария `006 → 007` нет; механика проверяется отдельным тестовым SQL вне production-каталога.

Порядок: восстановить прежнюю `public` → применить исходные SQL → заполнить совместимым историческим генератором → проверить его записи и `source` → применить целевые SQL → проверить `schema`, `data`, `preservation` → снять все строки таблиц/состояния sequences и полный журнал (включая технические времена) → повторить мигратор → сравнить снимки без потери точности чисел. Проверки читают сохранённые записи, не ответы API. Изменение числа записей допустимо, если оно соответствует явному ожидаемому результату сценария.

Только успешное завершение всех этапов даёт код `0`; итог содержит безопасную цель, commit, версии, дату и результаты этапов. Ошибка сообщает этап и прочитанную достигнутую версию либо невозможность чтения; прежнее состояние после очистки автоматически не восстанавливается. Устраните причину и повторите всю репетицию с исходника.

Каждый новый SQL проверяется на постоянном dev перед выпуском; после редактирования SQL заново выполняется вся репетиция, а не только повтор мигратора на обновлённой схеме. Railway Pre-Deploy и исторический production-журнал сохраняются. При неудачном выпуске сначала выясните реально применённую версию, затем проверяйте и выпускайте исправление вперёд; автоматического отката БД нет. Перед возвратом прежней версии приложения проверьте её совместимость с фактической схемой, включая уже успешно применённые миграции.

## Изолированные проверки

Обычные API-тесты и CI-образ используют явный `DB_ENVIRONMENT=test` и несекретную цель `test` из `config/database-targets.json`: `postgres://fixture:fixture@db.invalid/app` для обоих URL плюс фиктивные JWT-секреты. Это отдельная проверяемая конфигурация без production-доступов. Проверка `GET /` не открывает соединений к БД.

Обычные workspace tests не подключаются к PostgreSQL, даже если задан `MIGRATION_TEST_DATABASE_URL`. Для явного прогона из корня:

```sh
pnpm db:test --help
pnpm db:test --target dev
MIGRATION_TEST_DATABASE_URL=<direct-test-url> pnpm db:test --target test
```

`--target dev` использует общий dev-env и разрешённую dev-цель; постоянная БД не пересоздаётся. API и прочую работу с dev на время теста лучше остановить: тестовый мигратор использует ту же advisory lock, что и обычный. `--target test` требует отдельный URL и независимую несекретную секцию `test` файла `config/migration-test-target.json` (direct/runtime хосты, порт, БД, роль). Начальное `null`, отсутствие URL, конфликт `DB_ENVIRONMENT`, pooled URL и неправильная цель дают ненулевой код, а не пропуск. Альтернативный файл задаётся `MIGRATION_TEST_TARGETS_PATH`: относительный путь разрешается от корня репозитория, абсолютный также допустим. Не формируйте разрешённую цель из проверяемого URL.

Для временного локального PostgreSQL можно использовать Docker. Выберите свободный порт и уникальное имя контейнера; например:

```sh
docker run --detach --rm --name sadhana-migration-test \
  --publish 127.0.0.1:55432:5432 --tmpfs /var/lib/postgresql/data \
  --env POSTGRES_USER=fixture_admin --env POSTGRES_PASSWORD=local-test-only \
  --env POSTGRES_DB=postgres postgres:16
docker exec sadhana-migration-test pg_isready -U fixture_admin -d postgres
# Выполнить после готовности сервера:
docker exec sadhana-migration-test psql -U fixture_admin -d postgres -v ON_ERROR_STOP=1 \
  -c "CREATE ROLE fixture LOGIN PASSWORD 'local-test-only' NOCREATEDB NOSUPERUSER;" \
  -c 'CREATE DATABASE migration_test OWNER fixture;' \
  -c 'CREATE DATABASE reset_test OWNER fixture;'
```

Дождитесь готовности. Запишите в отдельный несекретный файл, например `/tmp/sadhana-migration-target.json`:

```json
{
  "test": {
    "directHost": "127.0.0.1",
    "runtimeHost": "127.0.0.1",
    "port": 55432,
    "database": "migration_test",
    "role": "fixture"
  }
}
```

Создайте также `/tmp/sadhana-reset-target.json` с той же секцией `test`, но независимым разрешённым именем `"database": "reset_test"`. Это отдельная заранее подготовленная БД для очистки всей `public`; она не должна совпадать с основной тестовой или постоянной dev-БД. Команды reset/reseed её не создают и не удаляют.

Запуск и обязательная очистка после успеха **или ошибки**:

```sh
MIGRATION_TEST_TARGETS_PATH=/tmp/sadhana-migration-target.json \
MIGRATION_TEST_DATABASE_URL=postgres://fixture:local-test-only@127.0.0.1:55432/migration_test \
MIGRATION_RESET_TEST_TARGETS_PATH=/tmp/sadhana-reset-target.json \
MIGRATION_RESET_TEST_DATABASE_URL=postgres://fixture:local-test-only@127.0.0.1:55432/reset_test \
  pnpm db:test --target test
docker stop sadhana-migration-test
```

Контейнер хранит данные в tmpfs и удаляется после остановки. Для внешней тестовой цели нужна отдельная БД/роль с правами создания/удаления схем и установки `uuid-ossp`; для reset/reseed используется отдельная заранее подготовленная тестовая БД с владельцем fixture без CREATEDB/superuser. Production-доступы не используются. TLS на Neon задаётся обычными разрешёнными параметрами URL.

`test/db/dev-reset-postgres.test.ts` запускается только через `--target test` и требует отдельные `MIGRATION_RESET_TEST_DATABASE_URL` и `MIGRATION_RESET_TEST_TARGETS_PATH`. Путь разрешается от корня репозитория, как у основной тестовой цели. Отсутствующая конфигурация или совпадение с основной тестовой БД дают неуспех. Перед тестом `public` должна быть пустой; сценарии не занимают существующие объекты. Проверяются та же БД до/после, отсутствие CREATEDB/superuser, удаление экспериментальной таблицы, сохранение независимой внешней таблицы, отказ при hstore/внешнем представлении/FK, историческое восстановление до 006 и повтор после ошибки на 005. Reseed проверяется на новом наборе и неизменном полном журнале/структуре, а также на откате при ошибке вставки и сверки. Временные объекты очищаются после успеха и ошибки. `db:test --target dev` эти разрушительные сценарии пропускает и не очищает постоянную `public`; весь Docker-контейнер удаляет подготовивший его контур.

Контур повторно проверяет цель перед соединением, затем добавляет собственный уникальный `search_path`; входной URL с `options` запрещён. Сценарии мигратора/первичного генератора создают отдельную схему, удаляют её в `finally` после успеха/ошибки и очищает временные SQL-файлы. Проверяются read-only статус, маленькая цепочка механики, транзакции и конкуренция; отдельно — настоящая цепочка, преобразование сохранённых данных сна и исторический baseline. `test/db/dev-fixtures-postgres.test.ts` дополнительно проверяет сохранённые профили, обычную авторизацию/refresh cookie, сохранность изменения через API после перезапуска, отказ повторного заполнения и откат всего набора при SQL-ошибке. Дочерний вывод драйвера/SQL не публикуется: команда сообщает безопасную цель, счётчики результатов и имена упавших сценариев; ошибка любого сценария даёт ненулевой код. Сборка не нужна; PostgreSQL не становится обязательным для CI.
