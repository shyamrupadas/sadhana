# Sadhana API

Код перенесён из отслеживаемых файлов коммита `6a00918b1699af6f0d4882b637a942846ce95ff6` локального репозитория `sadhana-backend`. SQL-миграции 001–006 сохранены без изменений.

Для локального запуска скопируйте шаблон и заполните `DATABASE_URL`, `JWT_SECRET` и `JWT_REFRESH_SECRET`:

```sh
cp apps/api/.env.example apps/api/.env.local
```

`apps/api/.env.local` не попадает в Git. Для подключения к Neon укажите URL с `sslmode=require`; при использовании production-базы локальные изменения данных сохраняются в ней. API слушает `0.0.0.0:8080` (или порт из `PORT`).

Из корня workspace: `pnpm dev` запускает web и API вместе, `pnpm dev:api` — только API, `pnpm dev:web` — только web. `pnpm build:api` собирает API.

## Миграции PostgreSQL

Для мигратора задайте отдельный `MIGRATION_DATABASE_URL` с **прямым** адресом той же ветки Neon. `DATABASE_URL` приложения может оставаться pooled; мигратор его не использует. Запуск из корня workspace:

```sh
pnpm --filter @sadhana/api migrate
```

Мигратор создаёт `schema_migrations`, сверяет SHA-256 точных байтов SQL и применяет только новые файлы. На существующей базе без журнала обычный запуск остановится. Исторические 001–006 в такой базе можно записать **только после повторной сверки схемы и признаков преобразования данных** с [инвентаризацией production Neon](../../.scratch/monorepo-migration/decisions/10-production-migration-inventory.md). В частности, подтвердите перенос `bedtime` из 005 по текущим данным и наличие новых ключей сна после 006: мигратор не может восстановить точную историю выполнения 005 из одной схемы. Сначала выполните процедуру на изолированной ветке Neon, полученной от production, и проверьте два обычных повтора. Затем на подтверждённой рабочей ветке выполните однократную команду с явным подтверждением выполненной сверки:

```sh
MIGRATION_BASELINE_CONFIRMATION=reviewed-current-schema-and-sleep-data-001-006 pnpm --filter @sadhana/api migrate:baseline
```

Эта команда не исполняет SQL 001–006. Для каждой записи она сохраняет время записи в журнал и признак ретроспективного учёта, а `applied_at` оставляет пустым: точная дата первоначального применения неизвестна. После неё обычный `migrate` проверяет суммы и применяет только более новые миграции. Запуск базовой команды повторно завершится ошибкой.

Для интеграционных тестов используйте отдельную локальную PostgreSQL или изолированную тестовую базу и задайте `MIGRATION_TEST_DATABASE_URL`. Тесты создают и удаляют собственные временные схемы внутри неё.
